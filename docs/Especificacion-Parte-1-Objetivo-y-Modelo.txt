Punto 1 — Objetivo del sistema (especificación + 
lógica) 
1.1 Definición formal del objetivo 
Objetivo: construir, para una semana W, un conjunto de sesiones (una por día operativo) 
donde cada sesión está compuesta por bloques y, para cada bloque, se generan 
prescripciones de ejercicios específicas por nivel/grupo de nivel, respetando las reglas 
de: 
 Distribución semanal de patrones (superior/inferior y variación) 
 SPOM (ruta + intensidad % + patrón activo + categoría) 
 Compatibilidad (intensidad ↔ dificultad ↔ contracción ↔ formato ↔ selección de 
ejercicios) 
 Presupuesto del bloque (volumen/reps o duración objetivo por bloque) 
 Contrato de salida (estructura estandarizada, auditable y reproducible) 
Entrada mínima: tablas/datasets del sistema (rotador semanal/plan por nivel, SPOM, 
intensidades, formatos, base de ejercicios, reglas de contracción y niveles). 
Salida mínima: WeekPlan completo, con trazabilidad por decisión. 
1.2 Alcance exacto (qué produce y para quién) 
El sistema debe producir todo completo: 
 Semana W (ej. 19) 
 Días: Lunes..Sábado (según configuración operativa; por defecto 6 días) 
 Para cada día: 
 Bloques: Initium, Nucleus, Deuteros 1, Deuteros 2, 
Athlos/Epikós 
 Para cada bloque: 
 Ruta (route_code) 
 Intensidad SPOM (pct) 
 Patrón activo / categoría 
 Formato (tipo + parámetros) 
 Ejercicios seleccionados (por nivel) 
 Prescripción (reps/duración/descanso/tempo/escalera/carga) 
 Observaciones (opcional) 
 Para cada grupo de nivel (según política): 
 ALFA_DELTA, SIGMA, OMEGA 
(En la práctica se emiten prescripciones al menos para 
alfa/delta/sigma/omega; si Spartan/Olympic existen en DB, se habilitan como 
niveles superiores opcionales.) 
1.3 Lógica del sistema (principio rector) 
El sistema es un pipeline determinista de restricciones. 
Principio: no se eligen ejercicios; se resuelven restricciones hasta que los ejercicios 
quedan determinados. 
Orden lógico de resolución (obligatorio): 
1. Estructura semanal: días y bloques (plantilla fija) 
2. Asignación de rutas por día/bloque/nivel (rotador/planificación semanal) 
3. SPOM: para cada ruta se resuelve % intensidad + patrón activo + categoría 
4. Derivación de presupuesto de bloque desde % (reps/duración, cantidad de 
ejercicios, dificultad) 
5. Derivación de mezcla de contracción (CON/EXC/ISO) desde % (y #ejercicios) 
6. Selección de formato por (bloque, nivel, %, tipo de esfuerzo) 
7. Selección de ejercicios por filtros (ruta, patrón, nivel, dificultad, contracción, 
equipo) 
8. Prescripción: asignación de reps/duración/descanso que: 
 cumple el presupuesto del bloque 
 es compatible con el formato 
 respeta el tipo de contracción y el nivel 
9. Validación global (día y semana) + fallback si faltan candidatos 
Resultado: una semana planificada que, dada la misma entrada, produce la misma salida. 
1.4 Condiciones de éxito (acceptance criteria) 
Una salida se considera válida si se cumplen todas: 
(A) Completitud 
 Existe plan para cada día configurado y para cada bloque obligatorio. 
 Cada bloque tiene route_code, pct, pattern_active, format, y ≥1 ejercicio 
por nivel objetivo. 
(B) Coherencia SPOM 
 pct y pattern_active coinciden con la entrada SPOM para esa semana y ruta. 
(C) Coherencia Intensidad 
 El bloque respeta: 
 reps_budget o duration_budget esperado para ese % 
 exercise_count_target esperado para ese % 
 difficulty_bucket esperado para ese % 
(D) Coherencia Contracción 
 La distribución CON/EXC/ISO del bloque cumple el objetivo para ese % (con 
tolerancia definida). 
(E) Coherencia Formato 
 El formato está permitido para ese bloque + nivel + intensidad. 
 
 Los parámetros del formato son válidos (vueltas/duración/descanso/escalera 
consistentes). 
 
(F) Selección de ejercicios 
 Cada ejercicio seleccionado pertenece a la ruta/patrón/categoría. 
 
 El nivel del ejercicio es compatible con el nivel del plan. 
 
 No hay duplicados inválidos ni colisiones prohibidas (reglas posteriores). 
 
(G) Reproducibilidad 
 Con mismos inputs y misma política de desempate (seed/orden), el output es 
idéntico.

1.6 Invariantes (reglas que no se rompen nunca) 
 SPOM manda sobre todo: si SPOM dice FL 95, no existe salida válida con FL 65. 
 
 El bloque Nucleus siempre existe. 
 
 Las prescripciones son función de: (ruta, %, nivel, formato, 
contracción); nunca de “preferencias”. 
 
 El output debe ser serializable (JSON/CSV/PDF) sin perder información estructural. 
 
 
 
 
 
 
 
 
 
 
 
 
Punto 2 — Entidades del dominio (modelo de datos + 
lógica) 
A continuación defino las entidades núcleo del sistema. Para cada una: (a) propósito 
lógico, (b) campos mínimos, (c) invariantes, (d) relaciones. Formato “ingeniería”: 
concreto, sin narrativa. 
 
2.1 WeekPlan 
Propósito lógico 
Unidad máxima de planificación. Agrega sesiones diarias y fija el contexto semanal (fuentes, 
reglas, versión de datos). Es el contenedor que permite reproducibilidad. 
Campos mínimos 
{ 
  "week_id": 19, 
  "start_date": "2025-12-22", 
  "timezone": "-03:00", 
  "days_order": 
["Lunes","Martes","Miércoles","Jueves","Viernes","Sábado"], 
  "level_groups": ["ALFA_DELTA","SIGMA","OMEGA"], 
  "day_plans": [ 
    {"day":"Lunes","level_group":"ALFA_DELTA","ref":"..."}, 
    {"day":"Lunes","level_group":"SIGMA","ref":"..."}, 
    {"day":"Lunes","level_group":"OMEGA","ref":"..."} 
  ], 
  "data_version": { 
    "spom_version": "2025-12", 
    "exercise_db_version": "2025-12", 
    "formats_version": "2025-12", 
    "rules_version": "v1" 
  }, 
  "generation_meta": { 
    "generator": "agent_id", 
    "seed": 12345, 
    "generated_at": "ISO8601" 
  } 
} 
 
Invariantes 
 week_id identifica de forma única el set de entradas SPOM/rotador. 
 
 Debe existir DayPlan para todo (day, level_group) configurado. 
 
 data_version y seed obligatorios si querés reproducibilidad. 
 
Relaciones 
 1 WeekPlan → N DayPlan. 
 
 
2.2 DayPlan 
Propósito lógico 
Representa una sesión diaria para un grupo de nivel. Define el orden de bloques y las rutas 
asignadas a cada bloque para ese día. 
Campos mínimos 
{ 
  "week_id": 19, 
  "day": "Lunes", 
  "level_group": "ALFA_DELTA", 
  "blocks_order": 
["INITIUM","NUCLEUS","DEUTEROS_1","DEUTEROS_2","ATHLOS_EPIKOS"], 
  "blocks": [ 
    {"type":"INITIUM","ref":"..."}, 
    {"type":"NUCLEUS","ref":"..."}, 
    {"type":"DEUTEROS_1","ref":"..."}, 
    {"type":"DEUTEROS_2","ref":"..."}, 
    {"type":"ATHLOS_EPIKOS","ref":"..."} 
  ], 
  "day_constraints": { 
    "primary_focus": "SUP|INF", 
    "notes": null 
  } 
} 
Invariantes 
 Tiene exactamente los bloques obligatorios (salvo que el modo operativo lo cambie 
explícitamente). 
 NUCLEUS no puede faltar. 
 blocks_order define el render y la ejecución. 
Relaciones 
 1 DayPlan → 1..N BlockPlan (por plantilla). 
2.3 BlockPlan 
Propósito lógico 
Unidad de decisión central. Para un bloque: resuelve ruta + SPOM + presupuesto + 
contracción + formato + ejercicios + prescripción. Debe ser auditable (trace). 
Campos mínimos 
{ 
"week_id": 19, 
"day": "Lunes", 
"level_group": "ALFA_DELTA", 
"block_type": "NUCLEUS", 
"route": {"code":"FL","name":"Front Lever"}, 
"pattern": {"active":"SUP_PULL","scope":"ESPECIFICO|GENERAL"}, 
"intensity_profile": {"pct":95,"bucket":"HIGH_SPECIFIC"}, 
"budget": { 
"reps_budget": 10, 
"duration_budget_sec": null, 
"exercise_count_target": {"min":2,"max":3}, 
"difficulty_bucket": 1 
  }, 
 
  "contraction_target": {"CON":0,"EXC":1,"ISO":2}, 
 
  "format": {"name":"Tempo Sets","params":{"sets":3,"rest_sec":60}}, 
 
  "prescriptions": [ 
    { 
      "level":"alfa", 
      "items":[ 
        {"exercise_ref":"...", "contraction":"ISO", 
"dose":{"duration_sec":6}, "rest_sec":60} 
      ] 
    } 
  ], 
 
  "trace": {"ref":"..."}, 
  "validation": {"status":"PASS","warnings":[]} 
} 
 
Invariantes 
 route.code obligatorio excepto en Initium (si lo tratás como “sin ruta”). 
 
 intensity_profile.pct debe venir de SPOM. 
 
 budget coherente con %. 
 
 prescriptions debe cubrir los niveles del level_group. 
 
Relaciones 
 1 BlockPlan usa 1 Route, 1 Pattern, 1 IntensityProfile, 1 Format. 
 
 1 BlockPlan contiene N Prescription. 
 
 
2.4 Route 
Propósito lógico 
Identificador del “movimiento objetivo”. Es la clave que vincula: 
 SPOM (intensidad/patrón) 
 Base de ejercicios (familia de variantes) 
 Correlaciones (rutas compatibles) 
Campos mínimos 
{ 
} 
"code": "FL", 
"name": "Front Lever", 
"domain": "SUP|INF", 
"default_category": "SUP_PULL", 
"aliases": ["Front Lever"] 
Invariantes 
 code es canónico (no cambia). 
 Debe mapear a al menos una categoría/patrón en SPOM. 
Relaciones 
 Route → 1..N Exercise (en DB). 
 Route ↔ Pattern (vía SPOM). 
 Route ↔ Route (vía correlación, opcional). 
2.5 Pattern 
Propósito lógico 
Define scope biomecánico y área del estímulo. Funciona como restricción de selección. 
Hay dos componentes: 
 active: etiqueta usada por SPOM (SUP_PULL, INF_CADERA, etc.) 
 scope: generalidad/especificidad (derivable del % o del tipo en SPOM) 
Campos mínimos 
{ 
"active": "SUP_PULL", 
"subtype": 
"PULL_VERTICAL|PULL_HORIZONTAL|BENT|STRAIGHT|MIXED|null", 
"scope": "GENERAL|SEMI|SPECIFIC", 
"notes": null 
} 
Invariantes 
 active pertenece a un enum cerrado. 
 scope no es decorativo: impacta la cardinalidad de candidatos en Exercise DB. 
Relaciones 
 Pattern condiciona Exercise.category/subcategory. 
2.6 IntensityProfile 
Propósito lógico 
Paquete de parámetros derivables de % que gobierna: 
 volumen de bloque 
 dificultad 
 #ejercicios 
 mezcla de contracción 
 formatos permitidos (en combinación con block+level) 
Campos mínimos 
{ 
} 
"pct": 95, 
"bucket": "LOW|MID|HIGH|MAX", 
"specificity": "GENERAL|SPECIFIC", 
"reps_budget": 10, 
"exercise_count_target": {"min":2,"max":3}, 
"difficulty_bucket": 1 
Invariantes 
 pct ∈ {55..95} según tu sistema (rangos reales de tabla). 
 Los demás campos deben ser deterministas respecto de % (misma tabla -> misma 
salida). 
Relaciones 
 IntensityProfile alimenta Budget, ContractionTarget, y ayuda a 
seleccionar Format. 
2.7 Exercise (registro de base de datos) 
Propósito lógico 
Candidato atómico seleccionable. Debe ser filtrable por 
ruta/patrón/nivel/contracción/dificultad y “dosificable” (reps/duración). 
Campos mínimos 
{ 
"exercise_id": "uuid-or-key", 
"name": "FL STR ISO 3''", 
"route_code": "FL", 
"category": "SUP_PULL", 
"subcategory": "PULL_STRAIGHT|PULL_VERTICAL|...", 
"level": "alfa|delta|sigma|omega|spartan|olympic", 
"difficulty_bucket": 1, 
"contraction": "ISO|EXC|CON", 
"dose_type": "REPS|DURATION", 
"rep_min": 0, 
"rep_max": 0, 
"duration_sec": 6, 
"equipment": ["rings","bar","parallettes","floor","wall"], 
"flags": ["requires_spot","high_joint_stress", "..."], 
"tags": ["frontlever","isometric"] 
} 
Invariantes 
 route_code obligatorio. 
 contraction obligatorio. 
 Debe existir al menos un mecanismo de dosificación (dose_type + valores). 
 level en enum cerrado. 
Relaciones 
 Exercise es seleccionado en PrescriptionItem. 
 Exercise puede referenciar progresión/regresión (opcional) para fallback. 
2.8 Format 
Propósito lógico 
Define la estructura temporal/organizacional del bloque (densidad y secuenciación). Es un 
“template” que impone constraints a: 
 distribución de reps/duración 
 
 descansos 
 
 #vueltas 
 
 escalera 
 
Campos mínimos 
{ 
  "name": "Singlet|Cluster|Tempo Sets|AMRAP Series|Tabata|EMOM|For 
Time|...", 
  "type": "DENSITY|TIMEBOX|LADDER|SETS", 
  "params_schema": { 
    "sets": "int?", 
    "rounds": "int?", 
    "work_sec": "int?", 
    "rest_sec": "int?", 
    "ladder": "string?" 
  }, 
  "compatibility": { 
    "allowed_blocks": ["NUCLEUS","DEUTEROS_1","..."], 
    "allowed_level_groups": ["ALFA_DELTA","SIGMA","OMEGA"], 
    "allowed_intensity_buckets": ["LOW","MID","HIGH","MAX"] 
  } 
} 
 
Invariantes 
 compatibility debe permitir validación automática. 
 
 params debe validar contra params_schema. 
 
Relaciones 
 Format es elegido por BlockPlan. 
 
 Format guía la función de prescripción. 
 
 
2.9 Prescription 
Propósito lógico 
Instanciación final ejecutable: lista de items (ejercicios) con dosis y descanso, por nivel. 
Campos mínimos 
{ 
  "level": "alfa", 
  "format_instance": {"name":"Tempo 
Sets","params":{"sets":3,"rest_sec":60}}, 
  "items": [ 
    { 
      "exercise_id": "X", 
      "contraction": "ISO", 
      "dose": {"duration_sec": 6, "reps": null}, 
      "rest_sec": 60, 
      "tempo": null, 
      "notes": null 
    } 
  ], 
  "block_totals": { 
    "total_reps": null, 
    "total_duration_sec": 180 
  } 
} 
 
Invariantes 
 Cada item debe referenciar un Exercise existente. 
 
 dose debe ser consistente con Exercise.dose_type. 
 
 block_totals debe aproximar el budget dentro de tolerancias definidas. 
Relaciones 
 Prescription pertenece a 1 BlockPlan. 
 PrescriptionItem.exercise_id → Exercise. 
2.10 Relaciones clave (mapa rápido) 
 WeekPlan 1→N DayPlan 
 DayPlan 1→N BlockPlan 
 BlockPlan 1→1 Route 
 BlockPlan 1→1 IntensityProfile (derivado de SPOM y tabla de intensidades) 
 BlockPlan 1→1 Pattern (viene de SPOM + derivación de scope) 
 BlockPlan 1→1 Format (por compatibilidad) 
 BlockPlan 1→N Prescription 
 Prescription 1→N Exercise (via items) 
Lógica global del punto 2 (por qué esta partición) 
 Route / Pattern / IntensityProfile forman el triángulo de intención (qué + cómo + 
cuánto). 
 Format es la plantilla de ejecución (estructura). 
 Exercise es el catálogo filtrable. 
 Prescription es la instanciación final. 
 BlockPlan es la unidad de decisión y auditoría. 
 DayPlan/WeekPlan agregan y permiten validación global y reproducibilidad. 
Punto 3 — IDs, códigos y normalización (especificación 
+ lógica) 
Objetivo del punto 
Definir un lenguaje canónico (códigos/IDs/enums) para que el agente: 
 pueda unir datasets (SPOM, rutas, ejercicios, formatos) sin ambigüedad 
 pueda validar y serializar planes consistentemente 
 no dependa de texto libre (nombres “humanos” solo display) 
3.1 Principios de normalización (reglas 
base) 
3.1.1 Canonical First 
 Todo objeto debe tener: 
 code (canónico, corto, estable) 
 id (único global si se requiere) 
 display_name (solo UI, no lógico) 
Nunca se usa display_name para matching. 
3.1.2 Matching determinista por claves 
 Join primario: 
 Route.code ↔ SPOM.route_code ↔ Exercise.route_code 
 Join secundario: 
 Pattern.active ↔ Exercise.category 
 Join terciario: 
 Level.code ↔ Exercise.level 
3.1.3 Normalización de texto 
Toda string que se reciba como input humano se convierte a canónico con: 
 trim 
 upper 
 reemplazo de múltiples espacios por uno 
 normalización de separadores (-, _, /) 
 diccionario de alias 
3.2 IDs y claves por entidad 
3.2.1 Route 
 Clave canónica: route_code (string corta) 
 Ejemplos: FL, PL, HSPU, PS, SU, MU, TTB, OAP, OAPU, FLR, MN_RP (normalizado) 
Regla de normalización de ruta: 
 Convertir / a _ para claves: 
 MN/RP → MN_RP 
 Mantener el display_name original para mostrar: 
 display: "MN/RP" 
 code: "MN_RP" 
Invariante: route_code es único en el sistema. 
3.2.2 Exercise 
 Clave primaria: exercise_id (UUID o key estable) 
 Claves lógicas: 
 route_code 
 level_code 
 contraction_code 
 category_code (+ subcategory_code) 
 difficulty_bucket (int) 
Regla: el exercise_id no debe codificar lógica (no deducir intensidad desde el nombre). 
3.2.3 Format 
 Clave canónica: format_code (string) 
 Ejemplos: SINGLET, AMRAP_SERIES, TABATA, EMOM, HIIT, INTERVAL, etc. 
 format_instance_id opcional (si versionás params) 
3.2.4 WeekPlan / DayPlan / BlockPlan 
 WeekPlan: week_id (int) + data_version_hash (string) 
 DayPlan: day_id = week_id + day_code + level_group 
 BlockPlan: block_id = day_id + block_type 
Esto habilita: 
 referencias estables 
 trazabilidad 
 caching por bloque 
3.3 Enums canónicos (cerrados) 
3.3.1 Días 
DAY_CODE ∈ {MON,TUE,WED,THU,FRI,SAT} 
MON=Lunes, TUE=Martes, ... 
3.3.2 BlockType 
BLOCK_TYPE ∈ {PHASE_PREVIA, INITIUM, NUCLEUS, DEUTEROS_1, 
DEUTEROS_2, ATHLOS_EPIKOS} 
Nota: si Athlos y Epikós son distintos en tu operación, separarlos en {ATHLOS, 
EPIKOS}. 
3.3.3 LevelGroup y Level 
LEVEL_GROUP ∈ {ALFA_DELTA, SIGMA, OMEGA} 
LEVEL_CODE ∈ {ALFA, DELTA, SIGMA, OMEGA, SPARTAN, OLYMPIC} 
Regla: LEVEL_GROUP define el set mínimo de niveles a emitir. 
 ALFA_DELTA → {ALFA, DELTA} 
 SIGMA → {SIGMA} 
 OMEGA → {OMEGA} 
 SPARTAN/OLYMPIC opcional si el bloque/dataset lo usa. 
3.3.4 Contracción 
CONTRACTION_CODE ∈ {CON, EXC, ISO} 
3.3.5 Intensidad 
Dos representaciones: 
 pct (int): 55, 60, 65, 70, 75, 80, 85, 90, 95 (según tablas reales) 
 intensity_bucket (enum derivado): LOW|MID|HIGH|MAX 
3.4 Categorías y patrones (normalización 
jerárquica) 
Tu sistema usa “patrón activo” como clave que se cruza con categorías. 
3.4.1 CategoryCode (macro) 
CATEGORY_CODE ∈ { 
SUP_PUSH, 
SUP_PULL, 
INF_RODILLA, 
INF_CADERA, 
LOWER,         
// si existe como agregado operativo 
MOBILITY, 
FLOW 
} 
3.4.2 SubcategoryCode (micro) 
Para evitar texto libre, modelar como códigos compuestos: 
 Para superior: 
SUBCATEGORY_CODE ⊆ { 
PUSH_VERTICAL, 
PUSH_HORIZONTAL, 
PULL_VERTICAL, 
PULL_HORIZONTAL, 
BENT_ARM, 
STRAIGHT_ARM, 
MIXED 
} 
 Para inferior: 
SUBCATEGORY_CODE ⊆ { 
HIP_DOMINANT, 
KNEE_DOMINANT, 
GENERAL_LOWER 
} 
3.4.3 Pattern.active (SPOM) → Category/Subcategory 
Pattern.active debe ser un enum cerrado que mapea determinísticamente. 
Ejemplo de mapping (extraído del SPOM de Semana 19): 
 SUP PUSH → SUP_PUSH 
 SUP PULL → SUP_PULL 
 INF RODILLA → INF_RODILLA 
 INF CADERA → INF_CADERA 
(En tu tabla SPOM se ven estas familias y rutas asociadas). 
[Planificaciones] - Semana 19 -… 
Regla: el SPOM puede traer además “Patrón” descriptivo (ej. “Planche 
específico”, “General Pull (horizontal + vertical)”); eso debe mapear a scope y/o 
subcategory. 
3.5 Scope / Especificidad (normalización) 
Necesitás una codificación estable para lo que vos llamás “abarcativo vs específico”. 
Definir: 
SCOPE_CODE ∈ {GENERAL, SEMI, SPECIFIC} 
Regla de derivación recomendada: 
 si pct >= 90 → SPECIFIC 
 si 70 <= pct < 90 → SEMI 
 si pct <= 65 → GENERAL 
Pero si SPOM incluye explícito “específico” vs “general”, esa etiqueta tiene prioridad. 
3.6 Normalización de nombres 
(display_name) 
3.6.1 display_name no afecta lógica 
 display_name se preserva para PDFs/UI. 
 Cualquier comparación o join debe usar code. 
3.6.2 Convención de nombres de ejercicios (solo display) 
Si querés consistencia en outputs humanos, estandarizar: 
<ROUTE> <VARIANTE> <CONTRACTION> <NIVEL/DETALLE> <DOSIS> 
Ej: "FL PRESS TUCK EXC x2" 
Pero reitero: la IA NO debe parsear esto para lógica; solo mostrarlo. 
3.7 Tabla de alias (resolver colisiones) 
Necesitás un diccionario central: 
{ 
"route_aliases": { 
"MN/RP": "MN_RP", 
"MN-RP": "MN_RP", 
"Manna / Reverse Planche": "MN_RP" 
}, 
"category_aliases": { 
"SUP PUSH": "SUP_PUSH", 
"SUPPUSH": "SUP_PUSH", 
"INF RODILLA": "INF_RODILLA" 
}, 
"level_aliases": { 
"alpha": "ALFA", 
"Δ": "DELTA" 
} 
} 
Regla: si el input no matchea alias ni enum, el agente debe fallar con error explícito (no 
inferir). 
3.8 Lógica del punto 3 (por qué esto es 
crítico) 
El sistema depende de joins entre múltiples tablas: 
 SPOM define % y patrón activo por ruta. 
 La base de ejercicios etiqueta cada ejercicio por ruta/patrón/nivel/contracción. 
 Formatos están restringidos por bloque/nivel/%. 
Sin normalización: 
 se rompen joins por diferencias como MN/RP vs MN_RP 
 aparecen duplicados (“FL” vs “Front Lever”) 
 el agente “inventa” equivalencias (inadmisible) 
Con este punto, la generación pasa de “texto interpretado” a “sistema tipado”. 
Punto 4 — Esquema de salida (contrato obligatorio del 
agente) 
Objetivo del punto 
Definir un output contract mínimo, cerrado y validable. El agente debe emitir estos campos 
sí o sí para que: 
 se pueda renderizar a PDF/Sheets 
 se pueda auditar (trace) 
 se pueda validar con reglas (tests) 
 se pueda re-generar idéntico (reproducibilidad) 
4.1 Formato de salida recomendado 
Formato primario: JSON (estructurado) 
Formato secundario: CSV/Sheet derivable (flatten) 
Formato terciario: PDF (render del JSON) 
La “verdad” es el JSON.

WEEK_DAYS = [MON, TUE, WED, THU, FRI, SAT]

5.5 Lógica detrás del 3 / 3 (razón de sistema) 
Esta regla no es fisiológica solamente, es sistémica. 
Problema a resolver 
Los alumnos no asisten todos los días. 
Si la semana fuera: 
 Lunes a miércoles: superior 
 Jueves a sábado: inferior

Solución del sistema 
Distribución intercalada y no trivial de SUP / INF. 
Resultado: 
 Cualquier combinación de 2–4 días tiene alta probabilidad de estímulo balanceado. 
 El sistema es robusto a asistencia parcial.

Punto 6 — Distribución de enfoque superior / inferior 
Regla 3/3 + mecanismo anti-sesgo por asistencia 
6.1 Propósito lógico del punto 
Este punto define cómo se asigna el foco SUP / INF a cada día de la semana de forma

 se cumpla el balance fisiológico mínimo 
 el sistema sea robusto a asistencia parcial 
 no exista dependencia de “qué días viene el alumno” 
 el SPOM pueda operar sin crear sesgos ocultos 
En términos de sistema: 
Esta capa resuelve el problema de distribución temporal del estímulo, no de 
contenido. 
6.2 Regla primaria (hard rule) 
En toda semana válida: - 3 días deben ser SUP (superior dominante) - 3 días deben ser INF (inferior dominante) 
Esto es invariante, no negociable. 
6.3 Definición formal de “día SUP / INF” 
Un día se define como SUP o INF exclusivamente por el bloque NUCLEUS. 
day.primary_focus =  
SUP  ⇔ NUCLEUS ∈ categorías SUP 
INF  ⇔ NUCLEUS ∈ categorías INF

Initium, Deuteros y Athlos/Epikós NO definen el foco del día. 
6.4 Qué problema real resuelve (modelo de asistencia) 
Suposición base (realista) 
 Los alumnos: 
 no vienen 6/6 
 suelen venir 2–4 días 
 eligen días “por conveniencia”, no por diseño 
Si NO existiera esta regla 
Ejemplo malo: 
MON–WED → SUP 
THU–SAT → INF 
Un alumno que entrena: 
 MON + WED + FRI 
→ 2 SUP + 1 INF (sesgo) 
 TUE + THU 
→ 1 SUP + 1 INF (ok) 
 MON + TUE 
→ 2 SUP (sesgo) 
�
�
el sistema se rompe por patrón de asistencia. 
6.5 Regla anti-sesgo (principio central) 
La distribución SUP / INF debe cumplir: 
Para cualquier subconjunto de días de tamaño 2 a 4, 
la probabilidad de recibir solo SUP o solo INF debe ser mínima. 
En términos prácticos: 
 No agrupar SUP consecutivos más allá de lo estrictamente necesario 
 Intercalar SUP / INF 
 Evitar patrones triviales (3 seguidos iguales) 
6.6 Restricciones estructurales de distribución 
Definimos un conjunto de restricciones duras: 
R1 — Cardinalidad 
count(SUP) = 3 
count(INF) = 3 
R2 — Separación 
No pueden existir 3 días consecutivos con el mismo foco. 
(2 consecutivos pueden existir, 3 no) 
R3 — Cobertura temprana 
En los primeros 3 días de la semana 
debe haber al menos 1 SUP y 1 INF. 
Esto protege a: 
 alumnos que entrenan solo L–M–X 
R4 — Cobertura tardía 
En los últimos 3 días de la semana 
debe haber al menos 1 SUP y 1 INF. 
Protege a: 
 alumnos que entrenan J–V–S

10.1 Propósito lógico 
Transformar SPOM.intensity_pct en una restricción de selección: 
 Define qué tan arriba o abajo en el árbol de categorías se permite seleccionar 
ejercicios. 
 Controla el tradeoff:

 Especificidad (técnica, neural, gesto final) 
En términos de sistema: 
scope gobierna el conjunto candidato; 
% gobierna el budget; 
ambos salen del mismo SPOMEntry pero actúan en capas distintas. 
10.2 Definición canónica: Scope 
Definimos un enum cerrado: 
SCOPE_CODE ∈ { GENERAL, SEMI, SPECIFIC, ULTRA } 
Semántica: 
 GENERAL: seleccionar desde la categoría raíz del patrón (máxima cobertura) 
 SEMI: restringir a subcategorías biomecánicas (horizontal/vertical, knee/hip) 
 SPECIFIC: restringir a familia técnica (bent/straight arm, músculo dominante) 
 ULTRA: restringir a la ruta/skill específica (FL, PL, PS, HT…) 
10.3 Input de la regla 
Entradas mínimas para resolver scope: 
 intensity_pct (obligatorio) 
 pattern_active (obligatorio) 
 pattern_descriptor (opcional, pero si existe tiene prioridad semántica) 
 route_code (obligatorio) 
10.4 Regla base: pct -> scope_code 
10.4.1 Mapeo determinista por rangos 
function scope_from_pct(pct): 
if pct >= 95: return ULTRA 
if pct >= 85: return SPECIFIC 
if pct >= 70: return SEMI 
return GENERAL 
Esto te da el comportamiento que describiste: 
 % alto ⇒ selección específica 
 % bajo ⇒ selección amplia 
10.5 Regla de override por descriptor 
(SPOM manda) 
Si pattern_descriptor existe, puede ajustar scope. 
10.5.1 Override semántico 
function scope_from_spom(pct, descriptor): 
base = scope_from_pct(pct) 
if descriptor contains "específico" or descriptor matches 
route_name: 
return max(base, SPECIFIC)    
// no puede ser GENERAL si dice 
específico 
if descriptor contains "General": 
return min(base, SEMI)        
// no puede saltar a ULTRA si 
dice general 
return base 
Invariante: el descriptor solo puede mover scope dentro de límites razonables, nunca 
invalidar el % (ej. 95% no puede terminar GENERAL).
