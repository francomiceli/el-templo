Punto 22 — Taxonomía de Formatos 
(Organización temporal del trabajo — modelo canónico del sistema) 
22.1 Definición formal de Format 
En el sistema de planificación, un Formato NO es una “idea de entrenamiento”, sino una 
plantilla operativa de organización del esfuerzo en el tiempo. 
Formalmente: 
Formato = función que transforma un presupuesto de trabajo (reps / 
tiempo / dificultad) en una secuencia temporal ejecutable. 
Un Format no define ejercicios, no define rutas, no define dificultad. 
Define cómo se consume el presupuesto ya asignado al bloque. 
22.2 Dimensiones estructurales de un Formato 
De la base de datos se desprende que todo formato está definido por 6 dimensiones 
canónicas: 
Format { 
format_id 
name 
block_type 
time_logic 
effort_logic 
priority_model 
intensity_window 
} 
Vamos una por una. 
22.3 Dimensión 1 — block_type (Dónde vive el 
formato) 
Todos los formatos están anclados a un tipo de bloque, no son globales. 
Valores observados en DB: 
 Initium 
 Nucleus 
 Deuteros 
 Athlos 
 Epikos 
Regla: 
 Un formato solo puede ser seleccionado si el BlockPlan.block_type coincide. 
 El mismo nombre de formato puede existir en múltiples bloques con reglas 
distintas. 
Ejemplo: 
 EMOM Initium 
 EMOM Nucleus 
 EMOM Deuteros 
Son formatos distintos, aunque compartan nombre. 
22.4 Dimensión 2 — time_logic (Cómo se organiza el 
tiempo) 
Esta es la clasificación primaria de la taxonomía. 
De la DB surgen 5 clases canónicas: 
1⃣ Time-based 
El tiempo es la variable dominante. 
Ejemplos: 
 EMOM 
 AMRAP 
 Tabata 
 Interval Training 
 Time Cap 
 For Time 
 Every X Seconds 
 HIIT 
Características: 
 El tiempo limita el trabajo 
 El volumen se adapta al tiempo 
 Alta dependencia de pacing 
2⃣ Volume-based 
El volumen es fijo o acumulativo. 
Ejemplos: 
 Accumulate 
 Chipper 
 Ladder 
 Pyramid 
 Death By 
 For Max (Reps) 
 Unbroken Reps 
Características: 
 Reps totales predefinidas o crecientes 
 El tiempo es consecuencia, no restricción primaria 
3⃣ Structure-based 
La secuencia está rígidamente definida. 
Ejemplos: 
 Singlet 
 Couplets 
 Triplets 
 Buy-in / Cash-out 
 Benchmark 
 Hero WOD 
 Rounds for Time 
 Task Priority 
Características: 
 Orden fijo de tareas 
 Baja variabilidad 
 Alta comparabilidad entre sesiones 
4⃣ Technical 
El foco es control, calidad o mecánica. 
Ejemplos: 
 Tempo Sets 
 Cluster 
 Complex 
 For Quality 
 For Tech 
 Flow Guiado 
 Unbroken Reps (cuando está clasificado como Technical) 
Características: 
 Velocidad controlada 
 Pausas prescritas 
 Alta exigencia técnica 
5⃣ Hybrid 
Combinación explícita de lógicas. 
Ejemplos: 
 EMOM + For Time 
 Broken Ladder 
 Rest-Pause 
 Open Style 
 Wave Loading 
 Task Priority vs Time Priority 
Características: 
 Más de una lógica activa 
 Reglas de transición internas 
 Mayor complejidad cognitiva 
22.5 Dimensión 3 — effort_logic (Cómo se expresa 
el esfuerzo) 
Independiente del tiempo, el formato define cómo se manifiesta el esfuerzo: 
Valores inferidos: 
 Continuous (AMRAP, For Time) 
 Intermittent (EMOM, Intervals) 
 Accumulative (Accumulate, Chipper) 
 Escalating (Ladder, Death By, Wave) 
 Fixed Sets (Tempo Sets, Singlet) 
Esto no se verbaliza al alumno, pero es clave para la IA. 
22.6 Dimensión 4 — priority_model (Qué manda si 
hay conflicto) 
Algunos formatos definen explícitamente qué priorizar: 
Ejemplos claros en DB: 
 Task Priority 
 Time Priority 
 Task Priority vs Time Priority 
 For Quality 
 For Max 
Modelo: 
priority_model ∈ {TASK, TIME, QUALITY, MAX_OUTPUT} 
Esto gobierna: 
 Criterios de corte 
 Penalizaciones 
 Instrucciones implícitas 
22.7 Dimensión 5 — intensity_window (Dónde puede 
existir el formato) 
Cada formato está ligado a rangos discretos de % de intensidad, no continuos. 
Ejemplos reales: 
 EMOM Initium Alfa → 55–90 
 Cluster Nucleus → 60–95 
 Singlet → 80–95 
 Tabata → 70–80 
 Flow Guiado → 55–60 
Regla: 
 El formato no es válido fuera de su ventana 
 Esto se cruza con SPOM + nivel + bloque 
22.8 Dimensión 6 — level_compatibility (Cuántos 
ejercicios admite) 
En la DB aparece un número recurrente (1, 2, 3). 
Interpretación estructural: 
format.exercise_slots = n 
Ejemplos: 
 Singlet → 1 
 Couplets → 2 
 Triplets → 3 
 Chipper → variable (pero mínimo definido) 
 Complex → ≥2 
Esto condiciona: 
 exercise_count_target 
 Distribución de contracciones 
 Dificultad combinada

22.10 Regla de oro del sistema 
El Formato nunca se elige por “variedad”. 
Se elige porque es el único compatible con el bloque, nivel, intensidad y

Punto 23 — Matriz de compatibilidad de 
formatos 
(bloque × nivel × intensidad → formatos permitidos) 
23.1 Qué ES esta matriz en tu sistema (definición 
exacta) 
En tu arquitectura, la matriz de compatibilidad: 
 NO es una regla derivada 
 NO es una heurística 
 NO es una inferencia 
�
�
Es un dataset explícito (la BD de Formatos). 
Formalmente: 
La matriz es una función discreta: 
AllowedFormats = f(Block, Nivel, Intensidad) 
donde: 
 Block ∈ dominio cerrado (Initium, Nucleus, Deuteros, Athlos, Epikos) 
 Nivel ∈ {Alfa, Delta, Sigma, Omega} 
 Intensidad ∈ grilla discreta {55, 60, 65, 70, 75, 80, 85, 90, 95} 
La salida no es un formato, es un conjunto de formatos válidos. 
23.2 Fuente de verdad (no negociable) 
La Base de Datos de Formatos es la única fuente de verdad. 
Cada fila de la BD representa: 
(Formato, Bloque, Nivel, Intensidad) → permitido 
Todo lo que no exista como fila: 
 no está permitido 
 no se puede “inferir” 
 no se puede “heredar” 
Esto es crítico para que el sistema sea cerrado y predecible. 
23.3 Normalización de ejes (para evitar errores lógicos) 
Eje 1 — Bloque 
Dominio cerrado (tal como aparece en BD): 
Initium 
Nucleus 
Deuteros 
Athlos 
Epikos 
No existen: 
 “bloques vecinos” 
 “bloques implícitos” 
Eje 2 — Nivel 
Dominio cerrado: 
Alfa 
Delta 
Sigma 
Omega 
⚠
Importante: 
La matriz opera por nivel explícito, no por grupos (Alfa/Delta juntos, etc.). 
La agrupación de niveles es una capa posterior (si se quiere), no acá. 
Eje 3 — Intensidad 
Dominio discreto, no continuo: 
{55, 60, 65, 70, 75, 80, 85, 90, 95} 
La intensidad no se interpola. 
23.4 Resolución de intensidad (pct → intensidad válida) 
Dado que SPOM produce un pct continuo, el sistema necesita una política de snapping. 
Política recomendada (determinista y conservadora) 
intensity_value = max{i ∈ grid | i ≤ pct} 
Ejemplos: 
 pct = 78 → 75 
 pct = 80 → 80 
 pct = 83 → 80 
 pct = 95 → 95 
Motivo: 
 nunca subir la intensidad real por redondeo 
 preservar coherencia metodológica 
Esta política es parte del contrato del sistema.

Punto 24 — Selección determinista de 
formato 
(prioridad “recomendados” > “secundarios” + 
tie-breakers) — a fondo, estrictamente sistémico 
24.1 Objetivo 
Dado un bloque ya definido por: 
 block_type 
 nivel 
 pct → intensity_value 
 contraction_slots (C/E/I efectivos, post-restricciones de movimiento) 
 exercise_count (slots) 
 work_budget (rep_equiv_total) 
se debe elegir un único format_code de forma: 
 determinista (misma entrada → misma salida) 
 trazable (explicar por qué ganó) 
 sin “criterio humano” implícito 
24.2 Fuentes de datos (autoridad) 
1. BD Formatos (Punto 23) 
Entrega candidatos con: 
 format_name 
 compatibility (1/2/3) 
 type (Time/Volume/Structure/Technical/Hybrid) 
 keyed por (bloque, nivel, intensidad) 
2. Definición formal del formato (catálogo / taxonomía) 
Para cada format_name debe existir metadata operativa: 
 supports_slot_count (min/max) 
 supports_contractions (CON/EXC/ISO) 
 param_schema (qué parámetros controla: rounds, sets, duration, tempo, 
etc.) 
 stability_class (carga operativa) 
Nota: la BD decide “permitidos”; el catálogo decide “si sirve para estos 
slots/contracciones”. 
24.3 Pipeline de selección (filtro + ranking) 
24.3.1 Paso A — Candidate set desde matriz 
C0 = AllowedFormats(block, nivel, intensity_value)   // BD Formatos 
24.3.2 Paso B — Filtros duros (hard constraints) 
Aplicar en orden fijo: 
F1 — Slot count 
C1 = {f ∈ C0 | exercise_count ∈ f.supports_slot_count} 
F2 — Contracción 
C2 = {f ∈ C1 | ∀slot ∈ slots: slot.contraction ∈ 
f.supports_contractions} 
F3 — Param constraints (si BD define caps por formato) 
Ejemplo: Tabata no admite ISO holds > X o EXC tempo > Y 
C3 = {f ∈ C2 | f.param_schema can represent required dose without 
violating caps} 
Si C3 queda vacío → fallback (24.8). 
24.4 “Recomendados” vs “Secundarios” (clasificación 
determinista) 
Tu BD tiene compatibility (1/2/3). En este punto lo convertimos en tiers. 
Definición de tiers (versión recomendada, simple) 
 Tier A (Recomendado) = compatibility == 2 
 Tier B (Secundario) = compatibility == 1 
 Tier C (Especial) = compatibility == 3 
Esto NO es “verdad universal”, es una convención de motor. 
Si vos querés otro mapping, se cambia en 
RulesVersion.compat_to_tier. 
Selección por tier 
A = {f ∈ C3 | tier(f) == A} 
if A not empty: C = A 
else: 
B = {f ∈ C3 | tier(f) == B} 
if B not empty: C = B 
else: 
C = {f ∈ C3 | tier(f) == C}   // último recurso 
Esto implementa exactamente: 
recomendados > secundarios (y luego especiales si no queda otra) 
24.5 Tie-breakers (orden total: siempre desempata) 
Una vez que tenés el set C (mismo tier), elegís con un orden total de desempate. 
Tie-breaker 1 — Fit por type según block_type (matriz interna fija) 
Definir una tabla BlockTypePreferredTypes (dato versionado): 
Ejemplo canónico: 
 NUCLEUS → preferir Technical > Structure-based > Time-based > 
Volume-based > Hybrid 
 DEUTEROS → preferir Time-based > Technical > Volume-based > 
Structure-based > Hybrid 
 ATHLOS → preferir Time-based > Hybrid > Volume-based > 
Structure-based > Technical 
 INITIUM → preferir Technical > Structure-based > Time-based > 
Volume-based > Hybrid 
 EPIKOS → preferir Hybrid > Structure-based > Time-based > Technical > 
Volume-based 
Scoring: 
type_rank = index_in_preference_list(f.type)   // menor = mejor 
Tie-breaker 2 — Complejidad operativa (stability_class) 
Definir stability_class por formato (dato en catálogo): 
 1 = muy estable (Singlet, Tempo Sets) 
 2 = estable (EMOM) 
 3 = medio (AMRAP Series, Ladder) 
 4 = alto costo cognitivo (Hybrid / Task Priority vs Time Priority) 
Elegir menor. 
Tie-breaker 3 — Parametrizabilidad exacta al budget 
Elegir el formato que produzca menor error de reconciliación al empaquetar: 
error = abs(delivered_rep_equiv - budget_total) 
choose min error 
(esto requiere simular parametrización rápida sin elegir ejercicios aún) 
Tie-breaker 4 — Rotador semanal / anti-repetición 
Si existe un rotador de formatos (o historial), aplicar: 
 penalizar repetir el mismo format_name en la misma ruta dentro de X semanas 
 si no hay historial, omitir 
Tie-breaker 5 — Orden canónico (para determinismo total) 
Si todavía hay empate: 
 elegir por format_name en orden lexicográfico (o format_id) 
Esto asegura que nunca hay “empate final”. 
24.6 Algoritmo final (resumen en pseudo) 
function choose_format(block, nivel, pct, slots, exercise_count, 
budget): 
intensity = snap_down(pct) 
C0 = query_bd_formats(block, nivel, intensity) 
  C1 = filter_slot_count(C0, exercise_count) 
  C2 = filter_contractions(C1, slots) 
  C3 = filter_param_schema(C2, budget, slots) 
 
  if empty(C3): return fallback_choose_format(...) 
 
  tier = highest_available_tier(C3)   // A > B > C 
  C = {f in C3 | tier(f) == tier} 
 
  return argmin_over_C( tuple( 
    type_rank(f.type, block), 
    stability_class(f), 
    budget_packaging_error(f, budget, slots), 
    rotation_penalty(f), 
    canonical_id(f) 
  ))

Punto 25 — Parámetros del formato 
(vueltas, duración, descanso, escalera) — a fondo, 
determinista, “engine-ready” 
25.1 Objetivo 
Una vez elegido el format_name (Punto 24), el motor debe instanciar ese formato en una 
Prescription concreta: 
 rounds / sets / ladders / steps 
 duration_total o interval_sec 
 rest_sec (si aplica) 
 reps_per_set o seconds_per_hold por slot 
 garantizando: 
 budget_total (Punto 17) 
 slots C/E/I (Punto 20–21) 
 restricciones del formato (catálogo / BD) 
 sin aleatoriedad 
Principio rector: 
Formato define parámetros; parámetros deben resolver “cómo 
empaquetar” un trabajo ya presupuestado. 
 
25.2 Modelo canónico: FormatInstance 
Representación mínima: 
{ 
  "format": "EMOM", 
  "params": { 
    "rounds": 10, 
    "interval_sec": 60, 
    "rest_rule": "REST_IS_REMAINDER" 
  }, 
  "work_packaging": { 
    "slot_payloads": [ 
      {"slot_id":"S1","mode":"ISO","per_round_sec":12}, 
      {"slot_id":"S2","mode":"EXC","per_round_reps":1}, 
      {"slot_id":"S3","mode":"CON","per_round_reps":2} 
    ], 
    "delivered_rep_equiv_total": 18 
  } 
} 
 
FormatInstance = format_name + params + “cómo se distribuye el trabajo dentro de 
esos params”. 
 
25.3 Catálogo obligatorio: ParamSchema por formato 
Para que un agente instancie formatos, cada formato debe declarar un schema de 
parámetros. 
Ejemplo: 
{ 
  "format": "EMOM", 
  "param_schema": { 
    "rounds": {"type":"int","min":4,"max":20}, 
    "interval_sec": {"type":"int","allowed":[45,60,90,120]}, 
"work_rule": 
{"type":"enum","allowed":["FIXED_PER_ROUND","ACCUMULATE"]}, 
"rest_rule": 
{"type":"enum","allowed":["REMAINDER","FIXED_REST"]} 
} 
} 
Sin schema, no hay instanciación determinista. 
25.4 Reglas globales (comunes a todos los formatos) 
25.4.1 Budget-first (invariante) 
El formato se ajusta para cumplir: 
delivered_rep_equiv_total == budget_total_rep_equiv (± tolerance) 
25.4.2 Preferencias por estabilidad (si hay múltiples soluciones) 
Cuando hay varias combinaciones válidas de parámetros: 
 elegir la que minimice complejidad: 
1. menos parámetros libres 
2. valores “canónicos” (ej 60s EMOM sobre 45s) 
3. menor rounding error 
25.4.3 Granularidad mínima 
 CON/EXC: reps enteras 
 ISO: segundos enteros, convertidos desde rep_equiv con rep_equiv_sec 
25.5 Parametrización por familia de formatos 
(determinista) 
Voy por los formatos que nombraste (EMOM, AMRAP, Singlet, Ladder, Tempo Sets, Tabata) 
y los parámetros que pediste. 
25.6 EMOM (Fixed Interval) 
25.6.1 Parámetros base 
 interval_sec (default 60) 
 rounds (entero) 
 rest_rule (rest = tiempo restante del minuto) 
25.6.2 Regla de construcción 
Inputs: 
 budget_total_rep_equiv 
 slot_allocations (rep_equiv por slot) 
 exercise_count 
Regla: 
1. Elegir interval_sec por prioridad: 
 60 si permitido 
 si ISO dominante y alta intensidad → 90 
 si Athlos y baja intensidad → 60 o 45 (si permitido) 
2. Elegir rounds para que el “per_round payload” sea estable: 
target_rep_equiv_per_round = clamp( budget_total / rounds, min=1, 
max=6 ) 
Selección determinista: 
 probar rounds en un set canónico (ej: [6,8,10,12,15]) 
 elegir el primero donde: 
 budget_total / rounds sea cercano a entero 
 per_round respete límites del formato (cap de reps por round) 
3. Distribuir por slot: 
 cada slot tiene slot_total_rep_equiv 
 convertir a per_round: 
per_round = floor(slot_total / rounds) 
remainder = slot_total - per_round*rounds 
distribute +1 to earliest rounds 
4. ISO conversion: 
per_round_sec = per_round_rep_equiv * rep_equiv_sec 
Output: rounds + interval + payload per round. 
25.7 AMRAP (Continuous Time Cap) 
25.7.1 Parámetros base 
 duration_sec (cap fijo) 
 cycle_definition (qué es 1 “vuelta”) 
 rest_rule (típicamente none) 
25.7.2 Cómo se parametriza sin romper budget 
AMRAP es tricky porque la gente puede hacer “más vueltas”. 
Tu sistema necesita que AMRAP sea budget-bounded. 
Dos políticas (elegir una como sistema): 
Política AMRAP-1 (recomendado): “AMRAP Series con sets cerrados” 
En vez de AMRAP puro, se define: 
 rounds_target (n vueltas objetivo) 
 duration_sec (cap) 
 el trabajo prescrito corresponde exactamente al budget 
 el cap es un límite, no un target de “infinitas vueltas” 
Parametrización: 
duration_sec = pick from allowed (6,8,10,12 min) 
rounds_target = choose so that reps_per_round stable 
payload_per_round computed like EMOM 
Política AMRAP-2 (AMRAP puro): “budget como mínimo” 
No recomendado para motor rígido: rompe invariantes (delivered != budget). 
25.8 Singlet (Fixed Sets, 1 ejercicio) 
25.8.1 Parámetros base 
 sets 
 reps_per_set (CON/EXC) o seconds_per_set (ISO) 
 rest_sec 
25.8.2 Regla de construcción 
Inputs: 
 slot_total_rep_equiv (solo 1 slot) 
 mode (CON/EXC/ISO) 
 intensity_value (para defaults de sets/rest) 
Determinismo: 
1. sets canónicos por intensidad (ejemplo): 
 LOW: 3–4 
 MID: 4–5 
 HIGH: 5–6 
 ULTRA: 6–8 (pero reps/hold muy bajos) 
(esto debe venir de tabla si querés 0 interpretación; si no, se fija como RulesVersion.) 
2. reps_per_set = distribute(slot_total_rep_equiv, sets) 
3. rest_sec canónico por intensidad: 
 LOW: 60–90 
 MID: 90 
 HIGH: 120 
 ULTRA: 150–180 
ISO: 
 seconds_per_set = reps_per_set * rep_equiv_sec 
25.9 Tempo Sets (Technical) 
25.9.1 Parámetros base 
 sets 
 reps_per_set 
 tempo (ej “31X1”, “50X0”) 
 rest_sec 
25.9.2 Regla de construcción 
 igual que Singlet en sets/reps/rest 
 tempo se selecciona por: 
 si slot es EXC → tempo con fase excéntrica larga 
 si CON → tempo controlado 
Determinismo: 
tempo = TempoTable[slot.mode][intensity_value] 
Sin TempoTable, no es determinista. 
25.10 Tabata (Fixed Interval 20/10 × 8) 
25.10.1 Parámetros base 
 work_sec (típicamente 20) 
 rest_sec (típicamente 10) 
 rounds (típicamente 8) 
 slots_supported (1–2) 
25.10.2 Regla de construcción 
Tabata tiene estructura casi fija. El motor debe: 
 validar que el budget sea compatible 
Dado: 
total_work_time = rounds * work_sec 
Conversión budget: 
 si slot CON: reps por intervalo 
 si slot ISO: segundos dentro del work_sec 
Regla: 
 si ISO seconds per interval > work_sec → formato inválido 
No se cambia tabata salvo que tu BD permita variantes (ej 30/15). 
25.11 Ladder (Progressive Steps) 
25.11.1 Parámetros base 
 start_step 
 step_increment 
 max_step o steps_count 
 rest_rule (between steps o none) 
 direction (up / up-down) 
25.11.2 Regla de construcción para cumplir budget 
Se define una secuencia de steps cuyos reps totales (rep_equiv) igualan budget. 
Ejemplo Ladder ascendente: 
sequence = [1,2,3,4] 
sum = 10 rep_equiv 
Algoritmo determinista: 
1. elegir plantilla por intensidad: 
 LOW: ladder más larga 
 HIGH: ladder corta (1-2-3) 
2. construir sequence mínima desde start=1 increment=1 hasta que: 
sum(sequence) >= budget_total 
3. si se pasa: 
 recortar último step para igualar budget (si permitido) 
 si no permitido → elegir otra plantilla 
ISO ladders: 
 ladder en segundos (3s,6s,9s…) usando rep_equiv_sec

1. parámetros respetan schema (min/max/allowed) 
2. delivered_work == budget_total (± tolerance) 
3. ISO no excede ventanas (ej 20s en tabata) 
4. rounds/sets no exceden caps del bloque/nivel/intensidad (si existen) 
25.14 Lógica del punto 25 (resumen) 
 Un formato se instancia mediante un ParamSchema 
 Se eligen parámetros en orden determinista (valores canónicos primero) 
 Se empaqueta el budget en esos parámetros (distribución + reconciliación) 
 Se convierten rep_equiv a reps/segundos según contracción 
 Se valida contra schema + budget + restricciones

26.1 Unidades canónicas (moneda única) 
26.1.1 rep_equiv 
El presupuesto del bloque se expresa en rep_equiv_total. 
Conversión por contracción (tu regla): 
 CON: 1 rep = 1 rep_equiv 
 ISO: 2 s = 1 rep_equiv 
 EXC: 3 s = 1 rep_equiv 
Formal: 
rep_equiv = CON_reps 
+ ISO_seconds / 2 
+ EXC_seconds / 3 
26.1.2 work_time_sec (tiempo efectivo del formato) 
Definición: tiempo total “de ventana” del bloque (no solo TUT). 
 EMOM: rounds × interval_sec 
 AMRAP: duration_sec 
 Tabata: rounds × (work+rest) 
 Sets: sum(estimated_work + rest) (si no hay estimation, se valida solo por budget, no 
densidad fuerte)

1. intensity_value ∈ {55..95} 
2. reps_budget_total (desde SPOM-Intensidad)

4. Delivered work empaquetado por slot: 
 CON_reps

26.4 Validaciones HARD (fallan el 
bloque) 
26.4.1 Budget exacto (hard) 
Definir tolerancia: 
 tolerance = 0 si querés exactitud 
 recomendado: tolerance = 1 rep_equiv por redondeos de segundos/reps 
Check: 
delivered_rep_equiv_total = CON_reps_total + ISO_sec_total/2 + 
EXC_sec_total/3 
if abs(delivered_rep_equiv_total - reps_budget_total) > tolerance: 
FAIL(BUDGET_MISMATCH) 
26.4.2 No exceder budget (hard, si aplica) 
Si tu política es “nunca pasarse”: 
if delivered_rep_equiv_total > reps_budget_total + tolerance: 
FAIL(BUDGET_OVER) 
26.4.3 Cumplimiento de slots (hard) 
Por cada slot: 
 Si slot es ISO, su payload debe ser ISO (no vale convertirlo silenciosamente a CON) 
forall slot: 
delivered_in_slot.mode == slot.mode 
Si hubo degradación (P21) debe estar trazada, pero acá ya trabajamos con “slots efectivos”. 
26.5 Densidad: definición y chequeos 
26.5.1 Densidad canónica 
density = delivered_rep_equiv_total / (work_time_sec / 60) 
# rep_equiv por minuto de bloque 
26.5.2 Rango esperado de densidad por intensidad 
(tabla necesaria) 
Como ya fijaste duraciones para AMRAP y EMOM, podemos derivar densidad esperada 
usando budget. 
Pero igual conviene validar contra un rango para detectar parametrizaciones raras (ej: 
EMOM 6 min en 80%). 
Definimos tolerancia relativa: 
density_expected = reps_budget_total / work_time_min 
density_ok if density within [expected*(1-δ), expected*(1+δ)] 
Recomendación determinista: 
 δ = 0.15 (±15%) 
Para EMOM 
work_time_min viene de tabla EMOM_duration_min. 
Para AMRAP 
work_time_min = 12 o 15 según regla. 
Check: 
expected = reps_budget_total / work_time_min 
if abs(density - expected) > expected*0.15: 
FAIL(DENSITY_OUT_OF_RANGE) 
Esto no agrega “opinión”: es solo consistencia matemática con la duración prescrita. 
26.6 Validación específica por formato 
(para evitar trucos) 
26.6.1 EMOM: payload por ronda razonable 
El motor debe impedir rondas imposibles. 
Definí caps simples: 
 max_rep_equiv_per_round por intensidad (dato o regla) 
Recomendación determinista minimal: 
 95/90: max 3 
 85/80: max 6 
 ≤75: max 8 
Check: 
rep_equiv_per_round = delivered_rep_equiv_total / rounds 
if rep_equiv_per_round > cap(intensity_value): 
FAIL(ROUND_PAYLOAD_TOO_HIGH) 
26.6.2 AMRAP: evitar “sub-prescripción” 
AMRAP puede ser demasiado liviano si el budget es alto para 12 min. 
Check equivalente: 
expected = reps_budget_total / work_time_min 
if expected > cap_density(intensity_value): 
  FAIL(AMRAP_INFEASIBLE_FOR_INTENSITY) 
 
Caps de densidad por intensidad (si no querés tabla): 
 95/90: ≤ 3.5 rep_equiv/min 
 
 85/80: ≤ 6 rep_equiv/min 
 
 ≤75: ≤ 8 rep_equiv/min 
 
(Esto es “cap operativa” para que no rompa el método.)

Punto 28 — G. Selección de ejercicios (Base de Datos) 
Filtros obligatorios (ruta + patrón + nivel + contracción + dificultad) 
28.1 Rol lógico del sistema de filtros 
El sistema de filtros es el núcleo determinista de la selección de ejercicios. 
Su función es: 
Reducir el universo completo de ejercicios a un conjunto candidato 
válido, tal que cualquier ejercicio seleccionado cumpla todas las 
restricciones estructurales del bloque. 
Este sistema: 
 no optimiza 
 no pondera 
 no decide variedad 
Solo elimina lo inválido. 
Si luego no hay suficientes ejercicios → se activa fallback controlado (definido en puntos 
posteriores). 
28.2 Orden obligatorio de aplicación de filtros 
El orden no es intercambiable. 
Cada filtro reduce el espacio de búsqueda y habilita el siguiente. 
Orden canónico: 
1. Filtro por ruta 
2. Filtro por patrón / categorías (scope SPOM) 
3. Filtro por nivel (grupo + subnivel) 
4. Filtro por dificultad (difficulty_bucket) 
5. Filtro por contracción (CON / EXC / ISO) 
Este orden garantiza: 
 joins simples 
 comportamiento predecible 
 trazabilidad del porqué un ejercicio entra o sale 
28.3 Filtro 1 — Ruta (Route Filter) 
Input 
 route (ej: FL, PL, HSPU…) 
Regla 
exercise.route_code == block.route 
Propósito 
 Asegurar coherencia mecánica del bloque 
 Evitar mezclas entre rutas incompatibles 
Notas 
 No hay fallback en este nivel 
 Si no hay ejercicios para una ruta → error de datos, no de planificación 
28.4 Filtro 2 — Patrón / Categorías (Scope SPOM) 
Inputs 
 spom_pct 
 spom_active_pattern 
 jerarquía de categorías 
Regla conceptual 
 El SPOM define qué tan específico o general debe ser el patrón 
 Ese scope se traduce en niveles de la jerarquía de categorías 
Ejemplo 
 pct bajo → categorías amplias (Push General / Pull General) 
 pct medio → subcategorías (Horizontal / Vertical, BA / SA) 
 pct alto → categoría específica (Planche / Front Lever) 
Regla técnica 
exercise.category ∈ allowed_categories(scope) 
Notas 
 Este filtro expande o contrae el universo según intensidad 
 No valida dificultad ni nivel todavía 
28.5 Filtro 3 — Nivel (grupo + subnivel) 
Inputs 
 level_group (ej: Alfa/Delta, Sigma, Omega) 
 level_num_target (1–2–3 según grupo) 
Regla 
exercise.level_code == block.level_group 
AND 
exercise.level_num <= block.level_num_target 
Interpretación 
 Siempre se permite: 
 mismo nivel 
 subniveles más fáciles 
 Nunca se permite: 
 subniveles más difíciles que el target 
Ejemplo 
 target = Alfa 2 → permite Alfa 1 y Alfa 2 
 target = Sigma 3 → permite Sigma 1, 2 y 3 
Notas 
 El nivel nunca se cruza entre grupos (Alfa ≠ Sigma) 
28.6 Filtro 4 — Dificultad (difficulty_bucket) 
Inputs 
 difficulty_bucket derivado de SPOM-Intensidad 
Convención 
 1 = más fácil 
 3 = más difícil 
Regla 
exercise.difficulty_relative <= block.difficulty_bucket 
Propósito 
 Alinear dificultad real del ejercicio con presupuesto del bloque 
 Evitar “ejercicios técnicamente válidos pero demasiado exigentes” 
Notas 
 Este filtro actúa después del nivel 
 Nivel y dificultad son ejes distintos: 
 nivel = quién puede hacerlo 
 dificultad = cuánto cuesta dentro del bloque 
28.7 Filtro 5 — Contracción (CON / EXC / ISO) 
Inputs 
 contraction_mix del bloque (ej: 2C / 1E / 1I) 
Regla 
exercise.contraction_code ∈ allowed_contractions 
Importante 
 En esta etapa NO se asigna todavía cuántos ejercicios de cada tipo 
 Solo se valida que el ejercicio sea compatible con la contracción requerida 
Asignación final se hace en un paso posterior (distribución dentro del bloque). 
28.8 Resultado del sistema de filtros 
El output del Punto 28 es: 
CandidateExercisePool = Exercise[] 
Tal que cada ejercicio del pool cumple simultáneamente: 
 ruta correcta 
 patrón/categoría válida para el scope SPOM 
 nivel permitido 
 dificultad permitida 
 contracción compatible 
Este pool es: 
 determinista 
 ordenable 
 auditable 
Todavía: 
 no hay selección final 
 no hay variedad 
 no hay orden interno 
28.9 Condiciones de error / fallback 
 Pool vacío → error de configuración o de datos 
 Pool < exercise_count_target → habilita fallback (definido en Punto 29+) 
 Pool válido → continúa pipeline 
28.10 Invariante del sistema 
Si un ejercicio aparece en el plan final, es porque pasó TODOS los filtros 
del Punto 28. 
No existen excepciones silenciosas. 
Toda excepción debe ser explícita y trazable. 
Punto 29 — G. Selección de ejercicios (Base de Datos) 
Filtros opcionales (equipamiento, regresión/progresión, fatiga, etc.) 
29.1 Rol lógico de los filtros opcionales 
Los filtros opcionales existen para mejorar la calidad operativa del plan sin romper las 
invariantes duras del Punto 28. 
 Punto 28 = validez estructural (hard constraints) 
 Punto 29 = calidad/contexto (soft constraints) 
Estos filtros: 
 pueden activarse/desactivarse por configuración 
 pueden degradarse por fallback 
 nunca deben contradecir hard constraints 
Formalmente: 
C_hard = hard_filters(DB, BlockContext) 
C_soft = soft_filters(C_hard, BlockContext, RuntimeContext) 
29.2 Modelo de ejecución: “scoring o filtrado” 
Hay 2 modos correctos. El motor debe elegir uno y mantenerlo consistente: 
Modo A — Soft as Filter (recomendado si hay alta densidad de datos) 
Aplicar filtros opcionales como exclusión: 
C = {e ∈ C_hard | passes_all_soft_filters(e)} 
Modo B — Soft as Rank (recomendado si faltan campos en BD) 
No excluye, solo ordena: 
rank(e) = Σ weights_i * feature_i(e) 
C = sort(C_hard, by=rank desc) 
Determinismo: incluso en Modo B, el ranking necesita tie-breaker canónico (ej 
exercise_id). 
29.3 Filtro opcional: Equipamiento (Equipment) 
Input (runtime) 
 available_equipment (set) 
 ej: {bar, rings, parallettes, box, band, weight_vest} 
 branch_profile (si la sucursal cambia el equipamiento) 
Campos requeridos en Exercise DB (si existe) 
 equipment_required (set) 
 equipment_optional (set) 
Regla (modo filter) 
equipment_required ⊆ available_equipment 
Fallback: 
 si no existe el campo en DB → no filtrar, solo rank 
 si pool queda corto → relajar a “allow missing optional” 
29.4 Filtro opcional: Regresión/Progresión (Progression Fit) 
Objetivo 
Elegir ejercicios coherentes con la progresión del grupo evitando saltos raros. 
Inputs 
 target_level_code 
 target_level_num 
 progression_direction ∈ {REGRESS, NEUTRAL, PROGRESS} 
 definido por: intensidad, semana del ciclo, o objetivo del día 
Datos necesarios 
 numeric_code (ya existe) 
 opcional: progression_family_id o relates_to 
Regla (modo rank) 
Preferir: 
 numeric_code cercano al “centro” del target: 
progression_score = -abs(exercise.numeric_code - 
target_numeric_code) 
Si existe relates_to: 
 penalizar escoger múltiples del mismo “family” en el mismo bloque (ver 29.7) 
Fallback: 
 si no hay target_numeric_code → usar level_num como proxy 
29.5 Filtro opcional: Fatiga (Fatigue / Load Management) 
Objetivo 
Evitar acumulación de estrés no deseada dentro del día o semana. 
Inputs (runtime) 
 fatigue_state por grupo: 
 upper_load_index, lower_load_index 
 historial reciente: 
 últimos 1–3 días por grupo 
 “anti-sesgo por asistencia” (si lo estás aplicando) 
Datos en Exercise DB (si existen o se agregan) 
 fatigue_tag ∈ {LOW, MID, HIGH} 
 o stress_axis (tendón, hombro, lumbar, etc.) 
 o joint_focus (hombro/codo/muñeca…) 
Regla (modo filter o rank) 
 Si upper_load_index alto: 
 penalizar fatigue_tag=HIGH en PUSH/PULL 
 Si lower_load_index alto: 
 penalizar fatigue_tag=HIGH en INFERIOR 
Fallback: 
 si no hay tags → usar proxies: 
 difficulty_relative alto = más fatiga 
 level_num alto = más costo 
29.6 Filtro opcional: Preferencias de entorno (Branch / Class 
Constraints) 
Casos típicos: 
 “clases numerosas”: evitar formatos/ejercicios con setup largo 
 “espacio limitado”: excluir ejercicios de desplazamiento 
 “piso resbaloso”: excluir saltos pliométricos 
Inputs: 
 class_size_estimate 
 space_profile 
 setup_cost_limit 
Datos requeridos (si existen) 
 setup_cost ∈ {LOW, MID, HIGH} 
 space_cost ∈ {LOW, MID, HIGH} 
Regla: 
setup_cost <= setup_cost_limit 
Fallback: 
 si no hay datos → rank por is_mobility o por familia 
29.7 Filtro opcional: Deduplicación por familia (relates_to) 
Objetivo 
No repetir el mismo ejercicio/variación “equivalente” en el mismo bloque. 
Datos 
 relates_to list (ya existe) 
 o family_id derivado 
Regla 
Durante selección (no solo filtrado): 
 si elegís e1, bloquear: 
 e2.exercise_name ∈ e1.relates_to 
 y/o e2.relates_to contiene e1 
Formal: 
blocked_set = closure(relates_to) 
29.8 Filtro opcional: Balance interno (empuje de variedad) 
Objetivo: 
 evitar 3 ejercicios con mismo “sabor” dentro del bloque 
Datos (si existen) 
 tags: BA/SA, horizontal/vertical, rings/bar, etc. 
Regla: 
 imponer caps: 
 max 2 con mismo tag 
 o rank: 
 
 penalizar repetición de tags

Punto 30 — G. Selección de ejercicios (Base de Datos) 
Algoritmo de selección (elegir N ejercicios: contracción + diversidad + 
consistencia) 
30.1 Objetivo (definición formal) 
Input (por BlockPlan) 
 CandidatePool = ejercicios que pasaron P28 (hard filters) 
 N = exercise_count_target (P15) 
 ContractionMix (P19–20) 
Ej: {CON:2, EXC:1, ISO:1} o derivado por intensidad 
 difficulty_bucket (P16) 
 scope_categories (P12 + P10) 
 soft_filter_mode (P29): FILTER o RANK 
 relates_to (dedup familia) 
 FormatInstance (si ya se eligió formato antes; si no, el formato se elige después) 
Output 
 SelectedExercises[] (tamaño N) 
 con asignación explícita: 
 slot_index 
 contraction_code 
 exercise_id 
 selection_trace 
Invariantes 
1. len(SelectedExercises) == N 
2. La mezcla de contracciones del set coincide con ContractionMix 
3. Todos los ejercicios ∈ CandidatePool (hard valid) 
4. No se violan reglas de deduplicación (si activas) 
5. Dificultad del set no supera el bucket (ya garantizado por hard filter; acá solo se 
controla escalonamiento interno) 
30.2 Decisión de diseño clave: selección por slots (obligatorio) 
No se selecciona “N ejercicios sueltos”. 
Se selecciona por slots predefinidos. 
Definición: 
Slots = expand(ContractionMix)  
# ej {CON:2, EXC:1, ISO:1} → [CON, CON, EXC, ISO] 
Luego el algoritmo asigna: 
slot[i] -> exercise 
Esto hace la cobertura de contracción trivialmente verificable. 
30.3 Construcción de buckets por contracción 
Particionar el pool: 
Pool_CON = {e ∈ CandidatePool | e.contraction_code == CON} 
Pool_EXC = {e ∈ CandidatePool | e.contraction_code == EXC} 
Pool_ISO = {e ∈ CandidatePool | e.contraction_code == ISO} 
Check hard de disponibilidad 
if |Pool_CON| < required(CON) → FAIL or FALLBACK 
if |Pool_EXC| < required(EXC) → FAIL or FALLBACK 
if |Pool_ISO| < required(ISO) → FAIL or FALLBACK 
Fallback permitido (en orden): 
1. relajar filtros opcionales (P29) 
2. expandir scope categorías (P10) 
3. bajar dificultad interna (preferir level_num menor) 
4. (último) degradar contracción EXC↔CON o ISO↔CON solo si tu sistema lo permite 
explícitamente (no silencioso) 
30.4 Definición de “diversidad” (criterios computables) 
El término “diversidad” debe convertirse en restricciones o scoring. 
Propuesta mínima computable (sin inventar campos nuevos): 
1. Diversidad por familia / equivalencia 
 basada en relates_to (dedup) 
 objetivo: evitar duplicados semánticos 
2. Diversidad por categoría secundaria 
 no repetir exactamente la misma category_secondary más de cap 
 cap depende de N: 
 N=2 → cap=2 (no importa) 
 N=3 → cap=2 
 N=4–5 → cap=2 
3. Diversidad por numeric_code (progresión) 
 evitar elegir ejercicios con numeric_code demasiado cercanos si querés variedad 
 o, si querés consistencia, lo contrario: mantener cercanía 
 esto lo controla un parámetro progression_mode 
Esto permite diversidad sin requerir tags adicionales. 
30.5 Definición de “consistencia” (criterios computables) 
Consistencia significa: el set “se siente del mismo bloque”, no una mezcla arbitraria. 
Criterios computables: 
1. Cohesión por scope 
 preferir ejercicios dentro del mismo allowed_category_set más específico 
posible 
2. Cohesión por nivel 
 preferir level_num cercano al target (no siempre irse al 1 si target=3) 
3. Cohesión por dificultad relativa 
 evitar saltos extremos dentro del set (ej: 1 y 3 juntos) salvo que el sistema lo pida 
30.6 Algoritmo base (determinista): “Slot-first + greedy con score” 
30.6.1 Orden determinista de slots 
Orden recomendado (reduce riesgo de quedar sin candidatos raros): 
1. EXC (más escaso) 
2. ISO (escaso) 
3. CON (más abundante) 
slot_order = sort_slots_by_scarcity([EXC, ISO, CON]) 
30.6.2 Score de candidato por slot 
Definir una función score(e, slot, current_selection). 
Componentes (todos deterministas): 
 S1: Nivel cercano al target 
S1 = -abs(e.level_num - target_level_num) 
 S2: Dificultad cercana al bucket (sin exceder) 
S2 = -abs(e.difficulty_relative - difficulty_bucket) 
 S3: Cohesión de categorías 
Preferir ejercicios cuya categoría ya esté representada si buscas consistencia, 
o penalizar si buscas diversidad. 
Esto depende de cohesion_mode. 
Ejemplo (consistencia): 
S3 = +count_same_category_secondary(e, selected) 
Ejemplo (diversidad): 
S3 = -count_same_category_secondary(e, selected) 
 S4: Penalización por familia (relates_to) 
if conflicts_with_relates_to(e, selected): S4 = -INF (hard reject) 
else S4 = 0 
 S5: Progresión (numeric_code) 
Si progression_mode = CONSISTENT: 
S5 = -abs(e.numeric_code - target_numeric_code) 
Si progression_mode = DIVERSE: 
S5 = +abs(e.numeric_code - avg_numeric_code(selected)) 
Score total (pesos fijos; no ML): 
score = 10*S4 + 3*S1 + 2*S2 + 2*S3 + 1*S5 
Nota: S4 es hard. El resto suma. 
30.6.3 Selección greedy por slot 
Para cada slot en slot_order: 
1. Pool_slot según contracción 
2. filtrar candidatos que no violen hard dedup 
3. ordenar por (score desc, numeric_code asc, exercise_id asc) 
(tie-breakers) 
4. tomar el primero 
5. agregar a selected 
6. actualizar estructuras (familias, categorías, etc.) 
Complejidad: O(N * |Pool|) (suficiente) 
30.7 Manejo de casos difíciles (cuando greedy puede fallar) 
Puede pasar que elegir “el mejor” temprano bloquee el último slot. 
Solución determinista: backtracking acotado. 
30.7.1 Backtracking depth=2 (recomendado) 
 Si al completar slots restantes el pool queda vacío: 
 retroceder 1 selección y tomar el segundo mejor 
 si falla, retroceder 2 
Esto mantiene determinismo si: 
 el orden de alternativas está fijado 
 el depth máximo está fijado

El motor debe emitir:

    "exercise_count_target": 4, 
    "contraction_mix": {"CON":2,"EXC":1,"ISO":1}, 
    "slots": [ 
      
{"slot":1,"contraction":"EXC","chosen":"PL:sigma:2:EXC:neg_planche"}

30.9 Validaciones finales (post-condition) 
Después de seleccionar: 
1. cobertura de contracción exacta 
 
2. sin duplicados ni conflictos relates_to 
 
3. categorías dentro del scope (ya era hard) 
4. nivel y dificultad dentro del rango (ya era hard) 
5. si hay policy de “cap de repetición de categoría secundaria”, verificarla 
Si falla alguna → backtracking / fallback. 
30.10 Parámetros de control (config del motor) 
Para hacerlo configurable sin cambiar lógica: 
 cohesion_mode: CONSISTENT | DIVERSE 
 progression_mode: CONSISTENT | DIVERSE 
 category_secondary_cap: int 
 backtrack_depth: 0/1/2 
 soft_filter_mode: FILTER | RANK 
 fallback_policy_order: lista ordenada 
Punto 31 — G. Selección de ejercicios (Base de Datos) 
Evitar duplicados y colisiones (patrón repetido, tejido saturado, etc.) 
31.1 Objetivo (definición formal) 
Evitar que un BlockPlan (y opcionalmente un DayPlan/WeekPlan) contenga 
combinaciones de ejercicios que: 
1. sean redundantes (mismo “ejercicio disfrazado”) 
2. saturen el mismo tejido / articulación / eje de forma no deseada 
3. repitan el mismo patrón/categoría más allá de lo permitido 
4. generen incompatibilidades operativas (setup, espacio, etc.) 
Esto se implementa como una capa post-hard-filters que opera en dos niveles: 
 Nivel Bloque (obligatorio): colisiones dentro del mismo bloque 
 Nivel Día/Semana (opcional): colisiones acumuladas por proximidad temporal 
31.2 Conceptos y entidades 
31.2.1 Definiciones mínimas 
 Duplicate: dos ejercicios que pertenecen a la misma “familia” funcional 
(equivalentes). 
 Collision: dos ejercicios que no son equivalentes pero comparten un recurso 
limitado (tejido, articulación, eje, setup) y exceden un umbral. 
31.2.2 Representación canónica: CollisionProfile (por ejercicio) 
Para detectar colisiones necesitas atributos computables. Hay 2 opciones: 
Opción A (data-driven, recomendada): Exercise DB contiene tags. 
Opción B (proxy): derivar proxies desde categorías existentes (menos fino). 
CollisionProfile mínimo (ideal): 
{ 
} 
"family_id": "PL_LEAN_FAMILY", 
"pattern_key": "PUSH:STRAIGHT_ARM:HORIZONTAL", 
"tissue_tags": ["ANT_SHOULDER", "WRIST", "ELBOW_TENDON"], 
"joint_tags": ["SHOULDER", "WRIST"], 
"axis_tags": ["SCAP_PROTRACTION", "ANT_PELVIC_TILT"], 
"stress_level": "HIGH" 
Si hoy no está en DB, esto se puede guardar como tabla aparte 
ExerciseCollisionTags. 
31.3 Evitar duplicados (hard) — “misma familia / relates_to” 
31.3.1 Fuente de verdad 
 relates_to (lista) del ejercicio 
 o family_id si existe 
31.3.2 Regla hard (bloque) 
Una vez elegido e, ningún otro x puede ser: 
 x.exercise_name ∈ e.relates_to 
 o e.exercise_name ∈ x.relates_to 
 o x.family_id == e.family_id 
Formal: 
blocked = closure(relates_to(selected)) 
candidate ∉ blocked 
closure = si A relaciona a B y B relaciona a C, bloquear C también (opcional, configurable). 
31.3.3 Política de igualdad 
Definir una key estable: 
 preferible: exercise_id 
 alternativa: normalizar exercise_name (uppercase, sin puntos, sin espacios 
dobles) 
31.4 Evitar repetición de patrón/categoría (soft/hard por política) 
31.4.1 Clave de patrón 
Definir pattern_key para cada ejercicio: 
Mínimo viable: 
pattern_key = pattern_principal + ">" + category_principal + ">" + 
category_secondary 
31.4.2 Regla por bloque 
Definir pattern_repeat_cap según N: 
 N=2 → cap=2 (sin restricción) 
 N=3 → cap=2 
 N=4–5 → cap=2 (máximo dos con misma category_secondary) 
Hard vs Soft: 
 Hard: nunca exceder cap 
 Soft: penalizar, pero permitir si pool es corto 
Recomendación: 
 Hard en bloques grandes (N≥4) 
 Soft en bloques chicos o cuando pool es estrecho 
31.5 Colisiones por “tejido saturado” (tissue load) 
Esto requiere introducir un modelo de “tejido” o al menos “zona”. 
31.5.1 Modelo de carga acumulada 
Para cada ejercicio seleccionado, se añade carga a tags: 
tissue_load[tag] += tissue_weight(exercise, intensity, contraction) 
Donde tissue_weight(...) puede ser: 
 data-driven (tabla) 
 o proxy simple (por difficulty_relative) 
Proxy determinista mínimo: 
base = difficulty_relative   # 1..3 
mult = contraction_multiplier(CON=1.0, ISO=1.1, EXC=1.2) 
tissue_weight = base * mult 
31.5.2 Umbrales por bloque 
Definir tissue_cap por bloque: 
 o constante (ej 5.0 por tag) 
 o dependiente de intensidad (más alto en intensidades bajas, más bajo en altas) 
Ejemplo determinista: 
 95–90: cap=3 
 85–80: cap=4 
 75–55: cap=5 
31.5.3 Regla 
Si al agregar un ejercicio se supera el cap en algún tag → colisión. 
if tissue_load[tag] + weight(e,tag) > tissue_cap(intensity): 
REJECT(e) or PENALIZE(e) 
Política: 
 En intensidad alta: REJECT (hard) 
 En intensidad media/baja: PENALIZE (soft) 
31.6 Colisiones por articulación (joint saturation) 
Similar a tejido, pero por articulación (hombro, muñeca, codo, lumbar, rodilla). 
Modelo mínimo: 
 joint_tags (list) 
 joint_cap(intensity) (tabla simple) 
Regla: 
 evitar más de X ejercicios que carguen fuerte misma articulación 
Ej: 
 90–95: max 1 “WRIST_HIGH” 
 80–85: max 2 
 ≤75: max 3 
Esto es útil especialmente para: 
 Planche (muñeca/hombro) 
 Front Lever (codo/hombro) 
 Inferior (rodilla/cadera) 
31.7 Colisiones por eje técnico (axis / skill redundancy) 
Objetivo: 
 evitar saturar el mismo “eje técnico” dentro del bloque 
Ejemplo: 
 3 ejercicios de protracción escapular + tilt anterior = redundante 
Requiere axis_tags. 
Regla: 
 axis_cap[tag] = 2 por bloque (configurable) 
31.8 Colisiones por setup / logística (opcional) 
Si existe setup_cost: 
 evitar elegir 3 ejercicios que requieren anillas + barra + paralelas si el bloque es 
rápido 
Regla: 
 setup_cap = 1 HIGH por bloque (en intensidades altas) 
31.9 Integración con el algoritmo de selección (P30) 
El control de duplicados/colisiones se integra en 2 puntos: 
1. Durante scoring: penalizar ejercicios que aumentan colisiones 
2. Como hard reject: bloquear ejercicios que violan caps hard 
Pseudo: 
for slot in slots: 
for e in Pool_slot: 
if violates_hard_dedup(e): continue 
if violates_hard_collision_caps(e): continue 
score = base_score(e) - collision_penalty(e, current_state) 
choose best 
Donde current_state incluye: 
 selected_exercises 
 tissue_load 
 joint_load 
 pattern_counts 
 axis_counts

Punto 32 — H. Prescripción 
(reps/duración/descanso/carga) 
Asignación de reps/duración por ejercicio (suma = reps_budget o 
encaja con formato) 
32.1 Objetivo (definición formal) 
Convertir un set de ejercicios seleccionados SelectedExercises[] en un set de 
prescripciones ejecutables ExercisePrescription[] tal que: 
Invariantes obligatorias 
1. La dosis total del bloque cumple el presupuesto: 
 en unidad canónica: Σ rep_equiv == reps_budget_total ± 
tolerance 
2. La dosis por ejercicio respeta: 
 su contraction_code (CON/EXC/ISO) 
 el FormatInstance (si aplica) 
3. La salida es instanciable en UI: 
 se puede mostrar y ejecutar sin decisiones faltantes 
32.2 Inputs del módulo de prescripción 
Por BlockPlan: 
 SelectedExercises[] (P30) 
 Cada uno con: exercise_id, contraction_code, difficulty_relative, 
etc. 
 
 reps_budget_total (P14; ya en rep_equiv) 
 
 ContractionMix (P19–20) como slots efectivos 
 
 FormatInstance (P24–25) (ej: EMOM 8’, AMRAP 12’, Tempo Sets…) 
 
 rep_equiv_rules (ya fijado): 
 
 ISO: 2s = 1 rep_equiv 
 
 EXC: 3s = 1 rep_equiv 
 
 CON: 1 rep = 1 rep_equiv
