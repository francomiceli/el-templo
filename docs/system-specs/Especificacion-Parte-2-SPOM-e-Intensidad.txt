Punto 13 — Intensidad → presupuesto del bloque 
Tabla de intensidad como fuente de verdad (pct → reps_budget, 
#ejercicios, dificultad) 
13.1 Definición: qué es “presupuesto del bloque” 
El presupuesto del bloque es un paquete cuantitativo que define los límites del contenido 
del bloque. 
Contrato: 
Budget = intensity_table[pct] (+ ajustes por block_type y level_group) 
El presupuesto define: 
 reps_budget o duration_budget_sec (según tipo de trabajo) 
 exercise_count_target (min/max) 
 difficulty_bucket (1/2/3) 
 (opcional) density_target o work_rest_ratio 
13.2 Fuente de verdad: IntensityTable (tabla) 
Invariante principal: 
Ningún agente “estima” presupuesto. 
Todo sale de una tabla versionada. 
Estructura canónica: 
{ 
} 
"pct": 95, 
"reps_budget": 10, 
"exercise_count_min": 2, 
"exercise_count_max": 3, 
"difficulty_bucket": 1 
Clave primaria: 
(pct) 
Regla: pct debe existir en tabla; si no existe ⇒ FAIL. 
13.3 Proyección: pct → (volumen, amplitud, dificultad) 
La tabla implementa 3 ejes simultáneos: 
1. Volumen (reps o tiempo total “de calidad”) 
2. Amplitud (# de ejercicios distintos) 
3. Dificultad (bucket 1–3) 
Comportamiento esperado (monotónico) 
 pct ↑ ⇒ reps_budget ↓ (menos repeticiones, más calidad) 
 pct ↑ ⇒ exercise_count ↓ (menos variedad, más específico) 
 pct ↑ ⇒ difficulty_bucket ↓ (más difícil, más técnico, menos “cómodo”) 
Nota: “difficulty_bucket” en tu sistema no es “más número = más difícil” 
necesariamente; lo tratamos como etiqueta ordinal definida por tabla. Si en tu 
tabla 1=más exigente, se mantiene. 
13.4 Budget base vs Budget efectivo (por tipo de bloque) 
El presupuesto que sale de la tabla es BASE. 
Luego se ajusta por block_type. 
Definimos: 
base_budget = intensity_table[pct] 
effective_budget = apply_block_caps(base_budget, block_type) 
13.4.1 Por qué existen caps por bloque 
Aunque una ruta sea 95% (muy específica), no todos los bloques pueden consumir el 
mismo presupuesto que Nucleus. 
 NUCLEUS = bloque principal → usa presupuesto completo 
 DEUTEROS_* = accesorio → usa presupuesto parcial 
 ATHLOS_EPIKOS = cierre → presupuesto variable (por objetivo metabólico) 
13.5 BlockCaps (reglas deterministas) 
Definimos multiplicadores por bloque: 
NUCLEUS        -> 1.00x del reps_budget 
DEUTEROS_1     
DEUTEROS_2     -> 0.70x -> 0.70x 
ATHLOS_EPIKOS  -> 0.80x o regla propia (depende de tu tabla de 
formatos) 
INITIUM        -> no usa reps_budget (warm-up / skill prep) 
Ejemplo: 
Si pct=95 y la tabla dice reps_budget=10: 
 Nucleus: 10 
 Deuteros: 7 
 Athlos: 8 
Redondeo: 
 regla fija: round_half_up o floor 
 debe ser determinista. 
13.6 #Ejercicios objetivo por bloque 
La tabla define un rango: 
"exercise_count_target": { "min": 2, "max": 3 } 
El bloque decide un número exacto dentro del rango: 
exercise_count = choose_count(min,max, block_type, level_group, 
scope) 
Reglas recomendadas: 
 pct alto ⇒ elegir min 
 pct bajo ⇒ elegir max 
 OMEGA puede tender a min (menos variación, más intención) 
Invariante: nunca salirse del rango del budget. 
13.7 Difficulty bucket (y cómo se usa) 
difficulty_bucket es un selector que gobierna: 
 qué ejercicios son elegibles (tag de dificultad del ejercicio) 
 qué tan cerca de “gesto final” se permite estar 
 (opcional) descansos mínimos 
Uso canónico: 
allowed_exercises = exercises where exercise.difficulty_bucket == 
budget.difficulty_bucket 
O si tu sistema lo maneja por “<=”: 
allowed_exercises = exercises where exercise.difficulty_bucket <= 
budget.difficulty_bucket 
Importante: esta comparación (== o <=) debe definirse como regla del sistema y no variar. 
13.8 Validaciones obligatorias del budget 
Para cada BlockPlan: 
1. Existe fila en IntensityTable[pct] 
2. effective_reps_budget = función determinista de: 
 tabla 
 block_type 
 política de redondeo 
3. exercise_count final dentro del rango 
4. difficulty_bucket válido (1..3) 
Output de validación: 
{ 
"budget_validation": { 
"status": "PASS", 
"base": 
{"pct":95,"reps_budget":10,"min":2,"max":3,"difficulty":1}, 
"caps": 
{"block_type":"DEUTEROS_1","multiplier":0.7,"rounding":"floor"}, 
"effective": {"reps_budget":7,"exercise_count":2,"difficulty":1} 
} 
} 
13.9 Lógica del punto 13 (resumen) 
 pct no se interpreta: se consulta en IntensityTable 
 La tabla devuelve el Budget Base 
 El block_type aplica caps → Budget Efectivo 
 El budget define: 
 reps/tiempo objetivo

Punto 14 — Regla de reps_budget 
Cómo se usa: ¿total del bloque vs por ejercicio? (a fondo, determinista) 
14.1 Definición formal 
reps_budget es un presupuesto total del bloque (no por ejercicio). 
Es decir: 
reps_budget = cantidad total de “unidades de esfuerzo” que el bloque puede 
consumir. 
Unidad de esfuerzo = repeticiones o equivalentes de tiempo (si el ejercicio es por 
duración). 
La decisión “por ejercicio” se calcula por reparto interno, no viene de la tabla. 
14.2 Por qué debe ser TOTAL del bloque 
(razón de sistema) 
Si fuera “por ejercicio”, el volumen se dispararía con el número de ejercicios, rompiendo: 
 consistencia semanal 
 relación intensidad–volumen 
 comparabilidad entre semanas 
Ejemplo: 
 pct=95 → reps_budget=10 
Si fueran 3 ejercicios “por ejercicio” ⇒ 30 reps (incompatible con alta especificidad). 
Conclusión: 
 reps_budget debe ser total del bloque. 
14.3 Representación canónica 
En BlockPlan.budget: 
"budget": { 
"budget_type": "REPS", 
"reps_budget_total": 10, 
"exercise_count_target": { "min": 2, "max": 3 } 
} 
14.4 Regla principal: reparto de 
reps_budget entre ejercicios 
El reparto se hace en dos fases: 
1. Asignación estructural (split por roles dentro del bloque) 
2. Asignación por tipo de contracción (ISO/EXC/CON) 
14.4.1 Fase 1 — Split por rol (si aplica) 
Si el bloque incluye: 
 1 ejercicio “main” (más específico) 
 1–2 ejercicios “support” (relacionales) 
Entonces: 
main_share = 0.60 
support_share = 0.40 split among remaining exercises 
Ejemplo (3 ejercicios, budget=10): 
 main = 6 
 support1 = 2 
 support2 = 2 
Ejemplo (2 ejercicios, budget=10): 
 main = 6 
 support = 4 
Regla determinista de “main”: 
 si scope ∈ {SPECIFIC, ULTRA} → el ejercicio con menor distancia al 
route_code es main 
 si scope ∈ {GENERAL, SEMI} → main se define por subpatrón del descriptor (si 
existe); si no, por ranking 
14.4.2 Fase 2 — Split por contracción (si aplica) 
Vos tenés una regla de “mezcla de contracciones” (CON/EXC/ISO). 
El presupuesto total debe cumplir esa mezcla. 
Definimos: 
"contraction_target": {"CON":0,"EXC":1,"ISO":2} 
Esto no define reps directas, define cuántos ejercicios (slots) por contracción. 
Regla: 
 si hay N ejercicios, asignar cada ejercicio a una contracción según target. 
 Luego, cada ejercicio recibe su porción de reps_budget según Fase 1. 
 Después se traduce a dosis (reps/duración) según dose_type. 
14.5 Reps_budget cuando hay ejercicios 
por duración (ISO/time) 
14.5.1 Normalización: “rep-equivalent” 
Para unir reps y duración, definís una conversión canónica. 
Ejemplo de regla simple (determinista): 
1 rep_equivalent = 3 segundos de TUT (ISO) 
Entonces: 
 si un ejercicio ISO tiene 6s → 2 rep_equivalents 
El sistema puede operar todo en rep_equivalents internamente. 
14.5.2 Contrato de Budget extendido 
"budget": { 
"budget_type": "REP_EQUIV", 
"rep_equiv_total": 10, 
"rep_equiv_unit_sec": 3 
} 
14.6 Regla: total del bloque vs por set 
reps_budget_total es total del bloque. 
Para convertirlo en prescripción ejecutable se aplica el formato: 
dose_per_exercise = allocate_budget(...) 
dose_per_set = dose_per_exercise / format.sets (si el formato es por 
sets) 
Ejemplo: 
 budget_total=10 
 2 ejercicios 
 split 6/4 
 formato: 3 sets 
Entonces: 
 ejercicio1 total = 6 → por set = 2 
 ejercicio2 total = 4 → por set = 1 o 2 según rounding 
14.7 Reglas de redondeo (críticas) 
El redondeo debe ser determinista y minimizar error acumulado. 
14.7.1 Regla de redondeo recomendada 
 usar floor en cada ejercicio 
 distribuir el “remanente” al ejercicio main primero 
Ejemplo: 
 total=10 
 split ideal 6/4 exacto → ok 
 split ideal 5.5 / 4.5 
 floor → 5 / 4 remanente=1 
 remanente a main → 6 / 4 
14.7.2 Invariante 
sum(allocated) == reps_budget_total 
14.8 Regla por nivel 
(ALFA/DELTA/SIGMA/OMEGA) 
El reps_budget_total se mantiene por bloque y grupo, pero puede ajustarse por nivel 
dentro del grupo si tu sistema lo define. 
Dos opciones válidas (elegir una y fijarla como regla): 
Opción A — Budget igual para niveles del grupo 
 ALFA y DELTA comparten el mismo budget_total 
 cambia solo la dificultad del ejercicio 
 más simple y estable 
Opción B — Budget escalado por nivel 
 ALFA recibe 0.85× 
 DELTA recibe 1.00× 
 SIGMA y OMEGA 1.00× 
Si no hay tabla explícita, recomiendo A para evitar inconsistencias. 
14.9 Regla: interacción con 
exercise_count 
exercise_count no multiplica el budget, solo lo reparte. 
Entonces: 
 exercise_count ↑ ⇒ dosis por ejercicio ↓ 
 exercise_count ↓ ⇒ dosis por ejercicio ↑ 
Esto es deseado porque: 
 % bajo tiende a más ejercicios (más variedad, menos dosis por gesto) 
 
 % alto tiende a menos ejercicios (menos variedad, más dosis específica) 
 
 
14.10 Validaciones obligatorias (per 
BlockPlan) 
El agente debe validar: 
1. sum(rep_equiv_per_exercise) == reps_budget_total 
 
2. #exercises == chosen_exercise_count 
 
3. Si el formato es por sets: 
 
 sum(per_set*sets) == total (o dentro de tolerancia por redondeo) 
 
4. Si hay mezclas por contracción: 
 
 #exercises_by_contraction cumple target 
 
Emitir: 
{ 
  "reps_budget_usage": { 
    "budget_total": 10, 
    "exercise_count": 3, 
    "allocation": [ 
      {"exercise_id":"A","share":0.6,"rep_equiv":6}, 
      {"exercise_id":"B","share":0.2,"rep_equiv":2}, 
      {"exercise_id":"C","share":0.2,"rep_equiv":2} 
    ], 
    "invariants": {"sum_ok": true} 
  } 
} 
 
 
14.11 Lógica del punto 14 (resumen) 
 reps_budget es TOTAL del bloque, no por ejercicio 
 Se reparte por reglas deterministas (main vs support) 
 Se adapta a ISO via rep_equivalent 
 El formato transforma “total” en “por set/round” 
 El redondeo debe conservar la suma total 
 Validaciones garantizan consistencia 
Punto 15 — Regla de exercise_count_target 
Rango (2–3, 3–5, etc.) + límites + selección determinista (a fondo) 
15.1 Definición formal 
exercise_count_target es un rango permitido de cantidad de ejercicios distintos 
dentro de un BlockPlan. 
Contrato: 
exercise_count_target = {min: a, max: b} 
Y el bloque debe elegir un exercise_count exacto: 
exercise_count ∈ [a, b] 
Invariante: el rango viene de la IntensityTable y se considera fuente de verdad. 
15.2 Por qué es un rango y no un 
número 
Razón de sistema: 
 el bloque puede necesitar: 
 más variedad (pct bajo + scope general) 
 menos variedad (pct alto + scope específico) 
 distintos formatos consumen mejor 2 ejercicios (sets pesados) o 4–5 (circuitos) 
Entonces: 
 la tabla define límites 
 el motor decide un punto dentro del rango según reglas 
15.3 Semántica: qué representa 
exercise_count 
exercise_count cuenta ejercicios únicos en la prescripción del bloque. 
Reglas de conteo 
 Variantes con diferente exercise_id cuentan como distintos. 
 Cambios de nivel (ALFA vs DELTA) no cambian el conteo si el bloque usa el mismo 
“slot” lógico: 
 Si ALFA hace una regresión del mismo slot y DELTA una progresión, sigue 
siendo 1 slot. 
 Si el bloque tiene 2 slots y en OMEGA se agrega un tercero, entonces el conteo es 
por nivel, y el output debe reflejarlo explícitamente (ver 15.9). 
15.4 Estructura de slots (modelo 
recomendado) 
Modelar el bloque como una lista de slots. 
"slots": [ 
{"slot_id":"S1","role":"MAIN"}, 
{"slot_id":"S2","role":"SUPPORT"}, 
{"slot_id":"S3","role":"SUPPORT"} 
] 
Entonces: 
exercise_count == #slots 
La selección real de ejercicios por nivel llena los slots. 
Esto permite mantener: 
 consistencia de estructura 
 variación por nivel sin cambiar arquitectura 
15.5 Fuente de verdad (IntensityTable) y 
límites 
La tabla de intensidad define: 
 exercise_count_min 
 exercise_count_max 
Ejemplo conceptual: 
 pct alto (85–95): 2–3 
 pct medio (70–80): 3–4 
 pct bajo (55–65): 4–6 
Regla dura: no se puede violar el rango. 
Si el motor no puede generar exercise_count dentro del rango por falta de ejercicios → 
FAIL (o fallback controlado, ver 15.10). 
15.6 Regla de selección del número 
exacto (determinista) 
Definimos una función: 
choose_exercise_count(min, max, pct, scope, block_type, level_group, 
format_family) -> int 
15.6.1 Heurística principal: % y scope 
if scope in {ULTRA, SPECIFIC}: prefer = min 
elif scope == SEMI: prefer = round((min+max)/2) 
else: prefer = max 
15.6.2 Ajuste por tipo de bloque 
 NUCLEUS: tender a menos ejercicios (calidad) 
 DEUTEROS_*: rango medio 
 ATHLOS_EPIKOS: puede tender a más (densidad/metabólico) pero sin romper la 
tabla 
Ejemplo: 
if block_type == NUCLEUS: prefer = max(min, prefer - 1) 
if block_type == ATHLOS_EPIKOS: prefer = min(max, prefer + 1) 
15.6.3 Ajuste por grupo de nivel 
 ALFA_DELTA: suele tolerar más variedad (aprendizaje amplio) 
 OMEGA: suele tolerar menos (intención técnica alta) 
if level_group == OMEGA: prefer = max(min, prefer - 1) 
if level_group == ALFA_DELTA: prefer = min(max, prefer + 1) 
15.6.4 Determinismo 
Si aún hay empate (ej. min=2 max=3 y prefer=2.5), resolver con: 
prefer = (hash(week_id + day_code + block_type) % 2 == 0) ? min : 
max 
No random sin seed. 
15.7 Restricciones duras adicionales 
(para evitar degeneraciones) 
Además del rango, aplicar constraints: 
R1 — Un MAIN mínimo 
Si exercise_count >= 2, debe existir: 
 1 slot MAIN 
 el resto SUPPORT/ACCESSORY 
R2 — No duplicar el mismo ejercicio en dos slots 
all selected exercise_id unique within the block for a given level 
(Excepto si un formato explícitamente reusa el mismo ejercicio con distinta contracción; en 
ese caso deben ser exercise_id distintos o variant_id distinto.) 
R3 — Diversidad de contracción (si contraction_target 
lo exige) 
Si el target dice ISO+EXC, no podés tener todos los slots ISO. 
R4 — Cohesión de patrón 
Ningún slot puede salirse del árbol habilitado por SPOM scope (Punto 12). 
15.8 Cómo se reparte el reps_budget 
según exercise_count (conexión con 
Punto 14) 
Una vez elegido exercise_count, se crean slots. 
Ejemplo: 
 budget_total=10 
 exercise_count=5 
Entonces la dosis promedio por slot es 2 rep_equiv, pero el split MAIN/SUPPORT manda. 
Regla recomendada para 4–6 ejercicios: 
 MAIN = 40–50% 
 SUPPORT = 50–60% repartido 
Para 2–3 ejercicios: 
 MAIN = 60% 
 SUPPORT = resto 
Esto mantiene que: 
 más ejercicios ⇒ menos carga por gesto 
 menos ejercicios ⇒ más carga por gesto 
15.9 Caso especial: variación de count 
por nivel (permitido pero explícito) 
Por defecto el bloque debe mantener el mismo exercise_count para todos los niveles del 
grupo. 
Solo se permite variación por nivel si existe una regla formal (ej. Omega agrega un slot 
técnico extra). 
Si ocurre, debe emitirse: 
"exercise_count_by_level": { 
"ALFA": 3, 
"DELTA": 3, 
"SIGMA": 3, 
"OMEGA": 4 
} 
Y se valida nivel por nivel. 
Si no se emite, se asume count uniforme. 
15.10 Fallos y fallback controlado 
(cuando el rango no es alcanzable) 
Caso A — Faltan ejercicios etiquetados 
Ejemplo: 
 scope SPECIFIC exige family=STRAIGHT_ARM 
 y en DB solo hay 1 ejercicio válido 
 pero exercise_count_min=2 
Resolución (orden): 
1. Intentar ampliar dentro del mismo scope usando “relacionales cercanos” (distancia 
+1) 
2. Si aún no alcanza: 
 fallback solo si rules_version permite: 
■ bajar 1 nivel de especificidad (SPECIFIC → SEMI) 
3. Si no está permitido ⇒ FAIL 
Debe registrarse como warning/error. 
Ejemplo trace: 
{ 
} 
"warning": "EXERCISE_COUNT_UNREACHABLE", 
"requested_range": {"min":2,"max":3}, 
"candidates_found": 1, 
"fallback": "SCOPE_DOWNGRADE_SPECIFIC_TO_SEMI" 
15.11 Validaciones obligatorias del punto 
15 
Por BlockPlan: 
1. exercise_count_target.min <= exercise_count <= max 
2. exercise_count == #slots 
3. #unique(exercise_id) cumple (por nivel) 
4. Contracción target cumplida por slots (si aplica) 
5. Todos los slots en árbol habilitado por SPOM 
15.12 Lógica del punto 15 (resumen) 
 exercise_count_target es un rango duro de la tabla de intensidad 
 El motor elige un número exacto con reglas deterministas: 
 scope/% + block_type + level_group 
 Se implementa como “slots” 
 Slots controlan diversidad, contracciones y cohesión 
 Si el rango es imposible por DB, hay fallback controlado o FAIL 
Punto 16 — Regla de difficulty_bucket (versión 
corregida) 
Cómo filtra ejercicios (a fondo, determinista) 
16.1 Propósito lógico 
difficulty_bucket es un filtro de elegibilidad que limita qué ejercicios pueden entrar 
en un bloque en función de la intensidad (%) de la ruta en esa semana. 
No define: 
 patrón/categoría (eso viene de SPOM → jerarquía) 
 scope (general/específico) 
 formatos 
Sí define: 
 el techo de dificultad permitido dentro del conjunto ya habilitado por SPOM. 
16.2 Convención global (invariante) 
Escala ordinal única: 
difficulty_bucket: 1 (más fácil) < 2 < 3 (más difícil) 
Aplica a: 
 ejercicios 
 bloques 
 grupos (ALFA/DELTA/SIGMA/OMEGA) 
 subsegmentos 1–2 (misma lógica: 1 fácil, 2 difícil) 
16.3 Fuente de verdad 
budget.difficulty_bucket proviene exclusivamente de la IntensityTable: 
budget = intensity_table[pct] 
bucket_max = budget.difficulty_bucket 
Invariante: el agente no lo calcula ni lo negocia. 
16.4 Semántica exacta del filtro (política 
cerrada) 
Política: “máximo permitido”. 
Regla: 
eligible_by_bucket(exercise) ⇔ exercise.difficulty_bucket <= 
budget.difficulty_bucket 
Ejemplos: 
 budget_bucket = 1 → solo ejercicios bucket 1 
 budget_bucket = 2 → ejercicios bucket 1 o 2 
 budget_bucket = 3 → ejercicios bucket 1, 2 o 3 
Esto hace que: 
 semanas/porcentajes “más exigentes” (si tu tabla les asigna bucket más alto) 
permitan ejercicios más difíciles; 
 semanas “más base” (bucket bajo) limiten la dificultad. 
Nota: si tu tabla decide lo contrario (pct alto → bucket bajo), el sistema sigue 
funcionando porque el bucket es fuente de verdad. La monotonicidad la 
controla la tabla, no el código. 
16.5 Requisitos de datos en Exercise DB 
(normalización) 
Cada ejercicio debe tener difficulty_bucket explícito. 
Modelo mínimo: 
{ 
"exercise_id": "EX-00123", 
"canonical_name": "Tuck Front Lever Hold", 
"route_code": "FL", 
"pattern_active": "SUP_PULL", 
"category_path": 
["SUP_PULL","PULL_GENERAL","PULL_HORIZONTAL","STRAIGHT_ARM"], 
"difficulty_bucket": 1, 
"level_min": "ALFA", 
"level_max": "SIGMA" 
} 
Reglas: 
 difficulty_bucket ∈ {1,2,3} obligatorio 
 ausencia de bucket ⇒ el ejercicio es inválido (no elegible) 
16.6 Posición del filtro en el pipeline 
(orden rígido) 
Para cada bloque: 
1. Scope/categoría (SPOM → jerarquía, Punto 12) 
2. Difficulty filter (este punto) 
3. Level filter (ALFA/DELTA/SIGMA/OMEGA) 
4. Contracción target (CON/EXC/ISO) 
5. Format compatibility (formatos posibles) 
6. Selección final + distribución de reps_budget 
Formal: 
C0 = candidates_by_scope(...) 
C1 = filter_bucket(C0, bucket_max) 
C2 = filter_level(C1, level_code) 
C3 = filter_contraction(C2, contraction_slot) 
C4 = filter_format_compatibility(C3, format) 
final = select_top_ranked(C4) 
16.7 Interacción con scope 
(general/específico) 
scope define “dónde buscar” en el árbol. 
bucket define “qué tan difícil puede ser lo que elegís” dentro de ese árbol. 
Esto implica: 
 Un scope ULTRA (ruta exacta) puede seguir devolviendo ejercicios fáciles (bucket 1) 
si están etiquetados como regresiones. 
 Un scope GENERAL puede incluir ejercicios bucket 3 (difíciles) si el budget lo 
permite. 
Invariante: bucket no amplía scope, solo recorta. 
16.8 Interacción con nivel (separación 
estricta) 
difficulty_bucket NO define si un alumno puede ejecutar un ejercicio. 
Eso lo define level_min/level_max (o el sistema de niveles por ejercicio). 
Regla: 
eligible_final = eligible_by_scope ∩ eligible_by_bucket ∩ 
eligible_by_level 
Ejemplo coherente: 
 bucket_max=3 (permite difícil) 
 pero level_code=ALFA 
 ⇒ igual se filtra por level_max, no entra un ejercicio olímpico si no hay regresión 
ALFA. 
16.9 Ranking dentro de lo elegible 
(cuando quedan muchos ejercicios) 
Bucket solo filtra. 
Después se ordena por cercanía al objetivo (ruta/scope) usando distancia jerárquica. 
Ranking recomendado (orden total): 
1. menor distance_to_route (más específico) 
2. bucket más alto dentro del permitido (si querés sesgo a “calidad”) 
3. estabilidad operativa (ejercicios “estables”, pocos requerimientos) 
4. variedad (evitar duplicados mecánicos) 
Formal: 
sort key = ( 
distance_to_target ASC, 
exercise.difficulty_bucket DESC,   // dentro del límite 
stability_score DESC, 
novelty_score DESC 
) 
Esto no cambia elegibilidad, solo selección. 
16.10 Manejo de vacío (cuando bucket 
deja 0 ejercicios) 
Caso: el conjunto luego de bucket es vacío. 
if C1 empty: 
apply_fallback_or_fail() 
Política de fallback (determinista, versionada) 
Definir RulesVersion.fallbacks: 
Fallback F1 — Relajar bucket (primero) 
Subir el bucket permitido solo si el problema es “demasiado restrictivo”: 
if bucket_max < 3: 
bucket_max = bucket_max + 1 
retry 
Esto mantiene scope intacto. 
Fallback F2 — Relajar scope (después) 
Si aún vacío, bajar especificidad: 
if scope in {ULTRA, SPECIFIC}: 
scope = SEMI 
retry 
Si no hay fallback permitido 
→ FAIL con error estructurado. 
Trace obligatorio: 
{ 
} 
"warning": "DIFFICULTY_FILTER_EMPTY", 
"bucket_requested": 1, 
"scope": "SPECIFIC", 
"fallbacks": ["BUCKET+1", "SCOPE_DOWNGRADE"], 
"result": "RECOVERED" 
16.11 Validaciones duras (BlockPlan) 
1. bucket del budget existe y ∈ {1,2,3} 
2. todo ejercicio seleccionado cumple: 
exercise.bucket <= budget.bucket 
 
3. el motor registra conteos: 
 
 count_after_scope 
 
 count_after_bucket 
 
 count_after_level 
 
Ejemplo: 
{ 
  "difficulty_trace": { 
    "bucket_max": 2, 
    "counts": { 
      "after_scope": 84, 
      "after_bucket": 53, 
      "after_level": 18 
    } 
  } 
} 
 
 
16.12 Tests de consistencia de la tabla 
(sanity checks) 
Como el bucket viene de la tabla, el sistema debe validar la tabla globalmente: 
 buckets ∈ {1,2,3} 
 
 no hay pct duplicados 
 
 (opcional) monotonicidad deseada: 
 
 si querés que pct alto permita bucket más difícil: bucket(pct) no decrece 
 
Esto se valida al cargar la tabla, no en runtime. 
16.13 Lógica del punto 16 (resumen) 
 difficulty_bucket es un máximo permitido de dificultad 
 escala fija: 1 fácil → 3 difícil 
 filtro duro: exercise.bucket <= budget.bucket 
 se aplica después de scope y antes de nivel/contracción/formato 
 requiere tagging explícito en la base de ejercicios 
 si deja vacío: fallback controlado o fail-fast 
 todo debe quedar trazado con conteos 
Punto 17 — Reconciliación entre tablas de reps 
Si hay más de una tabla: política única (a fondo, determinista) 
17.1 Problema que resuelve 
En el sistema existen (o pueden existir) múltiples fuentes que asignan “reps/volumen”: 
 Tabla A: pct → reps_budget / exercise_count / difficulty_bucket 
(IntensityTable) 
 Tabla B: ajustes por block_type (caps/multiplicadores) 
 Tabla C: reglas por format (sets, rounds, tiempo, work:rest) 
 Tabla D: reglas por contraction (ISO/TUT vs reps) 
 Tabla E: reglas por level_group o nivel (si las hay) 
Si estas tablas no tienen una política única, aparecen inconsistencias típicas: 
 la tabla de formato “impone” más volumen del que permite el budget 
 la tabla de contracción traduce ISO a segundos de forma distinta según bloque 
 el block cap reduce budget pero el formato no se adapta 
 dos tablas “definen reps” a la vez (doble conteo) 
Objetivo del punto 17: 
Definir una única cadena de autoridad y una unidad común, para que el sistema 
nunca “sume presupuestos” por accidente. 
17.2 Principio rector (invariante) 
Única fuente de verdad del volumen total 
El volumen total de un bloque se define por: 
BudgetTotal = IntensityTable[pct]  (base) 
BudgetEffective = apply_caps(BudgetTotal, block_type) 
Ninguna otra tabla puede aumentar BudgetEffective. 
Invariante duro: 
delivered_work <= BudgetEffective 
(donde delivered_work se mide en la unidad canónica definida abajo) 
17.3 Unidad canónica (para reconciliar 
reps vs tiempo) 
Para reconciliar tablas heterogéneas, todo se expresa internamente en rep_equivalents. 
Definición: 
REP_EQUIV = unidad interna de “trabajo” 
Conversión estándar: 
1 REP_EQUIV = 1 rep concéntrica estándar 
ISO: rep_equiv = ceil(seconds / REP_EQUIV_SEC) 
EXC: rep_equiv = reps  (o multiplicador si así lo definís) 
Se fija un parámetro global: 
"rep_equiv_sec": 3 
(ese valor puede ser 2/3/4 según tu criterio, pero debe ser único y versionado) 
17.4 Modelo de autoridad (orden de 
prioridad entre tablas) 
Definimos un orden absoluto de autoridad: 
Nivel 1 — SPOM 
 define pct y por lo tanto el budget base vía tabla 
Nivel 2 — IntensityTable (Budget Base) 
 define rep_equiv_total_base 
 define exercise_count_target 
 define difficulty_bucket 
Nivel 3 — BlockCaps (Budget Effective) 
 transforma budget base en budget efectivo por bloque 
Nivel 4 — ContractionProfile 
 transforma parte del budget en ISO seconds vs reps (pero sin cambiar total) 
Nivel 5 — FormatRules 
 empaqueta el trabajo en sets/rounds/intervalos 
 solo distribuye el budget, no lo aumenta 
Nivel 6 — Level rules 
 eligen variantes de ejercicio y pueden “hacer más fácil” la ejecución 
 pero no cambian el budget total salvo que exista una tabla explícita de escalado (y si 
existe, va antes de formats) 
Invariante: si dos tablas intentan definir el mismo campo “total_work”, gana la de mayor 
prioridad y la otra solo puede actuar como distribución. 
17.5 Política única: “Budget-first 
distribution” 
Esto es el corazón del punto: 
Primero se determina el budget total efectivo. 
Después, todas las demás tablas solo pueden distribuir ese budget. 
Formal: 
budget = BudgetEffective(week_id, route_code, block_type) 
slots = choose_exercise_slots(budget.exercise_count_target, other 
constraints) 
alloc = allocate_budget_to_slots(budget.rep_equiv_total, slots) 
format = choose_format(compatible_with(budget, contractions, 
level_group)) 
prescription = package_into_format(alloc, format) 
assert delivered_work(prescription) == budget.rep_equiv_total (± 
rounding) 
17.6 Caso: dos tablas de reps distintas 
(conflicto típico) 
Ejemplo de conflicto: 
 Tabla intensidad dice: pct=85 → reps_budget_total=18 
 Tabla “formatos” tiene un preset: “EMOM 10’ = 10 rounds” que implícitamente 
produciría 30 reps 
Resolución por política única 
 El formato no manda el volumen total 
 El formato debe parametrizarse para que el trabajo entregado sea 18 rep_equiv, no 
30. 
Esto significa: 
 se ajustan reps por round 
 o se ajusta número de rounds 
 o se ajusta duración 
Pero siempre cumpliendo budget. 
17.7 Cómo reconciliar “tablas por 
esquema” (reps-table vs time-table) 
Si existe: 
 Tabla de reps (para bloques de reps) 
 Tabla de tiempo (para bloques de intervalos) 
La política única es: 
1. Toda tabla debe expresar total_work en rep_equiv 
2. El tipo de salida decide si se presenta como: 
 reps 
 segundos 
 rounds × reps 
 intervalos 
Contrato recomendado 
{ 
} 
"pct": 85, 
"work_budget": { 
"unit": "REP_EQUIV", 
"total": 18, 
"rep_equiv_sec": 3 
}, 
"presentation_hints": { 
"preferred_mode": "REPS|TIME|MIXED" 
} 
La UI/planificación puede mostrarlo como tiempo si el formato lo requiere, pero 
internamente es el mismo total. 
17.8 Rounding y reconciliación (evitar 
drift) 
Como el budget se reparte en slots y sets, hay redondeo. 
Regla de reconciliación: 
1. Calcular ideal_alloc (floats) 
2. Aplicar floor a cada unidad 
3. Distribuir el remanente al: 
 slot MAIN primero 
 luego support por ranking 
Invariante: 
sum(alloc_int) == budget_total_int 
Si el formato produce drift (por ejemplo rounds fijos), se aplica “reconciliation pass”: 
while delivered_work != budget_total: 
adjust smallest movable parameter (reps_per_set or 
seconds_per_hold) 
Movible mínimo: 
 ajustar 1 rep en el set menos crítico 
 o 1 segundo en ISO (si 1 sec >= rep_equiv granularity) 
17.9 Política de escalado por 
bloque/nivel (si existiera) 
Si querés tener escalado por nivel (ALFA 0.85×, etc.), esa tabla debe ubicarse antes de 
formatos. 
Orden: 
budget_base = intensity_table[pct] 
budget_scaled = scale_by_level_group(budget_base, level_group) // 
opcional 
budget_effective = apply_block_caps(budget_scaled, block_type) 
Si no hay tabla explícita, no se hace. 
Regla dura: no hay escalado “implícito”. 
17.10 Validaciones globales (para 
detectar inconsistencias entre tablas) 
El agente debe ejecutar checks de consistencia: 
Check 1 — No double-definition 
 work_budget.total solo lo define IntensityTable (+ caps/scale) 
 FormatRules nunca define totals, solo distribución 
Check 2 — Delivered == Budget 
 Para cada BlockPlan: 
abs(delivered_work - budget_total) <= tolerance 
tolerancia típica: 
 0 para reps 
 0–1 rep_equiv para ISO (por conversión de segundos) 
Check 3 — Monotonicidad interna (si aplica) 
 si en la tabla a mayor pct baja el budget, eso debe sostenerse 
17.11 Output contractual para el agente 
(trace) 
Por cada bloque, emitir: 
{ 
  "work_reconciliation": { 
    "budget_source": "IntensityTable.vX", 
    "budget_total_rep_equiv": 18, 
    "caps": {"block_type":"DEUTEROS_1","multiplier":0.7}, 
    "format": {"code":"EMOM","rounds":9,"per_round_rep_equiv":2}, 
    "delivered_total_rep_equiv": 18, 
    "status": "PASS" 
  } 
} 
 
Si el formato tuvo que ajustarse: 
{ 
  "adjustments": [ 
    {"param":"rounds","from":10,"to":9}, 
    {"param":"reps_per_round","from":3,"to":2} 
  ] 
} 
 
 
17.12 Lógica del punto 17 (resumen) 
 El volumen total del bloque lo define una sola cadena: 
 IntensityTable[pct] → caps → (opcional) scale 
 
 Todo lo demás (contracción, formato, sets) solo distribuye ese total 
 
 Se usa una unidad interna única: rep_equiv 
 
 Se reconcilia con redondeo y un pass de ajuste 
 
 Se valida siempre que delivered_work == budget 
 
Punto 18 — Contracción (CON/EXC/ISO) derivada de 
intensidad 
Modelo de contracción como restricción (no descripción) — a fondo, 
formal 
18.1 Propósito lógico 
En este sistema, “contracción” no es un tag informativo del ejercicio. 
Es una restricción de planificación que se deriva de la intensidad (pct) y gobierna: 
 cuántos “slots” del bloque deben ser: 
 CON (concéntrico / reps) 
 EXC (excéntrico / reps controladas) 
 ISO (isométrico / tiempo bajo tensión) 
 cómo se traduce el work_budget (rep_equiv_total) a dosis ejecutable 
En términos de contrato: 
contraction_profile = contraction_table[pct] 
y se aplica como constraint duro sobre la selección. 
18.2 Definición formal: 
ContractionProfile 
Un ContractionProfile es un registro canónico: 
{ 
"pct": 95, 
"slots": { "CON": 0, "EXC": 1, "ISO": 2 }, 
"iso_rep_equiv_sec": 3, 
"exc_tempo_hint": "3-5s", 
"con_tempo_hint": "controlled" 
} 
Campos obligatorios: 
 pct 
 slots.CON / slots.EXC / slots.ISO (enteros ≥ 0) 
Campos opcionales: 
 iso_rep_equiv_sec (si no es global) 
 hints de tempo (no normativos) 
Invariante: la fuente de verdad es la tabla (no el agente). 
18.3 Semántica: contracción como 
constraint 
La contracción opera como “plantilla de composición” del bloque: 
 Si dice ISO=2, el bloque debe contener exactamente 2 slots ISO. 
 Si dice EXC=1, debe contener exactamente 1 slot EXC. 
 El resto de slots (si existen) se completan con CON, o el perfil debe sumarlos 
explícitamente. 
Esto implica dos posibles modelos (elegir uno y fijarlo): 
Modelo A — Perfil fija la distribución completa 
(recomendado) 
sum(slots) == exercise_count 
Modelo B — Perfil fija mínimos y el resto es libre 
sum(slots) <= exercise_count 
resto -> CON por defecto 
Para IA y consistencia, Modelo A es preferible: evita ambigüedad. 
18.4 Integración con 
exercise_count_target 
La contracción no decide cuántos ejercicios hay; eso lo decide exercise_count. 
Regla: 
1. Se elige exercise_count (Punto 15). 
2. Se obtiene ContractionProfile para pct. 
3. Se valida que el perfil sea compatible con exercise_count. 
Compatibilidad 
if sum(profile.slots) != exercise_count: 
resolve_mismatch() 
Resolución determinista (política única): 
 Si sum(profile.slots) < exercise_count: 
 completar slots faltantes con CON 
 Si sum(profile.slots) > exercise_count: 
 reducir en este orden: CON → EXC → ISO (ISO es más “prioritaria” a alta 
intensidad) 
Esto se registra como warning si ocurre. 
18.5 Contracción y scope: coherencia 
biomecánica 
Regla dura: 
 Los ejercicios ISO/EXC/CON deben estar dentro del mismo árbol habilitado por 
scope (Punto 12). 
La contracción no habilita ramas nuevas. 
18.6 Contracción y dificultad: coherencia 
de estímulo 
El filtro de difficulty (Punto 16) se aplica antes. 
Esto implica: 
 cada slot (ISO/EXC/CON) debe elegirse dentro del set ya filtrado por bucket_max. 
No existe: 
 “para ISO permito más difícil” 
 “para CON permito más fácil” 
Si querés eso, debe existir una tabla explícita de overrides por slot, pero no se asume. 
18.7 Tagging requerido en Exercise DB 
(critical) 
Para que la contracción funcione como constraint, cada ejercicio debe declarar: 
exercise.contraction_mode ∈ {CON, EXC, ISO, MIXED} 
Regla de matching: 
 slot ISO requiere exercise.contraction_mode ∈ {ISO, MIXED} 
 slot EXC requiere ∈ {EXC, MIXED} 
 slot CON requiere ∈ {CON, MIXED} 
Recomendación: evitar MIXED salvo que sea explícitamente intencionado.

ISO 
Entrada:

Salida: 
iso_seconds = rep_equiv_alloc * rep_equiv_sec 
CON 
Salida directa:

EXC 
Dos opciones (definir una): 
Opción EXC-1 (simple)

Opción EXC-2 (ponderada)

donde exc_multiplier es global (ej. 1.25) 
Si no tenés tabla explícita, usar EXC-1.

Punto 19 — Reglas pct → mezcla CON/EXC/ISO (por 
rangos) 
Modelo determinista por rangos + overrides (a fondo) 
19.1 Propósito lógico 
Definir una función determinista: 
contraction_profile(pct) -> {CON, EXC, ISO} 
donde el output no describe ejercicios, sino cuántos slots del bloque deben pertenecer a 
cada modo de contracción. 
La mezcla se usa para: 
 composición del bloque (slots) 
 conversión de budget a dosis (reps vs segundos) 
 compatibilidad de formatos 
19.2 Premisa de sistema (invariante) 
La mezcla C/E/I depende de intensidad porque intensidad en tu modelo implica: 
 a pct bajo: más volumen, más generalidad → predomina CON (reps) 
 a pct medio: control y calidad → aparece EXC e ISO 
 a pct alto: especificidad técnica → aumenta ISO y EXC, baja CON 
Esto NO se implementa “por intuición”; se implementa con reglas por rangos (o tabla) 
versionadas. 
19.3 Fuente de verdad: Tabla vs regla por 
rangos 
Dos enfoques válidos; en un agente de IA conviene fijar uno: 
Opción A — Tabla explícita (recomendado si ya existe) 
 pct exacto → slots exactos (la tabla manda) 
Opción B — Regla por rangos (lo que pediste) 
 rangos de pct → mezcla base 
 luego se reconcilia con exercise_count 
Acá desarrollo Opción B, pero con estructura compatible con migrar a tabla. 
19.4 Definición de rangos (con outputs 
base) 
Definimos rangos canónicos de pct: 
LOW      
MID      
HIGH     
ULTRA    
: pct ≤ 65 
: 70–80 
: 85–90 
: ≥ 95 
(estos cortes pueden ajustarse, pero deben quedar fijos como RulesVersion) 
19.5 Mezcla base por rango (en 
proporciones) 
La mezcla se define en proporciones, no en conteos absolutos, para luego mapear a slots. 
Proporciones base: 
LOW (≤65) — “capacidad / base” 
CON: 0.80 
EXC: 0.10 
ISO: 0.10 
MID (70–80) — “control / transferencia” 
CON: 0.60 
EXC: 0.20 
ISO: 0.20 
HIGH (85–90) — “técnica / fuerza específica” 
CON: 0.40 
EXC: 0.30 
ISO: 0.30 
ULTRA (≥95) — “skill / isométrico dominante” 
CON: 0.20 
EXC: 0.30 
ISO: 0.50 
Notas de implementación: 
 Estas proporciones no asumen nada del patrón (push/pull/legs). 
 Los ajustes por patrón serían otra capa (override), si existe. 
19.6 Conversión proporciones → slots 
(depende de exercise_count) 
Inputs: 
 exercise_count (del Punto 15) 
 proporciones base del rango 
Output: 
 slots enteros {CON, EXC, ISO} cuya suma coincide con exercise_count 
Regla determinista: 
raw = { 
CON: exercise_count * pCON, 
EXC: exercise_count * pEXC, 
ISO: exercise_count * pISO 
} 
slots = floor(raw) 
remainder = exercise_count - sum(slots) 
distribute remainder to largest fractional parts (ties: ISO > EXC > 
CON) 
Prioridad de ties (invariante) 
ISO > EXC > CON 
Justificación: cuando hay duda, se prioriza calidad/técnica. 
19.7 Ejemplos concretos 
Caso 1: pct=60 (LOW), exercise_count=5 
Proporciones: 0.8 / 0.1 / 0.1 
Raw: CON 4.0, EXC 0.5, ISO 0.5 
Floor: 4 / 0 / 0 (sum 4) remainder 1 
Fracciones: EXC 0.5, ISO 0.5 empate → ISO gana 
Resultado: 
{ "CON": 4, "EXC": 0, "ISO": 1 } 
Caso 2: pct=85 (HIGH), exercise_count=3 
Raw: CON 1.2, EXC 0.9, ISO 0.9 
Floor: 1 / 0 / 0 remainder 2 
Fracciones: EXC 0.9, ISO 0.9 empate → ISO luego EXC 
Resultado: 
{ "CON": 1, "EXC": 1, "ISO": 1 } 
Caso 3: pct=95 (ULTRA), exercise_count=2 
Raw: CON 0.4, EXC 0.6, ISO 1.0 
Floor: 0/0/1 remainder 1 
Fracciones: EXC 0.6, CON 0.4 
Resultado: 
{ "CON": 0, "EXC": 1, "ISO": 1 } 
19.8 Reglas de mínimos por rango (hard 
constraints) 
Las proporciones pueden generar casos degenerados (ej. 0 ISO en HIGH con pocos slots). 
Se definen mínimos por rango: 
 LOW: min ISO = 0, min EXC = 0 
 MID: min ISO = 1 si exercise_count ≥ 3 
 HIGH: min ISO = 1 si exercise_count ≥ 2 
 ULTRA: min ISO = 1 siempre; si exercise_count ≥ 3, min ISO = 2 
Implementación: 
apply_minimums(slots, pct_range, exercise_count): 
enforce mins by stealing from CON first, then EXC 
Prioridad de “robo”: 
CON → EXC → ISO (nunca robar ISO si es mínimo) 
19.9 Overrides por “tipo de bloque” (si 
existen) 
El rango da la mezcla base, pero puede haber política por bloque: 
 NUCLEUS tiende a ISO/EXC más presentes (calidad) 
 ATHLOS_EPIKOS tiende a CON (densidad) 
Override formal (multiplicadores de proporción): 
Ejemplo: 
 NUCLEUS: ISO×1.1, EXC×1.1, CON×0.8 
 ATHLOS: CON×1.2, ISO×0.8, EXC×0.8 
Luego renormalizar y reconvertir a slots. 
Regla dura: esto no cambia el budget total, solo mezcla. 
19.10 Overrides por patrón 
(push/pull/legs) — opcional 
Si tu sistema lo requiere, se definen ajustes por pattern_active: 
Ejemplo conceptual: 
 SUP_PUSH ULTRA: más ISO (planche/hspu holds) 
 INF: menos ISO, más EXC/CON (según tu metodología) 
Esto debe ser tabla explícita o regla versionada; no se asume. 
19.11 Manejo de imposibilidad (no hay 
ISO/EXC elegibles) 
Después de obtener slots, se valida con DB: 
if no eligible ISO exercises and slots.ISO > 0: 
fallback_slot_swap(ISO->EXC->CON) only if allowed 
else FAIL 
 
Swap order recomendado: 
ISO → EXC → CON 
 
Porque ISO es más específico; si no hay, bajás a excéntrico; si no hay, a concéntrico.

Punto 20 — Distribución de contracciones dentro del 
bloque 
Cómo se reparte CON/EXC/ISO cuando hay 2, 3, 4 (o más) ejercicios — a 
fondo, determinista 
20.1 Propósito lógico 
Dado: 
 exercise_count (número de slots del bloque) 
 contraction_slots = {CON, EXC, ISO} (Punto 19) 
 scope + bucket + level (filtros) 
 budget_total (rep_equiv_total) 
Se necesita producir: 
1. Un vector ordenado de slots con contracción asignada 
2. Una asignación de presupuesto a cada slot 
3. Un set de restricciones para la selección de ejercicios 
En términos de sistema: 
Primero se fija qué slots existen y qué contracción exige cada slot. 
Luego se selecciona un ejercicio para cada slot. 
El reparto de presupuesto se hace sobre slots, no sobre ejercicios directos. 
20.2 Representación canónica: Slots 
(estructura del bloque) 
Definimos BlockSlots[], lista ordenada: 
[

{"slot_id":"S2","role":"SUPPORT","contraction":"EXC"}, 
{"slot_id":"S3","role":"SUPPORT","contraction":"CON"} 
Campos: 
 slot_id (único en el bloque) 
 role ∈ {MAIN, SUPPORT} 
 contraction ∈ {CON, EXC, ISO} 
20.3 Regla general: orden y roles (MAIN 
primero) 
Siempre existe: 
 1 slot MAIN (si exercise_count ≥ 1) 
 el resto SUPPORT 
S1.role = MAIN 
S2..Sn.role = SUPPORT 
Esto es independiente de contracción. 
20.4 Regla: asignación de contracciones 
a slots (patrón determinista) 
Inputs: 
 conteos {CON,EXC,ISO} que suman N=exercise_count 
Se define un patrón de placement: 
Regla base 
1. El MAIN recibe la contracción “más específica” disponible: 
 prioridad: ISO > EXC > CON 
2. Los SUPPORT distribuyen el resto para cumplir conteos, ordenados por: 
 ISO primero, EXC después, CON último (misma prioridad) 
Formal: 
priority = [ISO, EXC, CON] 
assign MAIN: 
MAIN.contraction = first c in priority where slots[c] > 0 
slots[MAIN.contraction]-- 
assign SUPPORT: 
for each remaining slot i: 
pick first c in priority where slots[c] > 0 
assign and decrement 
Resultado: bloque ordenado “de más específico a más general”.

20.6 Reparto de presupuesto entre slots 
(con contracción aplicada) 
Una vez que los slots están definidos, se reparte budget_total (rep_equiv_total). 
20.6.1 Regla base de reparto por rol 
 MAIN recibe 60% 
 SUPPORT recibe 40% dividido entre soporte 
main = round_half_up(total * 0.60) 
support_total = total - main 
each_support = floor(support_total / (N-1)) 
remainder = support_total - each_support*(N-1) 
distribute remainder to earliest supports (S2, S3, ...) 
Invariante: suma exacta = total. 
20.6.2 Ajuste por contracción (opcional, solo si 
definido) 
Si querés sesgo de presupuesto hacia ISO a alta intensidad: 
 Si MAIN es ISO: mantener 60% 
 Si MAIN no es ISO pero hay ISO en SUPPORT: mover +1 rep_equiv desde CON 
hacia ISO (por prioridad) 
Esto debe ser tabla/política versionada. Si no existe, no se hace.

Punto 21 — Restricciones por movimiento 
Cuando una ruta / patrón / nivel NO soporta cierta contracción (C/E/I) — 
a fondo, formal 
21.1 Problema que resuelve 
Aunque el perfil de contracción (Puntos 18–20) diga que un bloque debe contener 
ISO/EXC/CON, no todas las rutas ni todos los niveles soportan todas las 
contracciones de forma válida, segura o coherente con el método. 
Ejemplos reales: 
 Front Lever ALFA → ISO sí, EXC parcial sí, CON puro no 
 Planche OMEGA → ISO y EXC dominantes, CON residual o inexistente 
 Inferior – Knee Dominant ALFA → CON sí, EXC sí, ISO limitado 
 HSPU SIGMA → CON y EXC sí, ISO sólo en variantes específicas 
Este punto define cómo el sistema bloquea, adapta o degrada contracciones cuando el 
movimiento no las soporta. 
21.2 Principio rector (invariante) 
La biomecánica del movimiento y el nivel del alumno tienen prioridad 
sobre la mezcla teórica de contracciones. 
Formalmente: 
allowed_contractions = capability(route, level, pattern) 
effective_contractions ⊆ allowed_contractions 
Nunca se fuerza una contracción inválida para una ruta/nivel. 
21.3 Fuente de verdad: 
MovementCapabilityMatrix 
Se define una matriz explícita (tabla o dataset versionado): 
{ 
} 
"route": "FL", 
"pattern_active": "SUP_PULL", 
"level_group": "ALFA", 
"allowed_contractions": ["ISO", "EXC"], 
"notes": "CON puro no existe en FL ALFA" 
Claves: 
 route (FL / PL / HSPU / INF…) 
 pattern_active 
 level_group (ALFA, DELTA, SIGMA, OMEGA, etc.) 
 allowed_contractions (subconjunto de {CON, EXC, ISO}) 
Esta tabla es obligatoria. 
Sin ella, el sistema no puede ser determinista. 
21.4 Jerarquía de aplicación (orden 
rígido) 
Las restricciones por movimiento se aplican después de definir: 
 mezcla C/E/I (Punto 19) 
 slots (Punto 20) 
y antes de: 
 selección de ejercicios 
 conversión de dosis 
Pipeline: 
slots = build_slots_from_pct() 
allowed = movement_capability(route, level_group) 
slots = reconcile_slots_with_capability(slots, allowed) 
select_exercises(slots) 
21.5 Regla central: intersección + 
reconciliación 
Para cada slot: 
if slot.contraction ∈ allowed_contractions: 
OK 
else: 
reconcile(slot) 
21.6 Política de reconciliación (orden 
fijo) 
Cuando una contracción no está permitida, se aplica una degradación controlada, nunca 
un reemplazo arbitrario. 
Orden de degradación permitido 
ISO → EXC → CON 
Nunca al revés. 
Ejemplo: 
 slot ISO no permitido → intentar EXC 
 EXC no permitido → intentar CON 
 CON no permitido → FAIL (no hay más degradación) 
21.7 Reconciliación a nivel de bloque (no 
sólo slot) 
Importante: no se reconcilia slot por slot de forma aislada, sino preservando el sentido 
del bloque. 
Proceso: 
1. Identificar slots inválidos 
2. Intentar degradarlos respetando: 
 conteo total de slots 
 prioridad MAIN vs SUPPORT 
3. Ajustar el contraction_profile_effective 
Ejemplo: 
Perfil teórico: 
{ "ISO":2, "EXC":1, "CON":0 } 
Movimiento: FL ALFA 
Allowed: ISO, EXC 
→ OK (no cambios) 
Otro ejemplo: 
Perfil teórico: 
{ "ISO":1, "EXC":1, "CON":1 } 
Movimiento: FL ALFA 
Allowed: ISO, EXC 
Slot CON inválido → no puede degradar (CON es el mínimo) 
Resultado: 
 convertir CON → EXC 
 perfil efectivo: 
{ "ISO":1, "EXC":2, "CON":0 } 
Registrar ajuste.
