## Executive Summary

### Most Important Invalidated Hypotheses

1. **Meta `message_id` dedup is "the leading suspect" / "likely missing or broken"** (Phase 93 CONTEXT.md line 23, line 91; STATE.md "investigation order" reasoning).
   - **Code reality:** dedup EXISTS and IS WIRED. `el-templo-bot/src/webhook/handler.ts:291-306` performs `INSERT INTO whatsapp_messages (... whatsapp_message_id, ...)` inside `try { } catch (err) { if (isDuplicateEntryError(err)) { return; } throw err; }`. Backed by a MySQL `UNIQUE` constraint on `whatsapp_messages.whatsapp_message_id` (`el-templo-api/src/db/schema/whatsapp.ts:84`). The same dedup is also wired for non-text messages at `handler.ts:274-289`. The Phase 93 CONTEXT hypothesis "Meta dedup likely the real fix surface" is wrong — it's not missing.
   - The remaining open question is whether dedup fires BEFORE the duplicate-response race window, not whether it exists. See "Unknowns" in Phase 93 section.

2. **BUG-04 "Ignacio Bordon" failure is fixed by adding a prompt rule OR by extraction-layer fix** (Phase 96 success criteria; REQUIREMENTS.md CTXT-02 options a/b/c).
   - **Code reality:** profile extraction is fire-and-forget AFTER the user-facing reply (`handler.ts:822-837` + `handler.ts:1369-1466`), so on turn N+1 the extracted `name` would arrive in `<profile>` AT BEST one turn later than the bot's next message. **There is no synchronous "you just said your name, here it is in this turn's context" path.** A prompt rule alone cannot fix BUG-04 if the underlying issue is that the user's CURRENT turn's name is not in `profileContext` until ONE TURN AFTER it was uttered. Per `post-phase-91-live-test-findings.md:43-44`, the team noted the model "chose to re-ask" while history was in context — but profile was not. This narrows option (a)/(b)/(c) — see Phase 96 details.

3. **Existing 3s debounce + 10s TTL already handles concurrency (REQUIREMENTS.md CONC-01 starting point: "investigate whether mechanism is already correct")**
   - **Strengthened, but with concerning detail:** `handler.ts:359-384` does enter via `isDebounceActive` check, set debounce TTL, sleep 3s, and process. BUT the sleep is `setTimeout(resolve, 3000)` — this just blocks the second incoming turn from a parallel handler if the FIRST handler hasn't yet returned. If two parallel webhook posts both pass `isDebounceActive === false` BEFORE either `setDebounce` write completes (Redis SETNX race window), BOTH handlers will then sleep 3s and fire AI calls. The set/check is NOT atomic (`isDebounceActive` then `setDebounce` are two separate operations — `session.ts:125-155`). See Phase 93 details.

4. **`DEBOUNCE_TTL_SECONDS=10` is a "safety-net TTL in case a handler crashes mid-turn"** (`handler.ts:96-97` comment + per debug session).
   - **Cross-phase reality:** the 10s TTL becomes a hard FAILURE mode when Phase 94 lands a 45s `OPENAI_TIMEOUT_MS`. If a single OpenAI call takes 11–45s, the debounce key auto-expires at second 10, and any inbound during seconds 10–45 will spawn a SECOND parallel handler. Phase 93's investigation cannot conclude "mechanism correct" without considering Phase 94's planned timeout boundary. This is the canonical cross-phase coupling and it's already in the debug session, but its scope is wider than just the TTL constant — it also implicates the 3s `setTimeout` sleep + Phase 97 RGUARD-03's `executeTool` timeout sweep.

5. **`request_human` tool already handles human takeover correctly per v5.3.2 invariant** (Phase 95 SC#3 invariant doc / REQUIREMENTS.md DEGR-02).
   - **Mostly confirmed, with a wrinkle:** `tools.ts:512-531` (`requestHuman` impl) just sets `conversation_status = 'human_takeover'` and returns a string — it does NOT send a user-facing message. The handler at `handler.ts:619-621` flags `humanTakeoverTriggered=true` so the post-AI segment loop only ships the FIRST segment of the AI reply (the handoff phrase), and the system-prompt rule at `system-prompt.ts:223` says "Invocá la tool y después SILENCIO". The user-facing message is whatever Mica wrote BEFORE invoking the tool, not the tool's own output. This means DEGR-01's "escalate via `request_human` after 2 failed attempts" requires the MODEL to actually emit a handoff phrase + the `request_human` tool call in the same turn — there's no handler-side fallback that synthesizes the handoff phrase if the model just calls the tool with no preceding text. **This narrows DEGR-01 implementation surface significantly.**

1. **DEBOUNCE_TTL_SECONDS (10s, Phase 93) ↔ OPENAI_TIMEOUT_MS (planned 45s, Phase 94) ↔ debounce delay (3s, Phase 93) ↔ executeTool timeout (planned, Phase 97 RGUARD-03).** Already canonical. Worst case: Phase 94 sets timeout to 45s and Phase 97 sets executeTool timeout to e.g. 30s per call × up to 5 iterations = 150s of bounded handler runtime, all of which exceeds the 10s debounce TTL. Phase 93 cannot ship without raising the TTL or proving the math is OK.

3. **Phase 96 CTXT-01/02 (profile re-asking fix) ↔ Phase 89 KGATE-05 (≥20% rendered / ≥35% knowledge block budget) ↔ RLOK-02 snapshot tripwire.** Any new prompt rule for "don't re-ask known data" adds bytes to the rendered E1A prompt. Also: if the CTXT fix involves injecting profile data MORE PROMINENTLY (Phase 96 SC#2 option b), `buildProfileContext` (`profile.ts:105-130`) output growth would similarly press against the cap.

4. **Phase 95 BOOK-01 (cross-venue class search) ↔ Phase 97 RGUARD-03 (executeTool timeout) ↔ Phase 94 LAT-02 (interim UX message).** A bounded `executeTool` call (Phase 97) could fail-fast on a slow localhost API, but Phase 94's interim UX is gated on `provider.chat()` timeouts, not on `executeTool` timeouts. So if `executeTool` times out mid-tool-loop, the handler currently has NO interim message to send the user — the model just receives a `Herramienta "x" no disponible.`-style string and re-invokes. Phase 95's DEGR-01 retry counter is the closest existing path, but Phase 95 is paired with the BOOK-01 fix, not with `executeTool`-level timeouts.

5. **Phase 97 RGUARD-01 (v5.3.3 regression suite) ↔ Phase 97 RGUARD-02 (zero regressions in v5.3.2 RLOK-01..04 + v5.3.1 KGATE/BPASS/METHOD/QREG) ↔ Phase 96 prompt edits ↔ Phase 95 system-prompt SC#3 wiring.** The RLOK-02 snapshot byte-equal lock (`v5-3-2-regression.test.ts:326-336`) breaks any time Phase 95 or Phase 96 changes the rendered E1A baseline. ## Phase 93 — Handler Concurrency

### What Exists

The handler entry path at `el-templo-bot/src/webhook/handler.ts` already has TWO independent dedup/concurrency mechanisms layered on top of each other:

1. **Meta `wamid` dedup** at `handler.ts:291-306` (text) and `handler.ts:274-289` (non-text). Inserts the inbound row with `whatsapp_message_id` as a UNIQUE column; on `ER_DUP_ENTRY` / errno 1062 (`handler.ts:61-64`), the handler returns early. Same `wamid` from Meta → second invocation is a no-op past this point.
2. **Phone-scoped Redis debounce** at `handler.ts:359-384`. Reads `wa:debounce:{phone}`; if set, returns early; else sets it with `EX 10`, sleeps 3s, then calls `processWithAiInner`. The `finally` block deletes the key.

The two layers serve different failure modes: Meta dedup prevents duplicate processing of the SAME `wamid`; phone debounce prevents duplicate processing of DIFFERENT messages from the same phone within ~3s.

### Key Mechanisms

- `handleInboundMessage` (`handler.ts:132-340`) — the orchestrator. Order: find/create conversation → determineClientState → dispatch interactive buttons → non-text fallback → wamid dedup → human-takeover check → `processWithAi`.
- `processWithAi` (`handler.ts:347-384`) — the OUTER function that owns the debounce. Adds inbound to session FIRST (so an in-flight peer can pick it up after its sleep), checks `isDebounceActive`, sets debounce TTL, sleeps `DEBOUNCE_DELAY_MS`, calls `processWithAiInner`, deletes debounce in `finally`.
- `processWithAiInner` (`handler.ts:391-889`) — the inner pipeline. Re-reads session (so coalescing works), resolves playbook, computes soft-rejection rule pre-AI, renders system prompt, calls provider.chat in a tool loop, post-processes reply, persists playbook state, fires-and-forgets profile extraction, splits reply, sends segments + saves outbound rows.
- `isDebounceActive` / `setDebounce` / `deleteDebounce` (`memory/session.ts:121-170`) — Redis-backed debounce helpers. `isDebounceActive` does `redis.get(key) !== null`; `setDebounce` does `redis.set(key, "1", "EX", ttlSeconds)`. NOT atomic together — two separate Redis round-trips.
- `isDuplicateEntryError` (`handler.ts:61-64`) — detects MySQL `ER_DUP_ENTRY` / errno 1062 to map UNIQUE violations to a no-op return.

### Hypotheses Invalidated

- **Phase 93 CONTEXT.md:23, :91** — "Meta message-ID dedup may not exist; leading suspect is Meta dedup missing." Code at `handler.ts:291-306` + schema at `whatsapp.ts:84` confirm dedup exists and is wired correctly.
- **REQUIREMENTS.md CONC-01 framing** — "existing 3s debounce + Redis dead-man switch (DEBOUNCE_DELAY_MS=3000, DEBOUNCE_TTL_SECONDS=10) is the starting point — investigate whether mechanism is already correct". The mechanism is missing one atomic property: `isDebounceActive` + `setDebounce` are non-atomic, so a SETNX-race window exists where two concurrent webhook invocations can both observe `false` and both proceed to set + sleep. Whether this race is the actual bug surface is the unknown — but the mechanism as described is NOT obviously correct.
- **`bot-3min-response-latency.md:53-54`** eliminated "BUG-02 is the 3s debounce sleep" by arguing the 10s TTL ceiling bounds the debounce contribution. This elimination is sound for BUG-02 but ALSO implicitly assumes the AI call completes before 10s — which Phase 94 will change (planned 45s timeout). The 10s TTL bound stops being a useful ceiling once Phase 94 lands.

### Hypotheses Strengthened

Concurrency is bounded at ~100 convs/day per `whatsapp-bot-architecture.txt:108-110`, and the existing two-layer mechanism (wamid dedup + per-phone Redis debounce) covers the documented failure modes IF the SETNX-race is closed. - **Webhook ack ordering** at `routes.ts:54` is correct per `bot-3min-response-latency.md:69`. Meta retries due to slow handler are not the cause of BUG-01 either.

### Cross-Phase Interactions

- **Phase 94 (LAT-01):** A 45s `OPENAI_TIMEOUT_MS` means a single hung `provider.chat` can keep the debounce key alive for ≤10s only (TTL expires automatically). The handler instance continues running past second 10 but the debounce key is gone — any inbound during seconds 10–45 spawns a parallel handler with a NEW debounce key. Fix space:
  - Raise `DEBOUNCE_TTL_SECONDS` to bound `OPENAI_TIMEOUT_MS + max_tool_iterations × executeTool_timeout + post-processing` (Phase 93 fix)
  - Renew the debounce key periodically inside the handler (Phase 93 fix)
  - Add an explicit handler-level lock (Phase 93 expansion)
- **Phase 97 (RGUARD-03):** `executeTool` localhost calls per-iteration also need bounded duration (`tools.ts:636`, `tools.ts:806` use `fetch` with no `signal: AbortSignal.timeout(...)`). Worst-case combined: 5 iterations × (OpenAI 45s + executeTool ∞) was the BUG-02 shape pre-fix; even post-Phase-94, executeTool is still unbounded until Phase 97 lands.
- **Phase 95 (BOOK-01, DEGR-01):** the `request_human` escalation path returns `humanTakeoverTriggered=true` only when the model emits the tool call (`handler.ts:619-621`). DEGR-01's "after 2 failed attempts" counter would need to live somewhere in the inner tool loop — handler.ts:589-642 — and must NOT bleed into the soft-rejection arc (different REGION, same handler).

### Unknowns

- Whether the BUG-01 failure was the SETNX-race or a Meta-side retry that somehow had a NEW `wamid` (genuinely different msg, not a retry) or a third cause. Code alone cannot tell. Per Phase 93 CONTEXT.md observability fallback, structured Pino logs at decision points + a fresh dev reproduction is the only diagnostic path.
- Whether Meta resends webhooks with the SAME `wamid` for "Hola" → "Hola?" → "Holaaaaa" or DIFFERENT `wamid`s. The user-visible duplicate could result from either:
  - Same wamid (Meta retry) — dedup at `handler.ts:291-306` should catch; if it's not catching, that's a wamid-dedup bug.
  - Different wamids (user pressed Send 3×) — debounce at `handler.ts:359-384` should catch via `isDebounceActive`; if it's not catching, that's the SETNX-race or a TTL-expiry interaction.
- The non-atomic `isDebounceActive` + `setDebounce` window (`session.ts:125-155`) is theoretically race-prone but practically depends on the gap between the two Redis round-trips. On a healthy local Redis the gap is sub-millisecond; on a stressed or remote Redis it can be tens of milliseconds. Whether this window is actually hit during BUG-01 is unknown without instrumentation.

## Phase 94 — OpenAI Latency + Graceful Failure

### What Exists

- `OpenAiProvider` (`el-templo-bot/src/ai/openai.ts:24-98`) constructs `new OpenAI()` at `openai.ts:29` with NO options object. The OpenAI SDK default request timeout is 600s (10 min) per `bot-3min-response-latency.md:66`.
- `provider.chat(...)` is called at TWO sites in `handler.ts`:
  - Initial call: `handler.ts:584` — outside the tool loop.
  - Tool-iteration follow-up: `handler.ts:641` — inside `while (response.toolCalls.length > 0 && iterations < MAX_TOOL_ITERATIONS)` (max 5 iters).
- The outer `try/catch` at `handler.ts:323-339` wraps `processWithAi` and only LOGS errors. No interim UX is sent to the user; the bot just goes silent.
- `OpenAiProvider.chat` itself has an internal `try/catch` (`openai.ts:88-97`) that re-throws as a generic `Error` after logging — `OpenAI.APIError` is unwrapped into a string message, losing the structured error shape.

### Key Mechanisms

- `provider.chat` is the only async-blocking call in the AI path (`handler.ts:584`, `handler.ts:641`). The tool loop (`handler.ts:589-642`) interleaves `provider.chat` with `executeTool` calls; both are awaited, no parallelism.
- `MAX_TOOL_ITERATIONS = 5` (`handler.ts:91`) bounds the worst-case number of `provider.chat` calls per inbound at 6 (1 initial + 5 iterations).
- Profile extraction (`handler.ts:1391`) is a SEPARATE `provider.chat` call but fire-and-forget (`handler.ts:823-837`) — exonerated as a latency cause per `bot-3min-response-latency.md:65`.

  1. `getProfile` reads Redis profile (`handler.ts:199`).
  2. System prompt rendered with `profileContext` from THAT read (`handler.ts:496-513`).
  3. AI generates reply.
  4. Reply sent.
  5. `extractAndUpdateProfile` fires AFTER reply send (`handler.ts:822-837`). New extraction is persisted, but only visible on turn N+1.

Parses `{name?, injuries?, classPreferences?, branchPreference?, notes?}`. Skips empty extractions. Merges with existing profile (union for arrays, override for strings). Logs `extractedFields` on success.

### Redis Usage Patterns

Per `redis.ts:11-15`:

- `wa:session:{phone}` — session messages, TTL 6h (`session.ts:16, 22`)

Client: `ioredis` (`redis.ts:17, 45-53`), `lazyConnect: true`, `maxRetriesPerRequest: 1`, exponential backoff retry. Graceful degradation throughout — every Redis call is wrapped in `if (!isRedisAvailable()) return null/no-op`.
