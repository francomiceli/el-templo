    - Check-in with classesRemaining = 0 throws BadRequestError "Agotaste tus clases del periodo"
    - Check-in on a fixed-mode subscription on a non-assigned day throws BadRequestError "Hoy no es un dia asignado"
    - Check-in within grace period (subscription expired but within grace days) succeeds silently
    - First check-in after grace period expires succeeds with warning status, increments graceCheckInsAfterExpiry to 1
    - Second check-in after grace period expires (graceCheckInsAfterExpiry >= 1) throws hard block BadRequestError "Suscripcion vencida — renovar"
    - Successful check-in decrements classesRemaining by 1 (UPDATE subscriptions SET classes_remaining = classes_remaining - 1)
    - Force check-in endpoint (POST /api/attendance/force) with { memberId, branchId, reason } bypasses all limits, creates attendance record with source="manual"
    - Force check-in still decrements classesRemaining (if applicable)
  </behavior>
  <action>
    Update AttendanceService constructor to accept SettingsService as additional dependency.

    Refactor checkIn method to add enforcement layers (after existing subscription check, overdue check, branch check, but before one-per-day check):

    1. **Fixed-day check**: If subscription has fixedDays (JSON parsed as number[]), get today's ISO day of week (1=Mon, 6=Sat). If today not in fixedDays, throw "Hoy no es un dia asignado de tu plan".

    2. **Grace period check** (replaces hard subscription expiry): Instead of requiring subscription to be strictly active, implement this logic:
       - Get subscription with endDate
       - If subscription is active and not expired: proceed normally
       - If subscription endDate < today:
         a. Calculate days since expiry
         b. Get gracePeriodDays from SettingsService
         c. If daysSinceExpiry <= gracePeriodDays: allow silently (transparent grace period)
         d. If daysSinceExpiry > gracePeriodDays AND subscription.graceCheckInsAfterExpiry === 0: allow but increment graceCheckInsAfterExpiry to 1 (first post-grace attendance). This is the warning check-in — admin/coach sees warning but member does not.
         e. If daysSinceExpiry > gracePeriodDays AND subscription.graceCheckInsAfterExpiry >= 1: hard block, throw "Suscripcion vencida — renovar. Consulta con tu coach."
       - Note: Grace period modifies the existing autoExpireSubscriptions behavior. During grace period, subscription should NOT be auto-expired. Adjust autoExpireSubscriptions to add gracePeriodDays to endDate comparison.

    3. **Weekly limit check**: Count attendance records for current Mon-Sun week. Compare to plan.classesPerWeek. If count >= classesPerWeek, throw "Alcanzaste tu limite semanal ({count}/{classesPerWeek})".

    4. **Monthly budget check**: If subscription.classesRemaining is not null and classesRemaining <= 0, throw "Agotaste tus clases del periodo".

    5. **After successful check-in**: If subscription.classesRemaining is not null, decrement: UPDATE subscriptions SET classes_remaining = classes_remaining - 1 WHERE id = subscriptionId AND classes_remaining > 0.

    Add forceCheckIn method:
    - Parameters: memberId, branchId, reason, adminId
    - Skips all checks (subscription, overdue, weekly, monthly, fixed day, grace period)
    - Creates attendance record with source="manual"
    - Still decrements classesRemaining if applicable (to keep budget accurate)
    - Logs the override with reason and adminId

    Update types.ts:
    - Add ForceCheckInInput: { memberId: number, branchId: number, reason: string }

    Update routes.ts:
    - Add POST /api/attendance/force endpoint

    Update schemas.ts:
    - Add forceCheckInSchema with body validation

    - Test monthly budget enforcement (setup: create subscription with classesRemaining=0, attempt check-in → expect 400)

    - Test fixed-day enforcement (setup: fixed plan with days [1,3,5], attempt check-in on day 2 → expect 400)
    - Test force check-in bypasses limits
    - Test grace period transparent access
