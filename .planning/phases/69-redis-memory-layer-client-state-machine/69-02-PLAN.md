**DB Migration** -- Update client_state enum values per CONTEXT.md decisions:

The current enum has: `lead, trial, active_member, lapsed, returning`. Per CONTEXT.md locked decisions, it should be: `lead, trial, active_member, inactive_member, expired_member`.

```sql
ALTER TABLE whatsapp_conversations MODIFY COLUMN client_state ENUM('lead', 'trial', 'active_member', 'inactive_member', 'expired_member') NOT NULL DEFAULT 'lead';
```

**state/machine.ts** -- Replace stub with state detection logic:

- Export `ClientState` type: `'lead' | 'trial' | 'active_member' | 'inactive_member' | 'expired_member'`
- Export `determineClientState(phone: string, db: DB): Promise<ClientState>` that:
  1. Query `users` table by phone number: `SELECT u.id, u.is_active, u.first_name FROM users u WHERE u.phone = {phone} LIMIT 1`
  2. If no user found -> return `'lead'`
  3. If user found, query subscriptions: `SELECT s.status, s.end_date FROM subscriptions s WHERE s.user_id = {userId} AND s.status IN ('active', 'paused') ORDER BY s.created_at DESC LIMIT 1`
  4. If no subscription -> check if subscription_plans.is_trial was used: `SELECT sp.is_trial FROM subscriptions s JOIN subscription_plans sp ON s.plan_id = sp.id WHERE s.user_id = {userId} ORDER BY s.created_at DESC LIMIT 1`. If is_trial = true and no active sub -> `'trial'`. If no subscriptions at all -> `'lead'`.
  5. If active subscription found:
     - If `status = 'active'` and end_date is in the future (or null) -> `'active_member'`
     - If end_date is in the past -> `'expired_member'`
  6. If no active subscription but has expired/cancelled ones -> `'expired_member'`
  7. For INACTIVE_MEMBER: this requires checking attendance. Since attendance detection adds complexity, and the CONTEXT says "no check-ins in 30+ days", query: `SELECT COUNT(*) FROM attendance WHERE user_id = {userId} AND created_at > DATE_SUB(NOW(), INTERVAL 30 DAY)`. If count = 0 and status = 'active' -> `'inactive_member'`.

- Export `updateConversationState(conversationId: number, state: ClientState, db: DB): Promise<void>` -- UPDATE whatsapp_conversations SET client_state = {state} WHERE id = {conversationId}.
- Use raw SQL via `sql` template literals (same pattern as handler.ts to avoid cross-package type conflicts).
- Use module-level Pino logger.

- `extractProfileUpdates(currentProfile: CustomerProfile | null, aiResponse: string, userMessage: string): string` -- Returns a concise instruction string that will be appended to the AI system prompt asking it to extract facts. This is NOT an AI call itself -- it generates the extraction prompt section. The actual extraction happens via a lightweight follow-up AI call in the handler.

After the main response, the handler makes a second AI call with a focused prompt: "Given this conversation exchange, extract any new profile facts" and the AI responds with structured JSON updates. This is cleaner than embedding extraction in the main conversation.

- Notes cap: when `notes` exceeds ~2000 characters (~500 tokens), truncate from the beginning (oldest notes dropped).

**webhook/handler.ts** -- Integrate profile and state machine:

1. At the start of `handleInboundMessage`, after finding/creating the conversation:
   - Call `determineClientState(phone, db)` to get the current state.
   - Call `updateConversationState(conversationId, state, db)` to persist it in MySQL.
   - Call `getProfile(phone)` to load the customer profile from Redis.

2. Pass `clientState` and `profile` to `processWithAi`.

3. In `processWithAi`, update the system prompt call:
   - Build `profileContext` string from profile data: "Nombre: {name}, Lesiones: {injuries}, Preferencias: {classPreferences}, Notas: {notes}" (only include fields that have values).
   - Call `getSystemPrompt({ clientState, profileContext })` instead of `getSystemPrompt()`.

4. After the AI responds successfully (after sending the reply), trigger a lightweight profile extraction:
   - Make a second AI call with a focused system message: "Sos un extractor de datos. Dado este intercambio, extraes datos nuevos del perfil del cliente en formato JSON. Solo responde con JSON valido o '{}' si no hay nada nuevo. Campos posibles: name (string), injuries (string[]), classPreferences (string[]), branchPreference (string), notes (string - observaciones breves)."
   - The user message for this call is: "Mensaje del usuario: {userMessage}\nRespuesta del bot: {replyText}\nPerfil actual: {JSON.stringify(currentProfile)}"
   - Parse the AI response as JSON. Merge non-empty fields into the existing profile. For `notes`, append new notes to existing, then cap at ~2000 chars.
   - Call `updateProfile(phone, mergedProfile)`.
   - This extraction is fire-and-forget: wrap in try/catch, log errors, never block the main response. If it fails, the profile just doesn't update.
   - Use the same AI provider instance. This is a cheap call (short prompt, short response).

5. If a conversation is new (just created), also set `linkedMemberId` in MySQL if the state machine found a matching user: `UPDATE whatsapp_conversations SET linked_member_id = {userId} WHERE id = {conversationId}`.
