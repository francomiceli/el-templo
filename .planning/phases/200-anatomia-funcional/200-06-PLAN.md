`anatomy/zone-hits.ts`:
- `export interface HitsZona { fuerte: MusculoId[]; sostiene: MusculoId[]; estira: MusculoId[]; movilidad?: true; sinDetalle?: true }`
- `export function rutasDistintas(ejercicios: readonly EjercicioZonaInput[]): string[]` — códigos normalizados que están en el modelo, sin repetir, en orden de aparición.
- `export function zoneHitsDeRutas(codes: readonly string[]): Partial<Record<ZonaSlug, HitsZona>>` — por cada ruta, cada rol con `GRUPO_DE_ROL[rol] !== null` y cada músculo con zona: agrega su id al grupo de esa zona (sin repetir; ids en el orden de `MUSCULOS`; zonas en el orden de `ZONAS_ORDEN`). Antagonista y músculos sin zona nunca aparecen. Sin claves vacías.
- `export function zoneHitsDelBloque(ejercicios: readonly EjercicioZonaInput[], role: string): Partial<Record<ZonaSlug, HitsZona>>`
  — `zoneHitsDeRutas(rutasDistintas(ejercicios))`; si da `{}` y `role` tiene fallback en `ROM_ROLE_ZONAS` (bloques ROM
  sin ruta), cada zona del fallback → `{ fuerte: [], sostiene: [], estira: [], movilidad: true }`. Así el chip marcado y
  la hoja coinciden con lo que pinta el cuerpo (`zonasDelBloque` usa el mismo fallback, D18). Decisión del planner: el
  fallback ROM no inventa músculos ni roles; el app lo muestra como "Trabaja la movilidad de esta zona".
  Si sigue dando `{}` (sin fallback ROM) y hay ejercicios sin ruta con zonas vía `zonasDeEjercicio` (`ZONAS_SIN_RUTA`:
  PLYO/POTENCIA/CARDIO/KL, D2), cada una de esas zonas → `{ fuerte: [], sostiene: [], estira: [], sinDetalle: true }`
  (agregar `sinDetalle?: true` a `HitsZona`). Así un bloque de potencia que enciende glúteos/cuádriceps/gemelos también
  marca su chip; el app lo muestra como "Este bloque trabaja esta zona" (sin músculos ni roles, D2).
