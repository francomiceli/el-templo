## Interaction Contracts

### S1 — RegisterPage `?ref=CODE`

**Capture:** clone the `promoCode` computed (`:213-216`) as `refCode` reading `route.query.ref` (string-or-null), and pass `ref: refCode.value ?? undefined` into `authStore.register({...})` (`:249-259`). Server resolves the code → `referrerId`.

**Confirmation badge (visible only when `?ref` present in URL):**

- Renders in the same slot/position as `.promo-badge` (above the register card). Reuse `.promo-badge` markup + styles 1:1 — icon `group_add`, eyebrow = `CÓDIGO DE REFERIDO`, prominent line = the code value (`{{ refCode }}`), and a subtext line (see copy). It is OPTIMISTIC: shown whenever the query param exists; the client cannot validate the code.
- If both `?promo` and `?ref` are present, both badges may stack (promo above, referral below) — no new layout logic, just two conditional blocks.

**States:**
| State | Behavior |
|-------|----------|
| No `?ref` param | Badge absent. Zero change vs today. |
| `?ref=CODE` present | Badge shown with the code, optimistically. |
| Registration submits, code valid | Link created `pending` server-side. Success toast stays GENERIC — see copy (do NOT promise a discount; qualification is deferred to first payment per D-01). |
| Registration submits, code invalid / self-referral / already-claimed | **Silent ignore.** Registration STILL succeeds; NO error notify about the referral. Attribution failure must never block or degrade signup (server wraps attribution in graceful-degradation try/catch, RESEARCH §auth analog `:263-272`). |

**Hard rule:** the referral must never add a blocking error, a required field, or a failure path to registration.

### S2 — MemberFormDialog "¿Quién lo trajo?"

**Placement:** CREATE flow only, Step 2 "Datos Personales", as a single full-width row AFTER the "Contacto de Emergencia" block (last field in the step). Rationale: it is optional attribution metadata, not identity — keep it below the required fields so it never competes with them. Do NOT add it to EDIT mode (a member has at most one referrer, set once at alta, D-14; editing attribution is Phase 158 admin-panel territory).

**Component:** copy the `SlotDetailDialog.vue:366-399` search pattern into a `q-select`, matching the surrounding `dense outlined` fields:

```
<q-select
  v-model="referrer"
  :options="referrerSearchResults"
  option-value="id" option-label="displayLabel"
  use-input clearable dense outlined
  input-debounce="300"
  :loading="searchingReferrer"
  label="¿Quién lo trajo? (opcional)"
  hint="Buscá por nombre o DNI al socio que lo refirió"
  @filter="onReferrerSearch" />
```

- `onReferrerSearch` mirrors `onMemberSearch` (`:898-924`): `< 2` chars → clear results; else `membersApi.searchMembers(val, 10)` → map to `{ id, displayLabel: "Nombre Apellido (DNI)" }`.
- Do NOT use the static `q-select`s already in the form (`:17`, `:79`) as the analog — those are fixed-option, not search-as-you-type.
- No prepend icon (match the plain fields around it — no new visual pattern).
- The picked `id` is submitted to the server, which validates and writes `referredBy`/`referrals` server-side (never trust the client body; Security V4).

**States:**
| State | Behavior |
|-------|----------|
| Empty / `< 2` chars typed | No results fetched. Quasar default input prompt; no loading. |
| Searching | `:loading` spinner in the field (terracotta), reusing analog behavior. |
| Results | Options list `Nombre Apellido (DNI)`. |
| No matches | `no-option` slot text: "No se encontró ningún socio". |
| Field left blank | Optional — alta proceeds with no attribution. NEVER blocks submit. |
| Server rejects the picked referrer (auto-referido / ya tiene referidor / socio no encontrado) | Surface via the EXISTING negative toast in `onSubmit`'s catch (`$q.notify({ type: 'negative', message })` via `extractError`, `:1104-1111`). Do NOT add a new inline error UI; the picker already constrains input to real members, so these are server-side edge cases. The alta itself is not rolled back UI-side beyond the existing catch. |

**Hard rule:** the "¿Quién lo trajo?" field is optional and has NO validation rule that can block the alta.
