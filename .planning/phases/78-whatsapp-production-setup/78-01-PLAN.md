**File 2: `docs/deployment/whatsapp-phone-registration.md`**

Document the WhatsApp Business phone number registration process:

1. **Prerequisites**:
   - Meta Business account verified at business.facebook.com
   - WhatsApp Business Platform app created at developers.facebook.com
   - A phone number that is NOT currently registered with WhatsApp (personal or business)
   - The phone number must be able to receive SMS or voice calls for verification

2. **Registration steps**:
   - Go to Meta Business Manager > WhatsApp Manager > Phone Numbers
   - Click "Add Phone Number"
   - Enter the phone number with country code (e.g., +54 for Argentina)
   - Choose verification method: SMS or voice call
   - Enter the verification code received
   - The number is now registered as a WhatsApp Business number

3. **Post-registration configuration**:
   - Set the display name (e.g., "El Templo")
   - Set the business profile (description, address, website, profile photo)
   - Copy the Phone Number ID from the dashboard -- this is `WHATSAPP_PHONE_ID` env var
   - The number can no longer be used with regular WhatsApp app

4. **Environment variable mapping**:
   - `WHATSAPP_PHONE_ID` = Phone Number ID from WhatsApp Manager dashboard
   - `WHATSAPP_TOKEN` = System User permanent token (see docs from Phase 77 DEPLOY-04)
   - `WHATSAPP_VERIFY_TOKEN` = Any random string you choose for webhook verification

5. **Important warnings**:
   - Once registered, the phone number is permanently tied to the WhatsApp Business Platform
   - You cannot use this number with the regular WhatsApp app anymore
   - For testing, use the Meta-provided test number (available in the app dashboard)
   - Production phone number should be a dedicated business line

Create a SQL migration that populates MySQL's timezone tables. This is needed because CONVERT_TZ returns NULL when timezone data is not loaded (used in class-reminder.ts lines 96-101 to convert UTC to America/Argentina/Buenos_Aires).

The migration file `el-templo-api/src/db/migrations/0043_populate_timezone_tables.sql` should:

1. Create the core timezone data that MySQL needs for named timezone conversions. Since `mysql_tzinfo_to_sql` is a CLI tool that can't run in a SQL migration, use an alternative approach:

   Insert the minimum required timezone data directly. For the bot's needs, only `America/Argentina/Buenos_Aires` is required (UTC-3, no DST since 2009).

   ```sql
   -- Populate MySQL timezone tables for CONVERT_TZ support
   -- Required by bot schedulers (class-reminder, trial-followup) that convert UTC to Argentina time
   --
   -- Argentina (Buenos Aires) is UTC-3 with no DST since 2009.
   -- This migration inserts the minimum timezone data needed.
   -- For full timezone support, run on the server:
   --   mysql_tzinfo_to_sql /usr/share/zoneinfo | mysql -u root mysql
   --
   -- This migration is idempotent: uses INSERT IGNORE to skip existing rows.

   -- Time zone name entry
   INSERT IGNORE INTO mysql.time_zone (Time_zone_id, Use_leap_seconds) VALUES (1, 'N');
   INSERT IGNORE INTO mysql.time_zone_name (Name, Time_zone_id) VALUES ('America/Argentina/Buenos_Aires', 1);

   -- Transition type: UTC-3 (offset = -10800 seconds), no DST
   INSERT IGNORE INTO mysql.time_zone_transition_type (Time_zone_id, Transition_type_id, Offset, Is_DST, Abbreviation) VALUES (1, 0, -10800, 0, 'ART');

   -- Single transition (effective from epoch)
   INSERT IGNORE INTO mysql.time_zone_transition (Time_zone_id, Transition_time, Transition_type_id) VALUES (1, 0, 0);

   -- Also add UTC alias for completeness
   INSERT IGNORE INTO mysql.time_zone (Time_zone_id, Use_leap_seconds) VALUES (2, 'N');
   INSERT IGNORE INTO mysql.time_zone_name (Name, Time_zone_id) VALUES ('UTC', 2);
   INSERT IGNORE INTO mysql.time_zone_transition_type (Time_zone_id, Transition_type_id, Offset, Is_DST, Abbreviation) VALUES (2, 0, 0, 0, 'UTC');
   INSERT IGNORE INTO mysql.time_zone_transition (Time_zone_id, Transition_time, Transition_type_id) VALUES (2, 0, 0);

   -- Flush tables to pick up changes
   FLUSH TABLES;
   ```

   **IMPORTANT:** Add a comment at the top of the migration noting that for production, the preferred approach is running `mysql_tzinfo_to_sql /usr/share/zoneinfo | mysql -u root mysql` on the server, which loads ALL timezones from the OS. This migration is the fallback for environments where that command cannot be run (e.g., managed MySQL, CI).

   Also add a comment noting that if the `mysql.time_zone` table already has data (e.g., from `mysql_tzinfo_to_sql` having been run), the INSERT IGNORE statements will safely skip without error.
