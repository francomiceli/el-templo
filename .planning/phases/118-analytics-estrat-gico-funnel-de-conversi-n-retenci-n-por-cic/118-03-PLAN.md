<objective>
Implementar la PROPUESTA #4: Caja vs Devengado + ARPU, todo separado por moneda (D-08).

Decisiones LOCKED:

- D-07: devengado prorrateado sobre la ventana real `start_date..end_date` de cada sub:
  `price_paid × (días-de-la-sub-dentro-del-mes ÷ días-totales-start..end)`. VALIDAR null/0/end<start
  ANTES de dividir; subs con ventana inválida se EXCLUYEN con caveat (nunca dividir por 0).
- **Hallazgo del researcher confirmado en código:** `cancelSubscription` (subscriptions/service.ts
  ~línea 1834) setea `status='cancelled'` + `cancelledAt` pero **NO acorta `end_date`**. Por lo tanto,
  para que el devengado sea honesto, la ventana efectiva de una sub cancelada debe terminar en
  `MIN(end_date, cancelled_at)` cuando `cancelled_at < end_date`. Si no se hiciera, una sub cancelada
  inflaría el devengado de meses futuros que nunca se prestaron. Documentar este criterio en el SUMMARY.
- D-08: caja = lo que ya calcula revenueTrend (misma forma); mostrar ambas series; ARPU mensual =
  devengado ÷ activos del mes (activeMemberExists); TODO por moneda (ARS/EUR jamás sumadas).
- D-11: endpoint SENSIBLE → ADMIN_ROLES con requireAdminAnalytics.
- D-12: test de integración obligatorio contra MySQL real (limpia financial_transactions/
  transaction_links/balances).

Domain service NUEVO. NO tocar el monolito analytics/service.ts (v4.9) — copiar la forma de
getRevenueTrend, no extenderlo.

Purpose: revenue honesto para planes largos (efecto "prepago largo") + métrica de salud unitaria.
Output: AdvancedFinanceService + endpoint + tipos/schema + test.
</objective>
