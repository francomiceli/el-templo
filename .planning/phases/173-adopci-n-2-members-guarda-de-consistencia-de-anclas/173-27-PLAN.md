<objective>
Paso 6 de la receta, plan 2 de 3: la batería de las **10 rutas de la ficha del socio**.

Purpose: son las rutas donde el `userId` llega **por la URL** y el servidor decide qué hacer con
él. Cuatro de ellas **escriben** (crear, editar y borrar notas; cambiar password) y una **crea una
relación entre dos usuarios** (asignar referidor). Es donde un fallo no solo filtra: modifica datos
de otro gimnasio. `PUT /:userId/password` es el peor caso de toda la fase — un fallo ahí permite
tomar control de una cuenta ajena.

Output: el segundo archivo de la batería, con la evidencia de escritura leída de la base.
</objective>

<threat_model>

## Trust Boundaries

| Boundary                        | Description                                                                          |
| ------------------------------- | ------------------------------------------------------------------------------------ |
| `:userId` de la URL → escritura | el id llega del cliente y decide sobre qué fila se escribe                           |
| `:noteId` + `:userId` → nota    | dos ids en la misma URL: una sola validación deja la otra combinación abierta        |
| `POST /:userId/referrals`       | crea una relación **entre dos usuarios**: el segundo extremo también puede ser ajeno |
| `PUT /:userId/password`         | un fallo acá es toma de control de una cuenta de otro gimnasio                       |

## STRIDE Threat Register

| Threat ID   | Category               | Component                        | Disposition | Mitigation Plan                                                                                                                         |
| ----------- | ---------------------- | -------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| T-173-27-01 | Elevation of Privilege | `PUT /:userId/password`          | mitigate    | caso dedicado que compara el `password_hash` de la base antes y después; control positivo que prueba que sí cambia para un socio propio |
| T-173-27-02 | Tampering              | `POST/PUT/DELETE` de notas       | mitigate    | conteo de filas antes/después y las DOS combinaciones cruzadas de `noteId`/`userId`                                                     |
| T-173-27-03 | Tampering              | `POST /:userId/referrals`        | mitigate    | intento de asignar un referidor de otro gimnasio: la relación cross-tenant no puede quedar persistida                                   |
| T-173-27-04 | Information Disclosure | historial financiero y conceptos | mitigate    | 404/vacío con el **motivo** afirmado junto al status; cero 403                                                                          |
| T-173-27-05 | Repudiation            | rechazo que ya escribió la mitad | mitigate    | la evidencia son varias columnas juntas en un solo `toEqual`, no una sola columna                                                       |
| T-173-27-06 | Information Disclosure | `POST /:userId/photo/upload-url` | mitigate    | no se genera URL prefirmada para un socio ajeno, verificado sin pegarle a S3                                                            |

</threat_model>
