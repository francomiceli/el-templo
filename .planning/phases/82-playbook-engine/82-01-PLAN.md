<objective>
Build the pure playbook resolver and the static registry of playbooks PB1-PB5 with their stages. This is the foundation of the Playbook Engine: a side-effect-free function that, given a contact's clientState and an optional Redis session snapshot, returns exactly one {playbookId, stageId} pair. No IO, no Redis, no prompt rendering — those land in plans 02 and 03.

Purpose: Locks in the engine's contract so subsequent plans can integrate it into the handler and the system prompt without ambiguity. The pure-function shape makes the engine trivially unit-testable and free of WhatsApp / Redis coupling.

  </objective>

1. `el-templo-bot/src/playbooks/resolver.ts` — Implement the engine's only public function:

```ts
import { PLAYBOOKS } from "./definitions.js";
import type { PlaybookId, PlaybookSessionState, ResolveContact, StageId } from "./types.js";

export interface ResolveResult {
  playbookId: PlaybookId | null;
  stageId: StageId | null;
}

export function resolvePlaybook(
  contact: ResolveContact,
  session: PlaybookSessionState | null,
): ResolveResult { ... }
```

Resolution rules (in order — first match wins):

1. **Cancellation intent overrides everything.** If `contact.cancellationIntent === true`, return `{ playbookId: "PB5", stageId: PLAYBOOKS.PB5.entryStageId }`. PB5 fires regardless of the underlying clientState because the user is explicitly asking to leave.
2. **Session reuse.** If `session?.activePlaybook` is set AND `session.currentStage` is set AND the active playbook is still consistent with the contact's clientState (use the mapping below), return the existing `{activePlaybook, currentStage}` unchanged. This guarantees the resolver is idempotent across turns and stage progression (which lives in plan 02) is preserved.
3. **State -> playbook mapping** (fresh resolution):
   - `lead` -> PB1, entryStageId
   - `trial` -> PB2, entryStageId
   - `expired_member` -> PB3, entryStageId
   - `inactive_member` -> PB4, entryStageId
   - `active_member` -> `{ playbookId: null, stageId: null }` (no active playbook — Mica falls back to her base persona; PB3 only kicks in via near-expiry signals which are a v5.4 concern)
4. **Consistency check helper** (private): A small `isConsistent(playbookId, clientState)` that encodes the inverse of the mapping above. Used by step 2.

The function MUST be pure: no `await`, no Redis import, no Date.now(), no logging. It is allowed to read from the in-memory `PLAYBOOKS` constant.

2. `el-templo-bot/test/playbook-resolver.test.ts` — Vitest suite. Cover:

- `lead` -> PB1.E1A
- `trial` -> PB2.E1A

- `active_member` -> `{ playbookId: null, stageId: null }`
- Cancellation intent on a `lead` -> still returns PB5 (override semantics)
- Cancellation intent on an `active_member` -> returns PB5
- Session reuse: contact `lead`, session `{activePlaybook: 'PB1', currentStage: 'PB1.E3'}` -> returns `PB1.E3` (NOT entry stage)
- Session reuse with mismatch: contact `expired_member`, session says `PB1.E2A` -> ignores stale session, returns `PB3.E1`
- Null session: contact `lead` -> returns `PB1.E1A`
- PB6 absence guard: `expect((PLAYBOOKS as Record<string, unknown>).PB6).toBeUndefined();`
- Purity smoke test: call `resolvePlaybook` 100 times with the same input and assert deep equality on every result (no hidden randomness).

Run with `pnpm test playbook-resolver` from `el-templo-bot/`. Use the same vitest patterns visible in existing `el-templo-bot/test/state-machine.test.ts` for consistency.

NOT allowed: importing Redis, the handler, the system prompt, or anything from `el-templo-api`. The resolver lives in isolation.
