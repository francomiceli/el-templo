  <action>
Read the current `getSystemPrompt` implementation. Extend the `SystemPromptOptions` interface:

```ts
import type { PlaybookId, StageId } from "../playbooks/types.js";
import { PLAYBOOKS } from "../playbooks/definitions.js";

interface SystemPromptOptions {
  clientState?: ClientState;
  profileContext?: string;
  activePlaybook?: PlaybookId | null;
  currentStage?: StageId | null;
}
```

Rendering rules (implement in this order at the bottom of `getSystemPrompt`, after the existing STATE_SECTIONS / profileContext blocks):

1. If `options?.activePlaybook` is set AND `options.currentStage` is set:
   a. Look up `PLAYBOOKS[activePlaybook]`. If not found, log nothing (silent) and skip playbook injection.
   b. Find the stage: `definition.stages.find(s => s.id === currentStage)`. If not found, fall back to the entry stage.
   c. Append exactly ONE section with a stable, grep-able header:

```
\n\n*Playbook activo: <definition.name> (<stage.id>)*\n\n<stage.promptSection>
```

d. Prepend a one-line directive: `Estás ejecutando el playbook <playbookId>, etapa <stageId>. Seguí ESTA guía y sólo ésta. Ignorá cualquier otra guía que hayas visto antes.` This is defensive — it tells the model to treat this section as authoritative even if old instructions leak through the context window.

2. CRITICAL: under NO circumstances iterate over `PLAYBOOKS` and concatenate all of them. The other four playbooks must never appear in the output. The only path that reads from `PLAYBOOKS` is the single `PLAYBOOKS[activePlaybook]` lookup above.

3. Preserve backward compatibility: if `activePlaybook` is `null` or `undefined`, render the prompt EXACTLY as v5.2 did (existing STATE_SECTIONS behavior untouched). This keeps the v5.2 QA suite (AVAT-03 in phase 85) passing.

4. The existing `STATE_SECTIONS` block stays as-is for now. Rationale: it's a short contextual note, and when an `activePlaybook` is set it will be superseded by the more detailed playbook section anyway. Plan 84 will revisit whether STATE_SECTIONS should be suppressed when a playbook is active. Leave a `// TODO(phase-84): consider suppressing STATE_SECTIONS when activePlaybook is set to avoid double-framing` comment.

5. Header format discipline: use `*Playbook activo: PB1 (PB1.E2A)*` as the EXACT format string. Tests will grep for this. Do NOT use markdown `###` — project rule (no markdown headers in Mica's WhatsApp output, and keeping the prompt consistent avoids confusing the model).

No `any`, no `console.*`, `catch (err: unknown)` if you add any try/catch (none should be needed — this is a pure string-building function).

Create a new Vitest file. Required test cases:

1. **Single-section invariant (PB1 lead):**
   - Call `getSystemPrompt({ clientState: "lead", activePlaybook: "PB1", currentStage: "PB1.E2A" })`.
   - Assert the output contains exactly ONE occurrence of `*Playbook activo:` — use `(out.match(/\*Playbook activo:/g) || []).length === 1`.
   - Assert `out.includes("*Playbook activo: PB1 (PB1.E2A)*")`.
   - Assert the output does NOT contain the other playbook names as section headers: `expect(out).not.toContain("Playbook activo: PB2")` and similarly for PB3, PB4, PB5.

2. **Other playbooks absent (content check):**
   - Extract a UNIQUE STRING from each playbook's entry stage's `promptSection` in `definitions.ts` (pick a distinctive Spanish phrase that only appears in that playbook — e.g. for PB3 "renovación", for PB5 "cancelar", for PB4 "30 días"). Store them as test fixtures.
   - With `activePlaybook: "PB1"`, assert the unique PB2/PB3/PB4/PB5 phrases are NOT in the output. This catches accidental concatenation bugs.
   - Rotate through all five playbooks (PB1, PB2, PB3, PB4, PB5), asserting only the active one's distinctive phrase is present.

3. **Stage-specific content:**
   - With `activePlaybook: "PB1", currentStage: "PB1.E2A"`, assert the output contains at least the first 20 characters of `PLAYBOOKS.PB1.stages.find(s => s.id === "PB1.E2A")!.promptSection`.
   - With `currentStage: "PB1.E3"`, assert it contains E3's text and NOT E2A's text (when they differ).

4. **No-playbook fallback:**
   - Call `getSystemPrompt({ clientState: "active_member" })` (no `activePlaybook`).
   - Assert `out.match(/\*Playbook activo:/g) === null`.
   - Assert the existing STATE_SECTIONS text for `active_member` is still present (backward compatibility).

5. **Unknown playbook safety:**
   - Call with `activePlaybook: "PB99" as PlaybookId` (cast) and assert it does not throw and the output contains no `*Playbook activo:` header.

6. **Unknown stage fallback:**
   - Call with `activePlaybook: "PB1", currentStage: "PB1.E999" as StageId` and assert the output contains the entry stage's content instead (graceful fallback).

Import the test fixtures directly from `../src/playbooks/definitions.js` so they stay in sync — do NOT hardcode the Spanish strings in the test file, read them from `PLAYBOOKS`.
