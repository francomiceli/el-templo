<objective>
Wire frequency into segmentation for the GOLDEN CASE ONLY (FREQ-05/06): an active (paying) member with 0 visits in the frequency window, or cooling down, gets the `en_riesgo` segment. The threshold is a tuneable `system_settings` key (mirroring `SEGMENT_DEFAULTS`, NOT an env var). The frequency signal is fed into the EXISTING nightly batch (`notification-cron.ts`, ~03:00 AR) as one more input — NO new cron is created, the login-recalc cooldown path stays unchanged, and the fine multi-band→segment mapping is explicitly NOT introduced (deferred to the segmentation module owner).

Purpose: Frequency is the strongest proactive churn predictor; surfacing the unambiguous high-value case (paying member who stopped showing up) as `en_riesgo` is the highest-leverage minimal change. This is the highest-risk piece of the phase, deliberately scoped to the golden case only (D-123-01/02).

Output: golden-case override in `calculateSegment` + a new `system_settings` threshold key + the existing batch extended to thread the frequency signal + an integration test for the golden case.
</objective>
