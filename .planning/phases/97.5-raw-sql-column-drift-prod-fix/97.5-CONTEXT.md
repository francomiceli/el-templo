## Implementation Decisions

### Test Surfaces

- **D-01 — RED integration test in a dedicated file at `el-templo-api/test/whatsapp/ai-tools-membership-drift.test.ts`:** Reproduces `Unknown column 'sub.status'` (and `'s.status'`) against real MySQL with a seeded active-subscription row. Two reasons: (1) follows the CLAUDE.md convention — integration tests for bot logic live in `el-templo-api/test/whatsapp/` (shared test DB); since reproducing the Unknown-column error requires real MySQL, this is an integration test by definition. (2) A separate file avoids commit-order coupling with the Phase 98 retry, which reopens `ai-tools.test.ts` to apply `98-TASK-2-WIP.patch` (104 lines) — no merge friction at cherry-pick time. Rejected: appending a `describe()` to existing `ai-tools.test.ts` (Phase 98 coupling); cross-package in `el-templo-bot/test/` (bot-side tests don't currently hit real MySQL — `MockAiProvider` pattern per `.planning/codebase/TESTING.md §"Bot Testing Strategy"`; routing real MySQL there just for this would establish a divergent pattern).

### Sweep-Lint Architecture

- **D-02 — Sweep-lint scanner = regex + line-by-line accumulator, zero new deps:** Scanner at `el-templo-api/test/lint/raw-sql-column-drift.test.ts`. Walks `.ts` files under `el-templo-bot/src/**` and `el-templo-api/src/**`, finds `` sql`...` `` blocks via a stateful line-by-line accumulator (handles multi-line templates), then matches `<alias>.<col>` and bare `<col>` references against the rename map. Rationale: the 175 known SQL sites are uniform and finite (sweep-confirmed in debug session); ts-morph is a 5MB devDep overkill; the hybrid mini-parser adds tokenizer complexity this codebase doesn't need. The lint is a SECONDARY guard behind the D-01 RED integration test — it doesn't need AST precision.
  - **D-02 (i) — Bare-column coverage REQUIRED:** Parse `FROM <table> [<alias>]` and `JOIN <table> <alias>` to know which tables are in scope for each `` sql`...` `` block. In single-table blocks (no JOIN), cross-check **bare unqualified column tokens** against the renamed columns of the FROM-table — NOT only `<alias>.<col>` patterns. Rationale: the codebase mixes both styles (`SELECT sub.status FROM subscriptions sub` AND `SELECT id, conversation_status FROM whatsapp_conversations` with no alias). Without bare-column detection, a future `SELECT status FROM subscriptions` drift is a false negative.
  - **D-02 (ii) — Synthetic-drift positive-control test REQUIRED:** A negative-control test feeds the scanner a known-drift fixture (e.g., a string `` sql`SELECT sub.status FROM subscriptions sub` `` constructed in-test) and asserts the scanner flags it. Guards against the scanner silently becoming a no-op (regex bug → matches nothing → false green). This fixture stays PERMANENTLY in the test file even after the 3 real drift sites are fixed in GREEN — it's the self-test that survives.
  - **D-02 (iii) — Drizzle-interpolated refs skipped:** Column references of the form `${schema.table.column}` or `${table.column}` resolve at Drizzle query-build time and are never wrong. Scanner detects and skips these via the `${...}` placeholder boundary before column-ref matching.

- **D-03 — Sweep-lint rename map: live Drizzle introspection + must-include SUBSET coverage assertion:** Build the JS-property → SQL-column rename map at test boot by walking every export of `el-templo-api/src/db/schema/*.ts` and reading each column's `.name` SQL-column attribute (Drizzle exposes this). The discovered map auto-updates when schema renames are added in v5.4.0+, zero hand-maintenance. PLUS an in-test assertion that `discoveredMap ⊇ knownHighRiskSet` — the discovered map must include the high-risk plain-word → prefixed renames verified by the debug-session sweep: `subscriptions.status → subscription_status`, `bookings.status → booking_status`, `attendance.status → attendance_status`, `attendance.source → attendance_source`, `whatsapp_conversations.status → conversation_status`, `whatsapp_messages.direction → message_direction`, `whatsapp_messages.messageType → wa_message_type`, `aura_config.sourceType → aura_config_source_type`, `exercises.level → exercise_level`, `format_compatibility.level → compat_level`. **Subset, NOT equality** — equality would break every time a new schema column-rename is added, defeating the auto-coverage benefit. Anchor the assertion on plain-word → prefixed renames only (status/source/direction/level → prefixed); medium camelCase → snake renames are covered by introspection without being asserted. Same guard-the-guard logic as D-02 (ii): if Drizzle internals shift or a schema import breaks, the coverage assertion fails LOUD instead of the scanner silently checking nothing.

### Fix Shape Application

- **D-04 — Inline rename in both `SubscriptionRow` declarations + JS-side reads, NO hardcoded unit pin:** The interface is declared twice with intentionally different shapes — `tools.ts:452` (8 fields for `checkMembership`'s SELECT: plan_name, status, start_date, end_date, price_paid, classes_per_week, multi_branch, +1) and `machine.ts:39` (3 fields for `determineClientState`'s SELECT: status, end_date, is_trial). Rename `status` → `subscription_status` in BOTH inline declarations and update JS-side reads at `tools.ts:538`, `machine.ts:90`, `machine.ts:116`. Rejected: extracting a shared `SubscriptionRow` type — the two shapes are intentionally different (different SELECT lists / consumers), so a shared type either over-types one consumer or splits into base+extends, an architectural change beyond the 4-surface cap (SC#4). Rejected: adding a Phase-95-§E-style hardcoded unit assert `expect(subscriptions.subscription_status.name).toBe("subscription_status")` — the D-02/D-03 sweep-lint generalizes that pattern across ALL tables via live introspection, so adding the pin would duplicate the sweep-lint with exactly the hardcoded-constant pattern we rejected in D-03.

### Commit Ordering

- **D-05 — Sweep-lint lands RED-FIRST, never after the GREEN fix:** The sweep-lint test (D-02 + D-03) must be authored in a state where it detects the 3 REAL drift sites (`tools.ts:495` `sub.status`, `tools.ts:500` `sub.status`, `machine.ts:77` `s.status`) and FAILS against `master`. The GREEN fix then turns BOTH the D-01 integration test AND the sweep-lint green simultaneously. Positive-control on real drift is stronger than the synthetic fixture alone — the synthetic fixture from D-02 (ii) stays as the PERMANENT self-test that survives after the real drift is fixed.
  - **Canonical commit chain (3 commits):** (1) RED — both `ai-tools-membership-drift.test.ts` AND `raw-sql-column-drift.test.ts` added, both FAIL on `master`; (2) GREEN — Option B fix applied (rename + 3 SELECT fixes + JS-side reads), both turn green; (3) SUMMARY.
  - **If plan-phase splits into 4 commits** (e.g., RED-A integration test → RED-B sweep-lint → GREEN → SUMMARY), the sweep-lint MUST still be RED-first, never added after the fix. Sequence order: integration test RED, then sweep-lint RED (both visible failing on `master` head), then GREEN fix, then SUMMARY.

<specifics>
## Specific Ideas

- **"Positive-control on real drift" philosophy:** D-05's RED-first sweep-lint is a stronger signal than the synthetic fixture alone because the real 3 drift sites prove the scanner detects the actual prod-bug class. The synthetic fixture (D-02 ii) is the safety net that survives after the real sites are GREEN — it ensures the scanner stays functional if a future refactor accidentally turns it into a no-op.
- **"Generalize, don't pin"** (drove D-04 rejection of the §E-style hardcoded unit assert): when a guardrail can be expressed as a rule over all relevant cases (the sweep-lint's live rename map), prefer it over a hardcoded constant per case (the §E unit pin). The pin is the seed of future maintenance debt; the rule auto-extends.
- **"Subset, not equality"** (D-03): introspection must DISCOVER more renames than asserted, not exactly the asserted set. This decouples the assertion from schema evolution.

</specifics>
