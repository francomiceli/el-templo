<objective>
Refactorizar la capa de auth de la member app (Quasar/Capacitor) para que un usuario activo nunca sea desloguado: (1) `useTokenStorage` pasa a dual-key (`accessToken` + `refreshToken`) con lectura del `authToken` legacy como access y cleanup diferido (D-03); (2) el `authStore` (`login`/`register`/`logout`) persiste ambos tokens vía `setTokens` y limpia vía `clearTokens` — sin esto el `refreshToken` del response nunca se guarda y el interceptor encuentra `getRefreshToken()=null` siempre, deslogueando al primer 401 y anulando toda la fase; (3) el interceptor de axios gana un lock anti-refresh-storm (Promise compartida en module scope) que dispara un único `/auth/refresh` por oleada de 401, encola y reintenta (D-02); (4) el boot hace refresh silencioso si el access expiró antes de `/auth/me` (Req 11). Incluye el unit test del lock con 5 requests 401 concurrentes (acceptance de Req 9).

Purpose: Cierra el problema raíz reportado (logout recurrente). Consume el contrato del API ya planificado (Plans 01/02): `POST /auth/refresh` body `{ refreshToken }` → `{ accessToken, refreshToken }`.
Output: storage dual-key + authStore que persiste ambos tokens + interceptor con lock + boot resiliente + unit test verde.
</objective>

Estado actual (a refactorizar):

- useTokenStorage.ts: key única `authToken`, getToken/setToken/removeToken (Capacitor Preferences native / localStorage web).
- stores/useAuthStore.ts (Pinia setup store): `login()` y `register()` leen `{ token: newToken, user }` del response, hacen `await setToken(newToken)` + `token.value = newToken`; `logout()` hace `await removeToken()`. Usa `const { setToken, removeToken } = useTokenStorage()`. Estos handlers son los ÚNICOS lugares que persisten el token tras autenticar — si no se actualizan, el `refreshToken` del nuevo contrato se descarta y la fase no funciona.
- boot/axios.ts: interceptor request agrega Bearer; interceptor response 401 borra token + redirige /login (sin retry). Tiene un workaround Android WebView (data={} en mutating requests) que NO debe perderse.
- boot/auth.ts: lee token, setea authStore.token, llama /auth/me; si falla → clearAuth + removeToken.

D-03 (storage soft migration):

- Lectura de access: si existe `accessToken` nuevo, usarlo; si NO existe pero sí `authToken` legacy, usar el legacy como access.
- Escritura: las keys nuevas (`accessToken`+`refreshToken`) se escriben en el primer refresh exitoso o re-login; `authToken` se borra DIFERIDO en ese mismo momento (NO eager al boot).

D-02 (lock):

- Promise compartida en module scope (NO por-request). El primer 401 dispara un único `/auth/refresh`; los concurrentes encolan/reusan la misma Promise; reintento único tras refresh exitoso.
- `/auth/refresh` whitelisteado: un 401 del propio refresh → clearAuth + redirect /login (no re-dispara refresh).
- Patrón ~40 LOC por-app (D-02): NO crear package compartido cross-repo.
