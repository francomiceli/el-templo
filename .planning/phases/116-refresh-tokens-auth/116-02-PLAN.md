<!-- Contrato del response que consumen los frontends (LOCKED — no degradar). -->

POST /api/auth/login -> 200 { token, accessToken, refreshToken, user, ... }
POST /api/auth/register -> 200/201 { token, accessToken, refreshToken, user, ... }
POST /api/auth/refresh -> body { refreshToken } -> 200 { accessToken, refreshToken } | 401 si inválido/revocado/expirado
POST /api/auth/logout -> body { refreshToken } -> 200 siempre (idempotente, D-04)
POST /api/auth/me/change-password -> body { currentPassword, newPassword } -> 200 { message, accessToken, refreshToken } (D-01)
POST /api/auth/me/delete-account -> (sin cambio de contrato visible) revoca refresh internamente (D-05)

NOTA path (D-01): el endpoint real de cambio de password es `POST /me/change-password` (routes.ts:534) bajo prefix `/api/auth` (app.ts:114). NO usar `/auth/change-password`.

RefreshTokenService (de Plan 01):

- issue(userId): Promise<string>
- rotate(plain): Promise<{ newToken: string; userId: number }> — lanza error tipado 401 si inválido/revocado/reuse. CLAVE: devuelve el `userId` del dueño del refresh, NO el email/role. La ruta /refresh DEBE consultar `users` por ese `userId` para obtener `email` + `role` antes de firmar el access JWT (ver Task 2).
- revoke(plain): Promise<void> [idempotente]
- revokeAllForUser(userId): Promise<void>

Firma access (Plan 01): `fastify.jwt.sign(payload, { expiresIn: fastify.accessTokenExpiresIn })` (30m), payload `{ userId, email, role }`. El `token` legacy se sigue firmando con el default 7d (`fastify.jwt.sign(payload)`).

Query de user por id (patrón YA presente en routes.ts:443 — `users` está importado): `await fastify.db.select({ id: users.id, email: users.email, role: users.role }).from(users).where(eq(users.id, userId)).limit(1)`. Importar `eq` y `users` ya están en scope del archivo.
