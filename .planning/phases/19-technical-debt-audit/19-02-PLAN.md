    1. Install Sentry: `cd el-templo-api && pnpm add @sentry/node`

    2. Create `el-templo-api/src/instrument.ts` -- Sentry initialization file:
       - Call `Sentry.init()` with:
         - `dsn`: from `process.env.SENTRY_DSN` (gracefully no-op if not set)
         - `environment`: from `process.env.NODE_ENV || 'development'`
         - `tracesSampleRate`: 0.2 in production, 1.0 otherwise
         - `sendDefaultPii`: true (captures user IP, request headers)
         - `beforeSend` hook: scrub `password`, `currentPassword`, `newPassword` from `event.request?.data`
       - Guard the entire init: if `!process.env.SENTRY_DSN`, skip init entirely (allows running without Sentry in dev)

    3. Modify `el-templo-api/src/index.ts`:
       - Add `import './instrument';` as the VERY FIRST import, before dotenv, before Fastify, before everything.
       - This is critical: Sentry must instrument modules before they load.

    4. Modify `el-templo-api/src/app.ts`:
       - After all plugins and routes are registered, add:
         ```typescript
         import * as Sentry from '@sentry/node';
         // ... at end of buildApp(), before return:
         Sentry.setupFastifyErrorHandler(app);
         ```
       - This hooks into Fastify's error lifecycle to capture unhandled errors.

    5. Add user context enrichment: In the authenticate decorator (or a new onRequest hook in app.ts), after JWT validation succeeds, call:
       ```typescript
       Sentry.setUser({ id: request.user.id, email: request.user.email });
       ```
       So all subsequent errors in that request include user identity.

    Per discretion: API-only Sentry in this phase. Frontend Sentry projects can be added later as a 30-minute task using the boot file pattern from RESEARCH.md.

  <action>
    Create a lightweight `createLogger(context: string)` utility in both frontend apps. This replaces raw console.* calls with structured, level-gated logging. The logger:

    1. Exports a `createLogger(context: string)` function that returns `{ debug, info, warn, error }` methods.
    2. Each method accepts `(message: string, data?: Record<string, unknown>)`.
    3. In production (`import.meta.env.PROD`):
       - `debug` and `info` are suppressed (no output)
       - `warn` outputs to console.warn
       - `error` outputs to console.error
    4. In development: all levels output with `[context]` prefix for easy filtering.
    5. All output includes the context string: `[DayPlayer] Session started { sessionId: '123' }`
    6. No external dependencies -- this is a pure TypeScript utility (< 40 LOC).
    7. The logger is designed to integrate with Sentry later: the `error` method is the natural hook point for `Sentry.captureMessage()` when frontend Sentry is added.

    Create the `utils/` directory if it doesn't exist in either project. The file should be identical in both projects (copy-paste is fine for a 30-line utility -- no shared package needed at this scale).

    Usage pattern (document in a comment at top of file):
    ```typescript
    import { createLogger } from 'src/utils/logger';
    const log = createLogger('DayPlayer');
    log.info('Session started', { sessionId: '123' });
    log.error('Failed to load session', { error: err.message });
    ```
  </action>
  <verify>

  </verify>
