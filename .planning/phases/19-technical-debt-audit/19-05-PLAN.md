<task type="auto">
  <name>Task 1: Set up Husky + lint-staged at monorepo root</name>
  <files>
    package.json
    .husky/pre-commit
  </files>
  <action>
    The monorepo currently has NO root package.json. Git hooks must live at the repo root (where .git is).

    1. Create root `package.json`:
       ```json
       {
         "name": "el-templo",
         "private": true,
         "scripts": {
           "prepare": "husky"
         },
         "devDependencies": {
           "husky": "^9.0.0",
           "lint-staged": "^16.0.0"
         },
         "lint-staged": {
           "el-templo-api/**/*.ts": [
             "eslint --fix --config el-templo-api/eslint.config.js"
           ],
           "el-templo-app/**/*.{ts,vue}": [
             "eslint --fix --config el-templo-app/eslint.config.js"
           ],
           "el-templo-admin/**/*.{ts,vue}": [
             "eslint --fix --config el-templo-admin/eslint.config.js"
           ],
           "**/*.{ts,vue,js,json,md}": [
             "prettier --write"
           ]
         }
       }
       ```

    2. Install dependencies: `cd /home/franco/projects/el-templo && pnpm install`

    3. Initialize Husky: `pnpm exec husky init`
       This creates `.husky/` directory and a sample pre-commit hook.

    4. Set up the pre-commit hook at `.husky/pre-commit`:
       ```bash
       pnpm exec lint-staged
       ```

    5. **Verify ESLint configs exist** for each project before configuring lint-staged:
       - Check `el-templo-api/eslint.config.js` (or .mjs/.cjs) -- if it doesn't exist, lint-staged should skip that project's lint rule or use a minimal config.
       - Check `el-templo-app/eslint.config.js` -- the app likely has this from Quasar.
       - Check `el-templo-admin/eslint.config.js` -- same as app.
       - Adjust the lint-staged config glob to match actual config file names (.js, .mjs, .cjs).

    6. **Verify Prettier is available:** Check if prettier is installed in any project. If not installed anywhere, add it to root devDependencies: `pnpm add -D prettier`. If already in sub-projects, it should be accessible from root via node_modules resolution.

    7. **Test the hook:** Create a test file with formatting issues, stage it, attempt commit, verify lint-staged runs and fixes. Then delete the test file.

    Important: Husky v9 uses a simple directory structure. The `.husky/pre-commit` file is just a shell script, no special format needed. Make sure it's executable (`chmod +x .husky/pre-commit`).
  </action>
  <verify>

    - `chmod +x .husky/pre-commit` confirms executable (or already is)
    - Create a temp file with bad formatting, `git add` it, `git commit --dry-run` or test with a real commit -- lint-staged should run

  <action>
    Create `README.md` at the repository root with the following sections:

    **1. Project Header:**
    - "El Templo" title
    - One-line description: "A modular fitness super-app for El Templo gym -- member training, admin management, and session generation."
    - Tech badges (optional): Vue 3, Fastify, TypeScript, MySQL

    **2. Architecture Overview:**
    - 3-app monorepo structure:
      - `el-templo-app/` -- Member-facing Vue 3 + Quasar + Capacitor PWA/mobile app
      - `el-templo-admin/` -- Coach/admin Vue 3 + Quasar web app
      - `el-templo-api/` -- Fastify + TypeScript + Drizzle ORM + MySQL API
    - Brief description of each app's purpose
    - How apps communicate (API is shared backend, CORS configured for both frontends)

    **3. Tech Stack:**
    - Frontend: Vue 3, Quasar Framework, TypeScript, Capacitor (member app), Pinia stores
    - Backend: Fastify 5, TypeScript, Drizzle ORM, MySQL 8
    - Infrastructure: GitHub Actions CI/CD, PM2, Nginx, Let's Encrypt SSL
    - Domains: app.eltemplo.org, admin.eltemplo.org, api.eltemplo.org

    **4. Prerequisites:**
    - Node.js 22+
    - pnpm 10+
    - MySQL 8.0+
    - Git

    **5. Getting Started:**
    - Clone the repository
    - Install dependencies: `pnpm install` in each project directory
    - Database setup: create database, copy .env.example to .env, configure credentials
    - Run migrations: `cd el-templo-api && pnpm run build && node dist/db/run-migrations.js`
    - Seed data: `node dist/db/seed.js && node dist/db/seed-spom.js`
    - Start API: `cd el-templo-api && pnpm run dev`
    - Start Member App: `cd el-templo-app && pnpm run dev` (localhost:9000)
    - Start Admin App: `cd el-templo-admin && pnpm run dev` (localhost:9100)

    **6. Development Workflow:**
    - Pre-commit hooks: ESLint + Prettier run automatically on staged files
    - Running tests: `cd el-templo-api && pnpm test`
    - Building: `cd <project> && pnpm run build`
    - Linting: `cd <project> && pnpm run lint`

    **7. Project Structure:**
    ```
    el-templo/
    ├── el-templo-api/          # Backend API
    │   ├── src/
    │   │   ├── modules/        # Feature modules (auth, sessions, admin, progression)
    │   │   ├── db/             # Database schema, migrations, seeds
    │   │   ├── plugins/        # Fastify plugins (database, auth, spom, sessions)
    │   │   └── app.ts          # App factory (buildApp)
    │   └── test/               # Integration tests
    ├── el-templo-app/          # Member app
    │   └── src/
    │       ├── modules/        # Feature modules (training, progression)
    │       ├── boot/           # Quasar boot files (axios, auth, sentry)
    │       └── stores/         # Pinia stores
    ├── el-templo-admin/        # Admin app
    │   └── src/
    │       ├── pages/          # Admin pages (sessions, generation, editing)
    │       ├── components/     # Shared components
    │       └── utils/          # Utilities (PDF builder, API composables)
    └── deploy/                 # Deployment scripts
    ```

    **8. Deployment:**
    - Brief overview: GitHub Actions builds all 3 apps, deploys via rsync to EC2
    - Reference deploy/ directory for scripts and guides
    - Production domains

    **9. Contributing:**
    - Branch naming: feature/*, fix/*, refactor/*
    - Commit style: conventional commits (feat, fix, refactor, docs, test)
    - Pre-commit hooks handle formatting
    - All tests must pass
    - No new `any` types
    - No new console.log (use logger)

    Keep the README practical and concise (~150-200 lines). Focus on "how do I get this running" over exhaustive documentation. Read actual file paths and scripts from the codebase to ensure accuracy.
