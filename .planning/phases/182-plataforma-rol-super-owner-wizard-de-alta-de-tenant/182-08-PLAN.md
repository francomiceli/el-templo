<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| navegador (localStorage) → API | Dos tokens distintos conviviendo en el mismo origen |
| router de Vue → rutas de plataforma | Control de acceso aparente en el cliente |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-182-26 | Elevation of Privilege | Interceptor de axios compartido | mitigate | Instancia `platformApi` separada con su propia clave de storage; `boot/axios.ts` prohibido de tocar y verificado por `git diff --name-only`; grep de `adminAccessToken` == 0 en el archivo nuevo |
| T-182-27 | Denial of Service | 401 de plataforma disparando el refresh de tenant | mitigate | El 401 handler de `platformApi` limpia solo `platformAccessToken` y no tiene lógica de refresh (grep de `refresh` == 0) |
| T-182-28 | Elevation of Privilege | Guard del router tomado como control de acceso | accept | Es UX por diseño: el control real es `requirePlatformAuth` en el borde de la API (verificado en `iso-04`). Queda escrito en el comentario del guard |
| T-182-07b | Information Disclosure | Datos sensibles en localStorage | mitigate | Solo se guarda el token de plataforma; la contraseña del owner que devuelve el alta se maneja en estado del componente (plan 182-09), nunca en storage |
| T-182-SC | Tampering | Dependencias del admin | mitigate | Ningún `pnpm add` en el admin: se reutilizan Quasar, Pinia y axios ya instalados |
</threat_model>
