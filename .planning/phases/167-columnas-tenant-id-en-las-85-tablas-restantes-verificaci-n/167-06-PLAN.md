<interfaces>
Contrato que este plan publica (lo consume el plan 167-07 y, mas adelante, las fases 169-176):

De `el-templo-api/src/db/scripts/verify-tenant-backfill.ts`:

- `QueryFn` — tipo de funcion que recibe un string de SQL y devuelve un array de filas
  (`Record<string, unknown>`). Es la abstraccion que permite correr la MISMA verificacion desde el
  CLI (conexion `mysql2` propia) y desde la suite (`app.db.execute` con `sql.raw`). Sin ella habria
  dos implementaciones divergentes.
- `verifyTenantBackfill(query)` — no imprime ni sale del proceso: devuelve el reporte.
- El reporte incluye, como minimo: `database` (nombre de la base contra la que corrio),
  `ddlMissing` (tablas gym-owned sin columna, nullable, sin default 1 o sin FK),
  `exemptViolations` (tablas exentas que SI tienen la columna), `badRows` (por tabla, filas con
  `tenant_id` inexistente en `tenants`), `fkMismatches` (aristas de FK declaradas con tenant distinto
  entre hijo y padre), `logicalMismatches` (idem para las aristas M9), `anchorless` (tablas sin cadena
  a un ancla), `partials` (filas M4 sin ancla dentro de tablas que si tienen ancla), `warnings` y
  `discrepancies` (numero: suma de todo lo que es error, sin contar `anchorless` ni `partials`).
- `formatReport(report)` — salida legible para consola y para pegar en un SUMMARY.
- Bloque CLI al final del archivo, guardado por `require.main === module` (mismo patron que
  `run-migrations.ts`): abre conexion `mysql2` con la misma carga de env que el runner
  (`.env.production` si `NODE_ENV=production`, si no `.env.development`, mas `.env`), imprime el
  reporte y sale con **codigo 0 si no hay discrepancias**, **1 si las hay**, **2 ante error de
  conexion o de uso**.

En `package.json`, dentro de `scripts`: `db:verify-tenant` ejecutando
`tsx src/db/scripts/verify-tenant-backfill.ts`. En el servidor se corre la version compilada
(`node dist/db/scripts/verify-tenant-backfill.js`): `tsconfig` incluye `src/**/*`, asi que el build la
emite sin cambios de configuracion.
