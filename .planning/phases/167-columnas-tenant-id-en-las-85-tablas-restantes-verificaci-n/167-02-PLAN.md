**Patron SQL obligatorio por tabla (4 statements, en este orden).** Difiere a proposito de la
migracion 0191 de la fase 166: el review 166 (WR-01) encontro que `ADD COLUMN ... NULL` sin DEFAULT
deja una ventana de carrera durante el rolling deploy — un INSERT del binario viejo entre el backfill
y el `MODIFY` escribe `tenant_id = NULL` y hace fallar el `MODIFY` (strict mode) o la FK (non-strict).
Con el DEFAULT declarado desde el `ADD COLUMN`, los inserts concurrentes resuelven a 1 desde el
instante cero y la ventana desaparece:

1. `ALTER TABLE <t> ADD COLUMN tenant_id INT NULL DEFAULT 1;`
2. `UPDATE <t> SET tenant_id = 1 WHERE tenant_id IS NULL;`
3. `ALTER TABLE <t> MODIFY COLUMN tenant_id INT NOT NULL DEFAULT 1;`
4. `ALTER TABLE <t> ADD CONSTRAINT fk_<t>_tenant FOREIGN KEY (tenant_id) REFERENCES tenants(id);`

Notas duras del patron:

- **Sin clausula de posicionamiento** (`AFTER`/`FIRST`): la columna va al final de la tabla, que es
  la forma garantizada INSTANT en MySQL 8. El orden fisico no importa (Drizzle nunca hace `SELECT *`).
- El paso 2 **normalmente afecta 0 filas** y eso es CORRECTO: con INSTANT ADD COLUMN, MySQL 8 devuelve
  el default para las filas preexistentes. El UPDATE queda igual como red (replay, motores que no
  toman el camino instant) y guardado por `IS NULL` para que un replay manual sea un no-op.
- El `DEFAULT 1` **debe repetirse en el MODIFY**: MySQL lo pierde si no se declara (verificado en
  produccion en la 166).
- **Sin `ADD INDEX` explicito**: InnoDB crea automaticamente el indice de la FK con el nombre del
  constraint (`fk_<t>_tenant`). La normalizacion de indices y uniques compuestas es la fase 168
  (CON-02) — agregar aca un `idx_<t>_tenant_id` ademas obligaria a introducir el tercer argumento de
  `mysqlTable` en 20+ archivos que hoy no lo tienen, sin beneficio.
- Nombre de constraint: `fk_<nombre_de_tabla>_tenant`, sin abreviar. El mas largo de este grupo es
  `fk_subscription_schedule_changes_tenant` (40 chars, limite MySQL 64).
