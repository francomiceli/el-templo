    **1. payments.ts schema** (el-templo-api/src/db/schema/payments.ts):
    Create payments table following the subscriptions schema pattern:
    - Fields: id (int PK autoincrement), memberId (FK to users.id, notNull), subscriptionId (FK to subscriptions.id, nullable — for one-off payments), amount (int, notNull — whole pesos), paymentMethod (mysqlEnum "payment_method" with values "cash", "transfer", "card"), paymentDate (date mode "string", notNull), reference (varchar 255 nullable — receipt/transfer ID), notes (text nullable), recordedBy (FK to users.id, notNull — the admin who recorded it), voidedAt (timestamp nullable), voidedBy (int FK to users.id nullable), voidReason (text nullable), createdAt (timestamp defaultNow notNull)
    - Indexes: idx_payments_member_id on memberId, idx_payments_subscription_id on subscriptionId
    - Relations: one to users (memberId), one to users (recordedBy), one to subscriptions (subscriptionId)
    - IMPORTANT: Follow the mysqlEnum naming convention — the enum name becomes the SQL column name (use "payment_method" not "method")

    **2. Migration 0033** (el-templo-api/src/db/migrations/0033_payments.sql):
    DDL for payments table matching the schema exactly. Column names must match Drizzle enum names. Include FK constraints and indexes.

    **3. schema/index.ts**: Add barrel export for payments schema.

    **4. payments/types.ts**: Define all types:
    - `PaymentMethod = "cash" | "transfer" | "card"`
    - `PaymentListItem` — payment row with memberName, planName joined
    - `PaymentDetail` — same as list item (flat)
    - `RecordPaymentInput` — { memberId, subscriptionId?, amount, paymentMethod, paymentDate, reference?, notes? }
    - `VoidPaymentInput` — { reason: string }
    - `MemberBalance` — { subscriptionId, planName, pricePaid (total owed), totalPaid, remaining, isOverdue }
    - `PaymentListParams` — { branchId?, paymentMethod?, dateFrom?, dateTo?, search?, page, limit }
    - `FinancialSummary` — { monthlyRevenue, totalOutstanding, collectionRate, revenueByMethod: { cash, transfer, card }, revenueByBranch: Array<{ branchId, branchName, revenue }> }
    - `OverdueMember` — { userId, firstName, lastName, branchName, planName, amountOwed, amountPaid, amountDue }

    **5. payments/schemas.ts**: Fastify JSON validation schemas for all routes (following the subscriptions/schemas.ts pattern):
    - recordPaymentSchema, voidPaymentSchema, memberPaymentsSchema, memberBalanceSchema, globalPaymentsSchema, financialSummarySchema, morososCountSchema

    **6. payments/service.ts**: PaymentService class with constructor DI (db, log) following SubscriptionService pattern:
    - `recordPayment(input, recordedBy)` — insert payment row, return PaymentDetail
    - `voidPayment(paymentId, reason, voidedBy)` — set voidedAt/voidedBy/voidReason, return PaymentDetail. Error if already voided.
    - `getMemberPayments(memberId)` — list all payments for member ordered by paymentDate desc, join subscription plan name
    - `getMemberBalance(memberId)` — find active/most-recent subscription, compute totalOwed (subscription.pricePaid), totalPaid (SUM non-voided payments for that subscription), remaining = MAX(0, owed - paid), isOverdue = subscription.endDate < today AND remaining > 0
    - `listPayments(params: PaymentListParams)` — global paginated list with filters (branch via member's branchId, payment method, date range, search by member name), join member name and plan name, server-side pagination. Include voided payments (show status derived from voidedAt presence).
    - `getFinancialSummary(branchId?, dateFrom?, dateTo?)` — compute: monthly revenue (SUM non-voided payments in current month or date range), total outstanding (SUM remaining balances across all active subscriptions with overdue), collection rate (totalPaid / totalOwed * 100), revenue breakdown by payment method, revenue breakdown by branch
    - `getOverdueMembers(branchId?)` — list members whose active subscription is overdue (endDate < today AND payments < pricePaid)
    - `getMorososCount(branchId?)` — return count of overdue members
    - Use custom error classes: NotFoundError, BadRequestError (import from subscriptions or define locally — prefer defining locally for module independence)

    **7. payments/routes.ts**: FastifyPluginAsync with admin role guard (onRequest hook, same pattern as subscriptions/routes.ts):
    - POST `/members/:userId/payments` — record payment (recordedBy from request.user.userId)
    - POST `/payments/:paymentId/void` — void payment
    - GET `/members/:userId/payments` — member payment history
    - GET `/members/:userId/balance` — member balance (overdue info)
    - GET `/payments` — global paginated list with query params for filters
    - GET `/payments/summary` — financial summary with optional branchId, dateFrom, dateTo query params
    - GET `/payments/morosos` — morosos count with optional branchId
    - Map service errors to HTTP: NotFoundError -> 404, BadRequestError -> 400

    **8. payments/index.ts**: Barrel export — paymentRoutes, PaymentService, error classes, types.

    **9. app.ts**: Register paymentRoutes at prefix "/api/admin/payments".

    - members/types.ts: Add `isOverdue?: boolean` to MemberListItem. Add `overdue?: boolean` filter to MemberListParams.
    - members/service.ts: In listMembers, add a LEFT JOIN subquery or post-processing to compute overdue status per member. When `overdue` filter param is true, filter to only overdue members. The overdue check: member has an active subscription where endDate < CURDATE() AND SUM(non-voided payments) < subscription.pricePaid. Add approach: use a correlated subquery or a CTE. Simplest approach: LEFT JOIN a derived table that computes overdue per userId and add `isOverdue` to the select.
    - members/schemas.ts: Add `overdue` boolean query param to listMembersSchema.
    - members/routes.ts: Pass `overdue` filter to listMembers params.
