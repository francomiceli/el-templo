<objective>
Block A — Data population engine. Extend the existing `bootstrap-milestones.ts` CLI with a READ-ONLY `--dry-run` mode (D-01) that prints the full hito→variantes plan for user review (Front Lever witness case), and an `--apply` mode (D-02/D-03) that persists the heuristic by transactionally accepting all `pending` milestone proposals — reusing `TreeEditorService.acceptMilestoneReview` (the only path that writes `milestone_exercise_id`). Apply is idempotent (D-04): re-runs touch only `pending` proposals, leaving coach-corrected `accepted`/`rejected` rows intact.

Purpose: Today `milestone_exercise_id` is NULL on every exercise, so `backboneNodeConditions()` treats all ~70 exercises as hitos and the Front Lever route renders flat. Populating the column collapses the row. This plan builds the population mechanism (the prod migration that ships the result is Plan 02).
Output: Extended CLI with dry-run + apply, plus an integration test proving truth-write + idempotency.
</objective>
