    - `acquireLock(lockKey: string, ttlSeconds: number): Promise<boolean>` -- Uses `redis.set(lockKey, 'locked', 'EX', ttlSeconds, 'NX')` (SET with NX for atomic acquire). Returns true if lock acquired, false if already held. Import `redis` and `isRedisAvailable` from `../redis.js`. If Redis unavailable, log warning and return false (skip scheduler run gracefully).
    - `releaseLock(lockKey: string): Promise<void>` -- Uses `redis.del(lockKey)`. Swallow errors with logging.

    ```typescript
      templateName: string,
      languageCode: string,

    ): Promise<string>
    ```

    Add `TemplateComponent` type to `types.ts`:

    - POST to `https://graph.facebook.com/{version}/{phoneId}/messages`

    - Same auth/error pattern as existing `sendTextMessage`
    - Returns the wamid

    Note: Template messages must be pre-approved in Meta Business Manager. The bot sends them by name; the actual template text is configured in Meta's dashboard. This is standard WhatsApp Business API behavior.

    **class-reminder.ts:** Implement the class reminder scheduler. Replace the stub with a working implementation.

    Export `startClassReminderScheduler(db: MySql2Database<typeof schema>): void` following the same pattern as `el-templo-api/src/jobs/mark-no-shows.ts` (receives db, schedules cron).

    **Cron schedule:** Every 30 minutes (`*/30 * * * *`), timezone `America/Argentina/Buenos_Aires`.

    **Core logic -- export separately as `runClassReminder(db)` for testability:**

    1. Acquire distributed lock: `acquireLock('wa:lock:class-reminder', 120)` (2 min TTL). If not acquired, log and return.
    2. Query upcoming bookings: Use raw SQL via `db.execute(sql`...`)` (per project decision [67-02] -- raw SQL via drizzle sql template literals):
       - JOIN bookings + schedules + users + whatsapp_conversations
       - WHERE bookings.status = 'reservado'
       - AND bookings.booking_date = CURDATE() (today's classes only)
       - AND schedules.start_time is within the next REMINDER_HOURS_BEFORE hours (default 2, from env `CLASS_REMINDER_HOURS` or 2)
       - AND schedules.start_time is NOT in the past (compare with current Argentina time)
       - AND whatsapp_conversations.phone IS NOT NULL (need phone to send WhatsApp)
       - SELECT: booking.id, user.firstName, schedule.startTime, schedule.dayOfWeek, whatsapp_conversations.phone, activity name (join activities table)
    3. For each eligible booking:
       - Check Redis key `wa:reminder:class:{bookingId}` -- if exists, skip (already reminded)
       - Call `sendTemplateMessage(phone, 'class_reminder', 'es_AR', [{ type: 'body', parameters: [{ type: 'text', text: firstName }, { type: 'text', text: className }, { type: 'text', text: startTime }] }])`
       - On success: Set Redis key `wa:reminder:class:{bookingId}` with 24h TTL (prevents re-send)
       - On failure: Log error, continue to next booking (don't fail the whole batch)
    4. Release lock: `releaseLock('wa:lock:class-reminder')`
    5. Log summary: `{ total: N, sent: M, skipped: S, failed: F }`

    Use pino logger (`pino({ name: 'scheduler:class-reminder' })`). Wrap entire function in try/finally to always release lock.

    **test/class-reminder.test.ts:** Unit tests with vitest mocks (same pattern as test/action-tools.test.ts):

    - Mock `../src/redis.js` (redis.get, redis.set)
    - Mock `../src/db.js` (db.execute returns test rows)

    Test cases:
    1. Lock not acquired -- runClassReminder returns early, no messages sent
    2. No upcoming bookings -- runs but sends 0 messages

    4. One booking found, already reminded (Redis key exists) -- skips
    5. sendTemplateMessage fails for one booking -- logs error, continues, lock released
    6. Lock always released even on query error (try/finally)
