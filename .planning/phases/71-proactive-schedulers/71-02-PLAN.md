  <action>
    **trial-followup.ts:** Replace the stub with a working implementation.

    Export `startTrialFollowupScheduler(db: MySql2Database<typeof schema>): void` -- same pattern as class-reminder.

    **Cron schedule:** Every 60 minutes (`0 * * * *`), timezone `America/Argentina/Buenos_Aires`. Only run between 10:00-20:00 Argentina time (check hour inside the handler, return early if outside window -- don't send follow-ups at 3am).

    **Core logic -- export separately as `runTrialFollowup(db)` for testability:**

    1. Acquire distributed lock: `acquireLock('wa:lock:trial-followup', 120)` (2 min TTL). If not acquired, return.
    2. Query eligible trial attendees: Use raw SQL via `db.execute(sql`...`)`:
       - JOIN attendance + users + subscriptions + whatsapp_conversations
       - WHERE users.role = 'member'
       - AND subscriptions.status = 'active' AND subscription_plans.name LIKE '%prueba%' OR subscription_plans.planType = 'trial' (identify trial subscriptions -- check schema for how trial plans are distinguished. If no planType field, use the subscription created by bot with pricePaid = 0 and priceTypeApplied = 'zero' per decision [70-01])
       - AND attendance.checked_in_at BETWEEN NOW() - INTERVAL 48 HOUR AND NOW() - INTERVAL 24 HOUR (attended 24-48h ago)
       - AND whatsapp_conversations.phone IS NOT NULL
       - AND subscriptions.status != converted to regular active (check that user does NOT have a non-trial active subscription)
       - SELECT: user.id, user.firstName, whatsapp_conversations.phone, attendance.checked_in_at
    3. For each eligible attendee:
       - Check Redis key `wa:followup:trial:{userId}` -- if exists, skip (already followed up)
       - Call `sendTemplateMessage(phone, 'trial_followup', 'es_AR', [{ type: 'body', parameters: [{ type: 'text', text: firstName }] }])`
       - On success: Set Redis key `wa:followup:trial:{userId}` with 7 day TTL (don't follow up same person again within a week)
       - On failure: Log error, continue
    4. Release lock (try/finally).
    5. Log summary.

    **Alternative simpler query approach** (if the trial subscription detection is complex): Since bot-created trial users have `pricePaid: 0` and `priceTypeApplied: 'zero'` per [70-01], query:
    - Users with a subscription where pricePaid = 0 AND priceTypeApplied = 'zero'
    - Who have attendance records 24-48h ago
    - Who have a whatsapp_conversations record (phone available)
    - Who do NOT have another subscription with pricePaid > 0 (not yet converted)

    Use pino logger (`pino({ name: 'scheduler:trial-followup' })`). No `any` types. `catch (err: unknown)`.

    **test/trial-followup.test.ts:** Unit tests with vitest mocks (same pattern as class-reminder tests):

    Test cases:
    1. Lock not acquired -- returns early
    2. Outside business hours (3am) -- returns early without querying
    3. No eligible trial attendees -- runs but sends 0 messages
    4. One eligible attendee, not yet followed up -- sends template, sets Redis key with 7d TTL
    5. One eligible attendee, already followed up (Redis key exists) -- skips
    6. Attendee already converted to paid membership -- not included in results (query filter)
    7. sendTemplateMessage fails -- logs error, continues, lock released
