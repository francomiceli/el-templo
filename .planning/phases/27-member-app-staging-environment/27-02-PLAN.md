<task type="auto">
  <name>Task 1: Create staging deployment workflow</name>
  <files>.github/workflows/deploy-staging.yml</files>
  <action>
    Create `.github/workflows/deploy-staging.yml` by adapting the existing `deploy.yml` for the staging environment.

    Key differences from production deploy.yml:

    **Trigger:**
    - Push to `staging` branch (not master/main)
    - Also support `workflow_dispatch` for manual triggers

    **Build jobs (build-api, build-app, build-admin):**
    - Same structure as production builds
    - build-app and build-admin use staging VITE env vars:
      - `VITE_API_URL: ${{ secrets.STAGING_VITE_API_URL }}` (should be https://api-staging.eltemplo.org/api)
      - `VITE_APP_NAME: "El Templo (Staging)"` (per user decision: different app name for device coexistence)
      - `VITE_SENTRY_DSN: ${{ secrets.STAGING_VITE_SENTRY_DSN }}` (separate Sentry project)
    - build-api uses same test database for tests (eltemplo_test, same as production CI)

    **Deploy job:**
    - Change condition to check `refs/heads/staging` instead of `refs/heads/master`
    - All secret references use STAGING_ prefix:
      - `STAGING_API_DEPLOY_PATH` (should be /opt/el-templo-staging/api)
      - `STAGING_APP_DEPLOY_PATH` (should be /opt/el-templo-staging/app)
      - `STAGING_ADMIN_DEPLOY_PATH` (should be /opt/el-templo-staging/admin)
      - Same `SSH_PRIVATE_KEY`, `SERVER_HOST`, `SSH_USER` (same server)
    - `.env.production` creation step uses staging secrets:
      ```
      NODE_ENV=production
      PORT=${{ secrets.STAGING_API_PORT }}     (should be 4001)
      DB_HOST=${{ secrets.STAGING_DB_HOST }}
      DB_PORT=${{ secrets.STAGING_DB_PORT }}
      DB_USER=${{ secrets.STAGING_DB_USER }}
      DB_PASSWORD=${{ secrets.STAGING_DB_PASSWORD }}
      DB_NAME=${{ secrets.STAGING_DB_NAME }}   (should be eltemplo_staging)
      JWT_SECRET=${{ secrets.STAGING_JWT_SECRET }}
      JWT_EXPIRES_IN=7d
      FRONTEND_URL=${{ secrets.STAGING_FRONTEND_URL }}
      ADMIN_URL=${{ secrets.STAGING_ADMIN_URL }}
      SENTRY_DSN=${{ secrets.STAGING_SENTRY_DSN }}
      STAGING_SEED_PASSWORD=${{ secrets.STAGING_SEED_PASSWORD }}
      ```
    - PM2 process name: `eltemplo-staging-api` (not eltemplo-api)
      - Restart command: `pm2 restart eltemplo-staging-api --update-env || pm2 start dist/index.js --name eltemplo-staging-api`
      - Per research recommendation: use direct pm2 start in deploy workflow (Option B), not ecosystem file
    - Smoke test: Use `STAGING_VITE_API_URL` to derive the health endpoint (same pattern as production)
    - Rollback: restore staging paths and restart `eltemplo-staging-api` PM2 process
    - Backup: same .previous pattern but with staging paths

    **Copy migration SQL files step** (same as production):
    - `cp -r src/db/migrations dist/db/` in build-api

    **Deploy Admin artifact path:**
    - Use `el-templo-admin/dist/spa` as the source path (same as production)

    **Important: Do NOT include change detection (detect-changes job)** for staging. Always build and deploy all 3 apps on every staging push. Staging deploys are less frequent and should always be complete to avoid stale frontend/backend mismatches. This simplifies the workflow significantly.

    The workflow name should be "Deploy Staging".

  </action>

    - All environment-specific values use STAGING_ prefixed secrets

    - .env.production uses STAGING_ secrets (STAGING_DB_NAME, STAGING_JWT_SECRET, etc.)
    - Smoke test hits staging API health endpoint
    - Rollback restores staging paths
    - VITE_APP_NAME is "El Templo (Staging)"
  </verify>
