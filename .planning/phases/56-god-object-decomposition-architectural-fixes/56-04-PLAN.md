Fix two architectural anti-patterns: composable-inside-computed (frontend) and new-inside-constructor (API).

Purpose: Composables called inside `computed()` create new reactive instances on every recomputation, leaking watchers and stores. Services that `new` their dependencies inside constructors can't be tested in isolation and create hidden coupling.

Output: Fixed player pages + DI-ready service constructors.
</objective>

**The anti-pattern (both files):**
```typescript
const player = computed(() => {
  if (!session.value) return null
  return useSessionPlayer(session.value) // BUG: creates new composable on every recompute
})
```

Composables (useSessionPlayer, useJourneySession) call `useSessionPlayerStore()` internally, which is a Pinia store composable. Calling composables inside `computed()` means every time the computed re-evaluates, a new store connection + reactive state is created, leaking the previous one.

**The fix pattern — use `shallowRef` + `watch`:**

For DayPlayer.vue (around line 146):

```typescript
import { shallowRef, watch } from "vue";

// Replace the computed with:
const player = shallowRef<ReturnType<typeof useSessionPlayer> | null>(null);

watch(
  session,
  (newSession) => {
    if (newSession) {
      player.value = useSessionPlayer(newSession);
    } else {
      player.value = null;
    }
  },
  { immediate: true },
);
```

For JourneySession.vue (around line 167):

```typescript
import { shallowRef, watch } from "vue";

// Replace the computed with:
const player = shallowRef<ReturnType<typeof useJourneySession> | null>(null);

watch(
  [() => session.value, () => selectedDuration.value] as const,
  ([newSession, newDuration]) => {
    if (newSession && newDuration) {
      player.value = useJourneySession(newSession, newDuration);
    } else {
      player.value = null;
    }
  },
  { immediate: true },
);
```

**Why shallowRef:** The composable returns an object with nested refs. `shallowRef` avoids deeply unwrapping the composable's reactive internals, which would break reactivity.

**Access pattern stays the same:** `player.value?.someMethod()` and `player.value?.someRef.value` work identically. Template access: `player?.someRef.value` (with optional chaining already used throughout both files).

Check all template and script usages of `player` in both files to ensure `.value` access is correct after the change. In templates, `player` was previously a computed (auto-unwrapped) — now it's a `shallowRef` which also auto-unwraps in templates, so `player?.currentBlock` still works the same way.
