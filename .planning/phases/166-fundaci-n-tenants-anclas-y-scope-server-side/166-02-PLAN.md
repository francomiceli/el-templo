Contrato que este plan publica (lo consumen los planes 166-03 y 166-04):

- `schema.users.tenantId` — columna fisica `tenant_id`, `int notNull default 1`,
  `references(() => tenants.id)`. Por el `.default(1)` de Drizzle, `tenantId` queda OPCIONAL en
  el tipo de insert -> `createStaffUser` y todos los inserts existentes siguen compilando.
- `schema.branches.tenantId` — identico, sobre `branches`.
- Indices: `idx_users_tenant_id`, `idx_branches_tenant_id`.
- Constraints SQL (el plan 166-03 los asserta por INFORMATION_SCHEMA): `fk_users_tenant`,
  `fk_branches_tenant`.

**Decision explicita (hallazgo bloqueante del PATTERNS §0.3 — camino A):** la columna es
`NOT NULL DEFAULT 1`, no `NOT NULL` a secas. Razon dura, no estetica: `test/setup.ts:38-61`
inserta branches y users con `INSERT IGNORE` sin `tenant_id` (sin DEFAULT esas filas NO se
insertan y se convierte en cascada de fallos cripticos en toda la suite), y el rolling deploy
corre codigo viejo que tampoco manda `tenant_id` (D-04 exige compatibilidad). Precedente de
NOT NULL con DEFAULT en las mismas anclas: `branches.country` y `branches.timezone`.
El DEFAULT se evalua para remocion cuando exista un tenant 2, fuera de v6.0.
