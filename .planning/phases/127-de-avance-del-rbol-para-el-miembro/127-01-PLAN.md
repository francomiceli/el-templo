<objective>
Build the backend that exposes a member's skill-tree progress: a new authenticated, member-scoped GET endpoint that returns the tree nested as category → subfamily → nodes, with a % reached at every level, all computed server-side (D-05). The tree structure is read from the phase-126 DAG (D-04); the % is computed from already-known progress — the member's `users.level` plus their completed sessions (D-03). Grouping is by the 5 coarse thematic categories derived in-code from `exercises.pattern` (D-01); static/dynamic is NOT a grouping axis (D-02).

Purpose: TREE-06 — the member can see their % of tree advancement per family/node, grouped by Tracción/Empuje/Piernas/Core/Movilidad. This is the honest first cut over existing data; phase 131's "dominado" registry will later enrich the `reached` definition without rewriting the view.

Output: A `tree-progress` API module (category map + service + schema + route + plugin) wired into the app, with an integration test in CI.
</objective>

Schema columns (already in _.ts, import via `import _ as schema from "../../db/schema"`):

- exercises: id, pattern, category, exercise (name), effort, level, difficulty, dificultadLineal, route, subfamilyId, canonicalExerciseId, routePending.
- exerciseSubfamilies: id, route, name, sortOrder.
- exerciseProgressions: id, fromExerciseId, toExerciseId, source ('auto'|'manual').
- users: id, level (enum alfa|delta|sigma|omega|spartan).
- completedSessions: id, userId, exercisesCompleted (json, nullable: maps block role → array of prescription ids — NOT exercise ids; see note in service task).

126 DAG node scope (the authoritative definition of "what nodes exist", from rebuild-progression-graph.ts):

- A node participates in the graph iff `subfamily_id IS NOT NULL AND canonical_exercise_id IS NULL AND effort IN ('CON','EXC','ISO')`.
- Partitions are `(subfamily_id × effort)`; edges are consecutive-by-dificultad_lineal within a partition. The tree's nodes = those confirmed canonical exercises; subfamilies = exercise_subfamilies rows that own ≥1 node.

Level → dificultadLineal ceiling (from src/modules/sessions/pipeline/utils/level-mapping.ts; reuse, do not redefine):

- LEVEL_LINEAR_MIN = { alfa:1, delta:4, sigma:7, omega:9, spartan:11 }.
- A level's _ceiling_ (max dl the member has reached) = the LEVEL_LINEAR_MIN of the NEXT level minus 1, with spartan = 12 (the dl scale max). I.e. alfa→3, delta→6, sigma→8, omega→10, spartan→12.
