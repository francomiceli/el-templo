<decisions>
Rigen DA-44 y DA-46 (`201-36-PLAN.md`). Para este plan:
- `resolveCorrectionVideo(fastify, key: string | null, info: { correctionId: number })` → `{ available: boolean; url: string |
  null; expiresIn: number | null }`. Clave NULL → `{ available: false, url: null, expiresIn: null }` SIN tocar storage. Con clave:
  storage (503 `CONQUER_VIDEOS_NO_DISPONIBLES` si no hay bucket) → `head(key)` (con `callVideoStore`) → `null` →
  `available: false` → si no, `presignGet(key, PRIVATE_GET_EXPIRES_SEC)` (ya lleva `ResponseCacheControl: "no-store"`). Lo
  reusan las rutas del coach (201-40).
- Orden de `GET .../:id/video-url`: no activo (409 `CONQUER_NO_ACTIVO`) → corrección propia en el gimnasio (404 "Corrección no
  encontrada"; la de otro alumno o gimnasio es indistinguible de una inexistente) → `who` (400 `CONQUER_VIDEO_QUIEN_INVALIDO` si
  no es `alumno` ni `coach`, validado en el servicio) → `resolveCorrectionVideo` con `video_key` o `reply_video_key`.
- `POST /corrections/seen` (sin body, como `skipDay0Schema`): no activo → 409; UPDATE `reply_seen_at = NOW()` con `tenantWhere`
  inline + `userId` + `status = "respondida"` + `isNull(replySeenAt)`. Idempotente. Devuelve `{ unseenReplies: 0 }`.
- `correctionCounts(db, ctx, userId)` → `{ pending, unseenReplies }` con UNA query (`SUM(CASE ...)` o dos `count` en un select).
  `member.corrections` va en `GET /state` (y en `POST /unlock-request`, que usa el mismo schema) SOLO si el alumno está
  `activo`, igual que `member.bodyCheck` (leer cómo se resuelve en `getConquerState`); el schema lo declara como propiedad.
</decisions>
