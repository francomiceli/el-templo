    **check_schedule(db, args):**
    - Uses raw SQL (same pattern as handler.ts -- `sql` template literals to avoid cross-package type conflicts)
    - Query: SELECT from schedules JOIN activities JOIN branches WHERE is_active=true
    - Filter by branchId if provided, filter by dayOfWeek if provided (note: schema uses ISO 1=Monday..6=Saturday)
    - For each schedule, count bookings for today's date (or the requested day) with status != 'cancelado' to calculate spots remaining (branch.maxCapacity - active bookings count)
    - Return formatted string with class name, day, time range, and spots available
    - Limit to first 5 results, append "hay X clases mas disponibles" if more exist

    **check_membership(db, args):**
    - Query: Look up user by phone number in users table, then find their active/paused subscription via subscriptions table JOIN subscription_plans
    - If no user found: return "No encontre una cuenta con ese numero. Si sos miembro, puede que estes registrado con otro numero."

    **get_location(db, args):**
    - Query branches table for active branches
    - If branchName provided, filter with LIKE match (case-insensitive)

  <action>
    Replace the echo reply logic in handleInboundMessage with AI-powered message processing.

    **Changes to handleInboundMessage:**

    1. After saving the inbound message (keep existing dedup and conversation management logic unchanged), check conversation status:
       - Query conversation status. If `human_takeover`, log and return early -- bot does not respond during human takeover.

    2. Build message history for AI context:
       - Query last 10 messages from whatsapp_messages for this conversation (ordered by created_at DESC, then reverse for chronological order)
       - Map to ChatMessage[] format: inbound -> "user" role, outbound_bot -> "assistant" role, outbound_human -> skip (or "assistant")
       - Prepend system message from getSystemPrompt()

    3. Call AI provider with tool loop:
       - `const provider = createAiProvider()`
       - Filter BOT_TOOLS to only info tools (check_schedule, check_membership, get_location, request_human)
       - Call `provider.chat(messages, BOT_TOOLS)`
       - **Tool call loop** (max 5 iterations to prevent runaway):
         - If response has toolCalls: for each tool call, execute via `executeTool(name, args, db, conversationId)`
         - Append assistant message with tool calls to messages array
         - Append tool result messages to messages array
         - Call provider.chat() again with updated messages
         - Repeat until response has content (text) and no tool calls, or max iterations reached
       - If max iterations reached without text response, use fallback: "Disculpa, no pude procesar tu consulta. Intenta de nuevo o escribi 'hablar con alguien' para que te ayude una persona."

    4. Send AI response as WhatsApp messages:
       - Split response into multiple messages if longer than ~800 chars. Split on double newlines ("\n\n") first, then on single newlines if segments are still too long. This creates the conversational multi-message feel specified in CONTEXT.md.
       - For each message segment: call sendTextMessage() and save outbound message to DB
       - If request_human tool was called during the loop, do NOT send any additional text after the handoff message

    5. Save all outbound messages to DB (same pattern as echo -- INSERT into whatsapp_messages with direction='outbound_bot')

    **Keep existing patterns:**
    - Raw SQL via `sql` template literals
    - FastifyBaseLogger parameter
    - Same function signature (db, log, message)
    - Best-effort reply (try/catch around send, log errors)

    **Do NOT:**
    - Import or use Redis (Phase 69 scope)
    - Implement conversation memory beyond the last 10 messages query
    - Add book_class or register_trial tool support (Phase 70)
