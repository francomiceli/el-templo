```typescript
import cron from "node-cron";
import pino from "pino";

```

Export function `startNotificationJobs(db: MySql2Database<typeof schema>)` that schedules these cron jobs:

**1. Queue Processor — every 15 minutes (per D-10):**

```
cron.schedule('*/15 * * * *', async () => { ... })
```

- Create NotificationService instance with db and log
- Call `service.processQueue()`
- Log result: `{ sent, failed }`
- After processing, call `service.purgeOldNotifications()` and log deleted count
- Wrap in try/catch, log errors

**2. Batch Segment Recalculation — daily at 03:00 Argentina time (per D-09):**

```
cron.schedule('0 3 * * *', async () => { ... }, { timezone: 'America/Argentina/Buenos_Aires' })
```

- Create SegmentationService and NotificationService
- Query ALL member_profiles rows: select userId, current segment
- For each member, call segmentationService.calculateAndUpdate(userId)
- Compare old segment vs new segment. If changed, determine transition and queue notification:
  - Any -> 'en_riesgo': queue 'segment_transition_en_riesgo'
  - 'en_riesgo' -> 'ghost': queue 'segment_transition_ghost'
  - ('en_riesgo' | 'ghost') -> ('intermitente' | 'espartano'): queue 'segment_transition_recovery'
  - Any -> 'espartano' (when old != 'espartano'): queue 'segment_transition_espartano'
- Use SEGMENT_TRANSITION_TEMPLATES from types.ts to look up the templateKey
- For Ghost monthly re-attempt (per D-04): if member is already ghost AND was ghost before (no transition), check:
  - ghostReattemptCount < 3
  - lastGhostReattemptAt is null OR lastGhostReattemptAt was 30+ days ago
  - If eligible: queue 'ghost_monthly_reattempt', increment ghostReattemptCount and update lastGhostReattemptAt on member_profiles
- Log summary: total members processed, transitions found, notifications queued
- Important: bypass the 1-hour cooldown on calculateAndUpdate for the batch job. Either call `calculateSegment` directly (public method) and do the update manually, or add a `force` parameter to `calculateAndUpdate`. Use `calculateSegment` + manual update to avoid modifying the service API.

**3. Morning Energy Reminder — daily at 08:00 Argentina time (per D-05):**

```
cron.schedule('0 8 * * *', async () => { ... }, { timezone: 'America/Argentina/Buenos_Aires' })
```

- Create NotificationService
- Query: find all member_profiles userIds WHERE onboardingCompletedAt IS NOT NULL (only onboarded members)
- For each userId, check if they already have a check_in_responses row for today with questionType='energy'
  - Query: SELECT 1 FROM check_in_responses WHERE userId=X AND questionType='energy' AND DATE(answeredAt) = CURDATE()
- If no response today, queue notification with templateKey='morning_energy' and scheduledAt=now
- Performance: do a single query to get all userIds who HAVEN'T answered today's energy check-in:
  ```sql
  SELECT mp.user_id FROM member_profiles mp
  WHERE mp.onboarding_completed_at IS NOT NULL
  AND mp.user_id NOT IN (
    SELECT cr.user_id FROM check_in_responses cr
    WHERE cr.question_type = 'energy' AND DATE(cr.answered_at) = CURDATE()
  )
  ```
- Log: count of reminders queued

**4. Weekly Summary — Saturday at 15:00 Argentina time (per D-07):**

```
cron.schedule('0 15 * * 6', async () => { ... }, { timezone: 'America/Argentina/Buenos_Aires' })
```

- Saturday = day 6 in cron
- Create NotificationService
- Query all member_profiles with onboardingCompletedAt IS NOT NULL
- For each, queue 'weekly_summary' notification
- Log count queued
