## Implementation Decisions

### Scope expansion — RLOK-04 added inside Phase 92 (not Phase 89.1)

- **Decision:** Add a new requirement `RLOK-04: $80k SALES_TECHNIQUES rhetorical example rewritten to non-numeric language; KFIX-02's "zero plan prices in PB1.E1A render" success criterion now empirically held under live conditions.`
- **Rejected alternatives:**
  - Phase 89.1 gap-closure for KFIX-02 — disproportionate ceremony for a ~50-char rewrite.
  - Pre-condition Task 0 inside Phase 92 with no requirement ID — loses traceability ("why was the price-anchoring example rewritten?" becomes a commit-archaeology question 3 months later).
- **Audit trail line:** "Post-Phase-91 live test (`contexto/post-phase-91-live-test-findings.md`) proved the model treats `$80,000` rhetorical examples in SALES_TECHNIQUES as factual plan pricing, violating the empirical intent of KFIX-02. RLOK-04 closes that gap."
- **Consequence:** Phase 92 is no longer a "test-only" phase — it ships one source change (the SALES_TECHNIQUES rewrite). This is more honest than pretending RLOK-03 is a no-op live confirmation.

### Authoritativeness — Phase 92 adds a new behavioural integration layer

- **Phase 89/90/91 in-phase tests stay as-is.** They cover source-state contracts (regex matrices, advance-guard scope, state-field rollout, signal correctness). Phase 92 does NOT touch them.
- **Phase 92 RLOK-01 adds a strictly new layer**: behavioural integration assertions on **observable outcomes**. Examples (planner derives the full list):
  - `KFIX-02`: rendered PB1.E1A lead prompt contains zero membership plan price numbers (regex over the assembled prompt string after RLOK-04 ships).
  - `KGATE-05` dual-threshold: assert raw byte caps (per Phase 89/90 precedent) — both ≥20% rendered AND ≥35% knowledge block must hold for the PB1.E1A baseline render.
  - Snapshot byte-count: `pb1-e1a-lead-rendered.snap.txt` matches the new post-RLOK-04 baseline (regenerated once in Phase 92, then locked).
  - `OBJN-01`: rejection-arc behavioural contract — softRejection=true on `"no me interesa"` produces a rendered prompt carrying `SOFT_REJECTION_WHY_RULE`; subsequent rejection-with-whyAsked produces `SOFT_REJECTION_BACKOFF_RULE`.
  - `KFIX-01..04`, `STAGE-01..02`: each gets at least one behavioural assertion mapped to its empirical promise (the planner produces the full requirement-ID → assertion table).
- **Rejected alternatives:**
  - Re-implement / consolidate all KFIX/STAGE/OBJN tests into Phase 92 — breaks the in-phase test idiom established across 3 phases, creates churn, makes regression isolation harder.
  - "RLOK-01 is a meta checklist pointing at existing tests" — paper exercise; authoritative locks must be executable code, not a document that rots when line numbers shift.

### Test file organization — single dedicated file

- **File:** `el-templo-bot/test/v5-3-2-regression.test.ts`
- **Structure:** one top-level `describe()` per requirement ID — `describe("RLOK-01: KFIX-01 behavioural lock", …)`, `describe("RLOK-01: KFIX-02 behavioural lock (post-RLOK-04)", …)`, `describe("RLOK-01: STAGE-01 behavioural lock", …)`, `describe("RLOK-02: full suite + snapshot", …)`, `describe("RLOK-03: live-test gates (referenced from SUMMARY)", …)`, `describe("RLOK-04: $80k removed from SALES_TECHNIQUES render", …)`, etc.
- **Discoverability contract:** `grep -l "v5-3-2" el-templo-bot/test/` answers "is the milestone locked?" in one command. Future v5.4 milestone follows the same naming convention (`v5-4-regression.test.ts`).
- **Rejected alternatives:**
  - Append to most-relevant existing file per fix — scatters the v5.3.2 lock; loses the one-grep property.
  - Dedicated file + cross-reference comments in existing files — comment maintenance overhead, rot risk.

### Live-test methodology — Claude scripts; user copy-pastes; transcript captured

- **Process:** Phase 92 plan includes a 5–10 turn script of EXACT user-side messages covering all four failure paths (price-during-discovery, method question, discovery rejection, Boarding Pass explanation). User copy-pastes each into real WhatsApp (prod or staging — user's call), captures Mica's responses, pastes back into the conversation with Claude. Claude annotates pass/fail per success criterion (one criterion per path) and folds the transcript into SUMMARY.md.
- **Why scripted:** This is the methodology the previous three live tests effectively used (post-Phase-89, post-Phase-90, post-Phase-91 — see `contexto/post-phase-*-live-test-findings.md`). It worked: each found real bugs. Deterministic re-run, scriptable, transcript becomes the audit artifact.
- **Improvisation:** happens naturally when something catches the user's attention — the $80k leak was found via an improvised follow-up to the price defer, NOT a scripted turn. The plan should not try to script that.
- **Surface:** user picks WhatsApp prod or staging at run time. Plan does not lock the surface.
- **Rejected alternatives:**
  - Pure improvisation from a checklist — harder to reproduce, ambiguous pass/fail.
  - Hybrid scripted-core + improvised-tail per path — over-engineered for the gain.

### Failure handling — retry up to 3 times before declaring failure

- **Trigger:** any single live-test path (one of the four) fails its success criterion.
- **Process:**
  1. **First failure** → Claude diagnoses likely cause: regex miss / prompt wording issue / signal didn't fire / **model variance**.
  2. **If model variance** (prompt is correct, signal/wiring is correct, but model chose to ignore the rule on this run — e.g. tuteo drift, occasional rule-ignoring): retry the same path verbatim. No code change.
  3. **If real bug** (prompt missing constraint, signal regex too tight, state didn't persist, etc.): apply a single targeted fix, regenerate snapshot if needed, retry the same path.
  4. **After 3 consecutive failures on the same path** (model variance ruled out, fixes attempted): open Phase 92.1 gap-closure with the specific RLOK-03 sub-failure as the new requirement. Phase 92 itself is marked `gaps_found` in VERIFICATION.md, findings written to `contexto/post-phase-92-live-test-findings.md`.
- **Rejected alternatives:**
  - Open Phase 92.1 on the FIRST failure — disproportionate; gpt-4o-mini has documented variance (e.g. tuteo drift). One bad run ≠ a real bug.
  - Document and move on — violates RLOK-03 success criterion ("confirms the four success criteria from the milestone brief are met in practice, not just in assertions").
- **Diagnosis heuristic:** the elevator-pitch issue (Problem 3 from earlier findings) is the canonical example of "prompt is correct, model ignores it" — that class of failure is NOT fixable by Phase 92 gap-closure ceremony, it needs a framing rule (already in the post-Phase-92 backlog). Recognising this distinction is the failure handler's job.

### Claude's Discretion (planner-level tactical decisions)

- **Transcript location:** inline in SUMMARY.md (established pattern from previous three live tests).
- **KGATE-05 assertion shape:** assert raw byte caps (per Phase 89/90 precedent), not floating-point percentages.
- **Snapshot regen commit strategy:** single atomic commit (RLOK-04 SALES_TECHNIQUES rewrite + snapshot regen + assertion update), same pattern as Phase 89's KFIX-01 regen commit.
- **Requirement-ID → behavioural-assertion mapping table:** that's literally what `91-01-PLAN.md`-style task action blocks produce — planner generates the full table.
- **Exact wording of the new SALES_TECHNIQUES sentence** (replacing `$80,000`): planner picks within constraint "non-numeric, preserves the price-anchoring sales-technique guidance, doesn't introduce a new place-holder string the model could parse as data" (e.g. avoid `$XX.XXX`, use prose like `"desde el plan más accesible"`).
- **Assertion file order within `v5-3-2-regression.test.ts`**: planner orders by requirement ID for grep predictability.
