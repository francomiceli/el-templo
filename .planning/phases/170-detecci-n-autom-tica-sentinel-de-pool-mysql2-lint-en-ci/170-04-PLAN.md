Comportamiento VERIFICADO de drizzle-orm 0.45.1 + mysql2 3.16.1 (RESEARCH, prueba ejecutada
con un pool instrumentado):

  fuera de transaccion:   POOL.query          select ... from `users` where ...
  dentro de transaccion:  POOL.getConnection
                          CONN.query          begin
                          CONN.query          select ...
                          CONN.query          insert into ...
                          CONN.query          commit
                          CONN.release

  - Drizzle llama query() con un OBJETO { sql, typeCast, rowsAsArray? } como primer
    argumento, y execute() con un string. Hay que normalizar las dos formas.
  - MySql2Session.transaction() hace new MySql2Session(await this.client.getConnection(), ...):
    a partir de ahi pool.query NO se llama nunca mas. 65 call sites de .transaction( en
    25 archivos dependen de que getConnection este envuelto.
  - fastify.decorate("dbPool", pool) y 18 sitios de test hacen app.dbPool.getConnection()
    sobre esta MISMA instancia: por eso el wrap es monkeypatch de propiedades propias y NO
    un Proxy (el Proxy cambia la identidad del objeto).
  - El pool REUSA los objetos PoolConnection: envolver en cada getConnection() sin marca
    apila wrappers sobre la misma conexion.
