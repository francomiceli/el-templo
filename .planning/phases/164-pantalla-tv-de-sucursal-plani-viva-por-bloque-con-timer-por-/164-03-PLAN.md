<interfaces>
Rutas que este plan publica (los planes 09 y 11 las consumen):

Device (sin JWT, prefijo `/api/tv`):
POST /api/tv/pair/start -> 201 { userCode, deviceCode }
GET /api/tv/pair/status?deviceCode=xxx
-> 200 { status: "pending" }
-> 200 { status: "paired", deviceToken, branchName } (una sola vez)
-> 200 { status: "consumed" } (device ya emitido)
-> 404 { status: "unknown" } (device_code inexistente)

Staff (JWT + TV_CONTROL_ROLES, prefijo `/api/admin/tv`):
POST /api/admin/tv/pair/claim body { userCode, branchId, name? } -> 200 { ok: true, branchId }
409 si el user_code ya fue reclamado - 404 si no existe
GET /api/admin/tv/devices?branchId=NN
-> 200 { devices: [{ id, name, branchId, branchName, isActive, lastSeenAt, createdAt }] }
POST /api/admin/tv/devices/:id/revoke -> 200 { ok: true }

Header del TV en las rutas autenticadas por dispositivo: `Authorization: Device <token>`
`request.tvDevice = { id, branchId }` (declaration merging sobre FastifyRequest).
</interfaces>

  <action>
    `pairing.ts` — clase `TvPairingService(db, log)` con:
    - `start(): Promise<{ userCode: string; deviceCode: string }>`: genera `userCode` de 6 chars con
      **CSPRNG** (`randomInt` de `node:crypto`, NUNCA `Math.random()`) sobre el alfabeto
      `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, reintentando ante colision del UNIQUE (max 5 intentos);
      genera `deviceCode` con `randomBytes(32).toString("base64url")`; inserta en `tv_pairings`
      guardando `device_code_hash = sha256(deviceCode)`. Devuelve ambos en claro UNA sola vez.
      El `deviceCode` NUNCA se loguea ni se muestra en pantalla.
    - `claim(userCode, branchId, claimedBy, name?): Promise<void>`: un UNICO
      `UPDATE tv_pairings SET claimed_at = NOW(), claimed_by = ?, branch_id = ?, device_name = ?
      WHERE user_code = ? AND claimed_at IS NULL` y chequeo de `affectedRows`. Si es 0: distinguir
      404 (no existe el code) de 409 (ya reclamado) con un SELECT posterior solo para el mensaje.
      Nunca `SELECT` + `UPDATE` (TOCTOU).
    - `consume(deviceCode): Promise<{ status: "pending" } | { status: "paired"; deviceToken: string; branchName: string } | { status: "consumed" } | { status: "unknown" }>`:
      busca por `sha256(deviceCode)`. Si no existe -> `unknown`. Si `claimed_at` es null -> `pending`.
      Si `device_id` ya esta seteado -> `consumed`. Si esta reclamado y sin device: genera el device
      token opaco (`randomBytes(32).base64url`), inserta la fila en `tv_devices`
      (branch_id del pairing, token_hash = sha256, name = device_name, paired_by = claimed_by),
      setea `tv_pairings.device_id` y devuelve el plaintext UNA sola vez.
    Todo error de camino invalido va a `log.warn` (nunca `log.error`): un TV mal configurado
    pollea cada 3 s y llenaria Sentry.

    `device-auth.ts` — `makeDeviceAuth(db)` que devuelve un hook `onRequest`:
    lee `Authorization: Device <token>`, calcula sha256, busca en `tv_devices` con
    `is_active = true`, responde `401 { error: "Dispositivo no vinculado" }` si no matchea (401 y no
    403: el TV lo interpreta como "revocado" y vuelve a la pantalla de pairing), y setea
    `request.tvDevice = { id, branchId }` via declaration merging sobre `FastifyRequest`.
    Actualiza `last_seen_at` fire-and-forget (`void db.update(...)`) para no pagar latencia en el
    poll (D-05). Nunca loguea el token.
